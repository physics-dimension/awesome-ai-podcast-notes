# OpenAI 计划将 ChatGPT 打造为全能应用 —— Akshay Nathan 访谈

## 开场：想法与品味成为新瓶颈

我认为瓶颈现在变成了想法和品味。我想，因为现在每个人都能构建东西，所以这真的是一个自下而上的野心的时代。因为有太多东西可以构建，你在任何时候都会受到想法和你能做之事的数量的制约。关于想法一个有趣的点是，它们并非凭空出现。在产品开发中，它们通常来源于与用户的交流，或是对你看到的摩擦、反馈的反应。所以，像我们之前谈到的那些通才，他们能闭环这些反馈，并基于此提出扎实的想法，这永远有其价值。

> **主持人插话**：在进入今天的内容之前，我想对听众说几句。感谢你们。如果不是你们选择点击并收听我们的内容，我们就不可能为你们带来如此渴望的 AI 工程、科学和娱乐内容。几乎每天都有人来找我们谈赞助，但幸运的是，你们中有足够多的人订阅了我们，让这一切在没有广告的情况下可持续下去，我们希望保持这样。我只想请你们帮一个忙：你们能做的、最强大且完全免费的事情就是点击订阅按钮。这是我对你们唯一的请求，这对我以及每周努力将 In Space 带给你们的团队来说意义重大。如果你们订阅了，我保证我们会永不停止地让节目变得更好。现在，让我们进入正题。

## 从无代码到超级应用：ChatGPT Work 的诞生

### 主持人开场与 Akshay 的背景

**主持人**：我们和 OpenAI 的 Akshay 一起在演播室。欢迎。

**Akshay**：谢谢。

**主持人**：还有我们可靠的联合主持人 Vibhu。你们最近推出了 ChatGPT Work，你领导核心产品工程。这一路走来很长。我发现很有意思的是，你从无代码或低代码起步，在 Walrus 和 Airtable 工作过。而在某种程度上，ChatGPT Work 就像是超级应用中的超级应用 —— 终极无代码，你只需写一个提示即可。

**Akshay**：是的，事物真的会绕回原点。我职业生涯的很大一部分时间都在做消费者金融科技，但之后我有了一个假设：我们作为工程师能用代码做到的事情，如果能以更易用的方式带给更多人，那将是真正的魔法。我当时在做一个创业项目，甚至在 LLM 和视觉 LLM 出现之前，就在研究如何用 AI 进行自动化测试，当时还很简陋。之后我在 Airtable 工作了一段时间，秉持同样的理念：如果我们能把数据库或其背后的参数带给用户，那会对他们非常有用。但一旦 LLM 出现，就变得很清楚：这是缺失的那一块拼图，是让每个人都能体验代码魔力而无需了解底层技术的核心技术。所以我认为这个产品的发布以及我们一直在做的事情，正是这一愿景的体现。

### 加入 OpenAI 的感受与不变的核心

**主持人**：你 2023 年加入 OpenAI 时情况如何？现在有了 ChatGPT、Codex 应用、ChatGPT for Work 等等，变化有多大？

**Akshay**：实际上我觉得更有趣的是那些没有改变的东西。我加入时公司大概有 500 人。我担心的是我是否在寻找一个更早期阶段的环境，它是否够创业。结果我发现，它比我能想象的更有创业氛围，而且这一点至今未变。那种自下而上的野心，以及任何人都能提出想法并快速发布的氛围，真的很酷。从使命角度看，当时吸引我的是将前沿智能带给每个人、构建 AGI 并普及给所有人。而且我们认识到，这一愿景不会是线性发展的，我们会尝试不同的产品，会有成功也有失败。但愿景和使命从未改变，现在我们开始看到这些碎片逐渐拼合，这真的很酷。

### 企业级产品的教训：没有一刀切的解决方案

**主持人**：你曾在企业级产品上工作过，很多人从未接触过 ChatGPT Enterprise。你从那里学到了什么，并带到了现在的工作中？

**Akshay**：我学到的是，在企业中没有一刀切的解决方案。我记得在 ChatGPT Enterprise 早期，我们与客户交谈。当时是 ChatGPT 发布一年后，每个人都兴奋地将 AI 引入企业。很多团队成立了 AI 部署团队，预算巨大。如果你问他们想解决什么，起初你会得到一些基础答案，比如我们有这些合同和数据等等。但如果你再问他们一个具体的用例，希望 AI 在工作场所实现什么，你会得到非常多样化的答案。有趣的是，你使用这些模型和产品时，你有一个盒子，可以向它说任何话，这是魔法所在；但另一方面，这也意味着你不知道该用它做什么。在企业中，我认为很大一部分是要真正地满足用户所在的位置，了解他们试图解决的用例，然后教会他们如何利用 AI 获得杠杆。

**主持人**：这是否与“前向部署工程”（Forward Deployed Engineering）有本质区别？

**Akshay**：我认为有市场推广的一面，也有产品的一面。你需要更多地站在产品这边。无论我们在 FDE 方面做得有多好，归根结底，如果用户正看着他们的电脑或手机，我们的产品就有责任帮助他们并指引方向。所以我们对此非常兴奋。

### 过去三年的变化：采用率仍在增长，但机会更大

**主持人**：你认为过去三年采用情况有变化吗？有推理模型这样的阶跃函数变化，但企业仍然存在黑箱问题，不知道如何使用它，还是情况已经改变？

**Akshay**：我们看到现在出现了巨大的增长。每个人都非常兴奋。数以百万计甚至数亿的人在使用 ChatGPT，他们大致知道如何与 AI 合作。但每当新的能力解锁时 —— 比如现在 agent 的出现 —— 仍然只有一批早期用户真正理解它：你可以做任何事情，只要确保有正确的上下文、连接到正确的工具、并进行监督，那么一切都是可能的。但还有 10 倍或 100 倍更大的市场，他们还没意识到这一点。所以我认为这是下一阶段。采用率已经存在并且增长很快，但机会远大于此，尤其是在 ChatGPT Work 上，我们想要在那片领域发力。

## 深入 ChatGPT Work：从 Codex 到超级应用的融合

### 决策过程：Codex 带来的启示

**主持人**：我们跳过前面，直接聊 ChatGPT Work。大概一个月前发布的。是什么样的决策过程导致了它的推出？你们合并了浏览器等。简单总结一下过去几个月的工作。

**Akshay**：感觉已经过了很久，但其实只有几个月。最明显的触发点是我们发布 Codex 时 —— 甚至内部使用 Codex 时 —— 我们注意到一个意外的现象。最近我们发布了一些数据：在 OpenAI 内部，非开发者对 Codex 的采纳出现了真正的拐点。在产品开发过程中，我们会进行 UX 访谈，与内部人员交流。让我印象深刻的是，战略财务、市场营销等团队的人都在使用 Codex 处理他们的用例，这很酷；但更让我触动的是，他们为自己能使用 Codex 而感到自豪。这种感觉像是“我本不该用它，但我用了”，同时也觉得自己拥有了一种超能力。我们当时认识到，Codex 和 agent 的力量，我们已经有庞大的用户群，他们认识并喜欢 ChatGPT。如何向他们展示 agent 的能力，如何把它带给他们，这是一个困难的产品问题。有很多方式可以做到。所以我们将之称为“合并”和“超级应用”，最终以 ChatGPT Work 的形式发布。但这一切源于最初的认知：这种力量不仅仅适用于开发者，甚至可能比我们预期的更早，它可以扩展到所有人。

### ChatGPT Work 与 Codex 的定位：为“工作类”事务而生

**主持人**：你如何区分这些产品？Codex 从 CLI 开始，然后有了应用，现在 ChatGPT、Codex 和 ChatGPT Work 融合了。这是面向普通用户、企业、还是工作场景？你如何定位？

**Akshay**：我们希望它定位在“如果你正在做一些与工作相关的事情”。生产力实际上是我所支持的支柱——这也是团队名称的原因。我们称之为生产力，而不是“企业”或“工作”，是因为还有个人生产力。我在 ChatGPT Work 上看到人们在自己的个人生活中使用它做了一些技术上不算工作的事情，但这些 agent 非常能干。最近一个例子：有人在我们内部的 Slack 上分享，他的包裹没收到，他拿到了快递公司提供的照片，然后他让 ChatGPT Work 帮忙找到包裹。agent 非常执著，它根据照片查看了附近的一些列表，最终确定了包裹所在的公寓楼，并给出了信息。所以我认为所有这些“工作类”或生产力相关的事情，都是我们希望这个产品能做的。

你问到 Codex。我们认为 Codex 是一个持久的品牌，但我们有一个原则：我们不希望用户被困在一个标签或体验中，从而无法获得产品的全部力量。基本上，你在桌面版 Codex 产品中能做的一切，在 ChatGPT Work 中也能做，反之亦然。但我们在产品上做出了一些有观点的决策，比如在获取仓库状态时，我们想向最终用户暴露多少；在显示 agent 思考过程（如 diff 展示）时，我们希望让用户感受到按钮后面的变化；在安全方面，我们如何考虑沙箱，如何在一个状态与另一个状态之间设置正确的默认值。所以背后有一些观点。但我们不希望用户需要去选择他们处在哪种体验中。

### Codex 与 ChatGPT Work 的底层架构：共享 harness

**主持人**：这是一个很好的 AGI 目标：人们不想去选择他们要哪种版本的 AGI，他们只希望 AGI 为他们做决定。我有个问题：Codex 的 harness 和 ChatGPT Work 的 harness 是一样的吗？还是只是 UI 上的差异，或者有提示层面甚至更深层的区别？

**Akshay**：harness 是一样的，是共享的。在两个产品中，我们都改进了 harness，使其更适合知识工作，特别是涉及插件、计算机使用或工件（artifacts）时。无论你处于哪种模式，都能获得这种能力。但在 UX 层面，我们有观点鲜明的设计：在 Codex 模式下，UX 应该如何表现；以及我提到的一些沙箱相关的差异。但底层的 harness 能力应该是相同的。

**主持人**：我有点好奇，有没有什么查询在这两种模式下看起来会不同？比如创建一个退休计算器电子表格。

**Akshay**：我试过类似的事情。在两种模式下，在 Codex 模式（如果你在一个仓库中）你会看到正在创建的工作表的 diff 和文件编辑。但在 Work 模式下，你不会看到这些。这一点很明显。另外一件事我想深入了解的是你的生产力团队。还有哪些顶层团队？生产力不是涵盖一切吗？

**Akshay**：我们有专注于 ChatGPT 核心聊天体验的消费者团队。并非所有都是生产力，人们每天用 ChatGPT 进行搜索、思考如何给亲人写信息、学习新话题、创建图像等等。聊天中有数百种用法，拥有数亿用户，这显然需要专门的团队。此外还有专注于企业、基础设施、API 等领域的团队。

### 合并体验的思考：为什么不是完全分离？

**主持人**：我同时运行了 Work 和 Codex。这是 Work 版本，这是 Codex 版本。我选了 5.6 souls，所以它会花些时间。我们可以放在后台，等完成后再看看区别。但我注意到，如果回到 Codex 版本，你会看到你在一个 Git 仓库中，有些内容可能被隐藏了，因为部分信息在 chain of thought 中。有没有什么你觉得不直观的东西？你们收到反馈后决定不做的？

**Akshay**：在 ChatGPT Work 中，有一个方向我们本可以走：让两种体验完全分离，比如不同的应用，或者在同一应用中完全不同的体验。为什么要把它们合并？Codex 显然深受喜爱。之所以合并，是因为我们所有人的工作都在随着 AI 急剧变化，每隔几个月就完全不同。我们的假设是，我们正在构建的技术能给人杠杆：你可以自动化工作中更枯燥的部分，从而更快地分享更多想法。这可能会模糊一些角色界限：纯写代码、创建战略文档、策划活动、帮助营销或做播客的人。随着时间推移，这些界限会变得模糊。所以根据“你是谁”来划定硬边界会很困难。我们应该让用户选择，但不应将他们框定。因此，我们在保持基础功能统一方面做了很多工作，比如插件在 ChatGPT Work 和云端是统一的。这是因为一个假设：最终所有东西都会汇聚，我们不想把用户框死，但我们会对何时进入哪种体验给予建议。

### 新旧 Harness 的对比：从 ChatGPT 到 Codex Harness

**主持人**：有没有用户习惯了旧的 ChatGPT harness（它现在被 Codex harness 取代了）？可能更偏向对话的一方。你能比较一下这两个 harness 吗？

**Akshay**：ChatGPT 现有的 harness 仍然存在，在这个应用中。当你开始一个新聊天而不进入 Work 模式时，你就在和传统的 ChatGPT 对话。这个版本不会去写代码，不会进入沙箱。实际上，当我们检测到你在创建电子表格时，我们会试图将你推向 Work 模式。这是一个路由决策：模型看到你在尝试做一些更适合在 Work 模式下完成的事情，然后主动引导。你的问题可能是：ChatGPT 聊天 harness 的优势是什么？更广泛地说，你希望我做一个 harness 工程的口述历史。我的观点是，这有点像不断的分歧、收敛、再分歧、再收敛的过程。对于聊天中的很多用例（搜索、学习等），我们一直优化延迟、个性和其他特性，这就是人们喜爱 ChatGPT 的原因。而 Codex 让我们学到的是，当 agent 能访问到一个无限灵活的计算机环境时，它可以做非常强大的事情。所以当我们考虑知识工作该用哪种模式时，我们更自然地倾向于将这个计算机环境引入 Work，并可能向不习惯这种环境的用户抽象一些细节，但同时赋予他们相同的权力。但最终，我们希望在所有场所都拥有这种权力，无论用户在哪里，都能满足他们的需求。所以我相信未来我们会努力使所有场景下的能力对等。这只是历史侧重和当前聚焦的问题。

## 模型选择与使用建议

### 新模型的指南：默认最好，高级选项留给高手

**主持人**：除了 harness 和使用场景，还有新发布的模型。你有什么使用建议？人们喜欢精打细算，比如只在高推理时用 Terra 等等。

**Akshay**：首先，没有这些模型，一切都不可能。Work 的灵感也部分源于 Codex 的成果，而 Codex 的成果又得益于模型能力的飞速提升。现在又出现了一个阶跃函数式的跳跃。对于使用建议，我们希望默认配置是最佳的。所以我们选定了我们认为对大多数人最好的默认设置。对于高级用户，我们提供了一些选项。可能现在的选项有点多，我们正在努力简化。你可以调整推理强度，在不同模型类别间切换，但默认设置应该对大多数用例来说足够好。我的建议是大多数人坚持默认设置。如果你遇到某种情况，觉得在成本效率或智能质量上不满意，可以改变默认设置，看看能否得到更好的结果。但默认设置应该足够好了。

**主持人**：我最近一直在用 Soul Light 配合 Goal，我认为 Goal 基本上增加了推理努力，但有更多的终止轮次和交互。这是一种好的思考方式吗？相比 Soul Ultra 或 Soul 超高推理。

**Akshay**：很难说，因为存在交互效应。这取决于个人的协作偏好：你喜欢与模型有多少交互轮次，以便引导和确保它做正确的事。一般来说，人们应该尝试适合自己的方式。我认为 Ultra 或多 agent 设置最适合极其复杂、开放探索或高度可并行的任务。使用 Goal 最适合那些你能持续做出可验证进展的任务。但大多数任务其实不属于这两类，尤其是刚开始的时候。所以最好的第一步是用默认配置，然后看看你想往哪个方向调整。

### 推理强度滑块：简化为一维

**主持人**：你们设计了一个滑块，这对减少恐慌非常有帮助。在移动端上有一个漂亮的阶梯。

**Akshay**：我还没试过。在高级视图里可以点击。只是一个简单的阶梯。设计理念是，即使有多个维度，也尝试将其投射到单一维度上：一端是速度和效率，另一端是质量和全面性。

**主持人**：我对它频繁使用 Soul 感到困惑。较低档位用的是 Terra？我认为是 Spider。你们预设 Terra 只用于 Light 模式。但我认为更多人应该使用 Terra，因为 Soul 老是容量不足。

**Akshay**：（笑）我就是原因。你看，我们的退休计算器已经跑了 10 分钟了。Work 完成了，Codex 还在计算。我们可以看看思维过程。实际上，这是 8 分钟在 Work 上，Codex 还在计算。你知道吗，OpenAI 安全团队的 Gabriel Chua 给我看了这个，我很震惊这看起来就像 Excel。它在编辑 Excel 文件，你从未购买过 Excel 许可证，但这是可行的、agentic 的 Excel。这次发布的一大重点就是工件（artifacts）。与 5.5 和 5.4 相比，模型侧有了巨大改进，产品质量也在提升。UX 侧也很疯狂，比如托管站点，无需再自己托管网页了。我有个关于此的故事，稍后可以讲。

### 模型训练与 Harness 团队的协作

**主持人**：代码训练方面，你们在发布 ChatGPT Work 的同一天发布了 5.6，这是模型训练团队和 harness 团队相互影响的结果，还是仅仅是发布日期的巧合？

**Akshay**：我们与研究团队密切合作，这是工作中最神奇也最有趣的部分。以工件为例，背后有很多工作：确保我们有合适的基础设施来训练模型以做得更好，同时在产品端为用户提供与模型协作工件的正确体验。这个查看器的直觉是，你可能仍需要 Excel 许可证，但这是第一阶段。当你看到这个工件时，如果它与你实际看到的或发送给同事的结果高度保真，那么迭代和信任就会变得非常容易。

**主持人**：当你提到同事能看到时，是否考虑过多用户、多团队协作的工件？你们有什么想法吗？

**Akshay**：这是我们正在积极思考的事情。在内部，我曾多次遇到这种情况：有人 ping 我一个问题，我让 ChatGPT Work 回答，然后我把答案转发回去。最简单的例子就是我们三个人在一个共享文档上。我在想，这个循环中我是否必要？或许我可以重述他们的问题，或提取一些上下文。但当我反馈答案时，这个过程也是有损的：我给出的只是我对 ChatGPT Work 生成内容的解读。而底层有如此多的上下文和真实世界内容，这可能会很有趣。所以答案实际上是预先响应每一个入站请求。这就像是 AI 之间的消息转发服务。这有助于人们了解他们可以提问和委托什么，很多人在尝试或看到别人演示之前都不知道。同时还有一个轻微的安全问题：本质上你是权限层。我可以查询一切并得到自动回复，但也许我不应该看到那些内容。我不知道我不知道的东西。特别是当 ChatGPT Work 连接你的插件、从本地文件拉取内容时，agent 能够访问的上下文是高度个人化的，我们需要保护这一点。这绝对是个挑战。

## 工件与站点：知识工作的新范式

### Excel、PowerPoint、Docs 之外的新格式

**主持人**：Excel、PowerPoint、Docs 是工作的三大件。你们还考虑哪些工作格式？比如你在 Airtable 工作过，未来会不会有 OpenAI 版的 Airtable？

**Akshay**：这是个好问题。你没有提到站点（Sites），而这是这次发布的重要组成部分。站点有一个方面经常在 Twitter/X 上被讨论：它像一个原型工具。实际上，就连你们刚才提到的模型滑块，也几乎完全在一个站点中开发。设计、工程、产品团队在这个站点上协作，调整控件，感受交互。但另一个较少被谈及的是，站点也是一种知识工作的工件。前几天我和公司财务团队的人聊天，他们提到，以前团队每月协作的报告是用幻灯片和电子表格做的，现在都改用站点。因为它的带宽更高。PowerPoint 和 Excel 虽然无限灵活，但有时你作为用户可能不知道如何使用某些功能，或者产品本身不支持。但在站点中，你可以要求任何东西，也能得到任何东西。一旦人们看到这种魔力，它就变得非常有价值。

### 个人案例：从游戏到研究工件

**主持人**：让我展示一个我的案例，涉及 ChatGPT Work、5.6、token 亿万富翁、token 最大化、站点和自动研究。我喜欢一个叫 Strata 的棋盘游戏。我拍了 30 张照片扔进 ChatGPT，消耗了 17 亿 token，最后出来一个可玩的站点，支持 3D 方块放置等。因为我需要实体块和训练朋友，所以我也能训练 AI，让 AI 自我对弈。我定义了一个损失函数，让它们自学。我那时在圣马特奥参加会议，所以用了自动研究来创建基准。参数太多，我开始让 ChatGPT 为我创建一个站点，它创建了一个实验面板。在侧边栏中可以看到站点。作为研究工件，它能很好地传达正在做的事情。后来我把它移出了站点，因为我需要更多的数据库和基础设施，但这是你可以开始摆弄并调试超参数的研究输出。你不再阅读 ChatGPT 的文本输出，而是阅读站点输出。但这也带来了大量信息过载，所以还需要进一步整理。这从 Markdown 过渡到完整的功能站点是有趣的趋势。

**Akshay**：是的，Markdown 对阅读来说并不最优，不如直接写 HTML 网站。你可以通过技能（skills）定制很多内容，很详细。站点可以并排，你可以迭代想要和不想要的内容。

**主持人**：我好奇你们内部是怎么用的。我这样做对吗？

**Akshay**：我认为这是一种我们看到的、各种团队都在使用的工作流。以前是 Doc 的规范工件现在变成了站点。因为站点就是 HTML，无限灵活，你可以让某些内容更突出，比如设置为英雄图。显然还有更多工作要做，让协作更容易。你提到它们很长、很啰嗦，可以拆解，我们可以做些什么。

### 平衡简单性与能力

**主持人**：你的工作也变成了元层面：你不是在设计产品，而是在设计一个制造产品的产品。你如何管理这一点？

**Akshay**：我们在 UX 方面思考了很多，如何平衡简单性和能力。如果正如你所说，我们设计的产品是为了制造其他产品，那么可以构建的东西太多，我们不能把所有东西都放在你面前，否则你会不知所措。即使是在 ChatGPT 中，我们也面临类似挑战。现在能力更强了，我们不断在寻找平衡：给用户足够的 UI 表面，让他们能够表达需求、验证 agent 使用了正确工具和来源，然后让系统为他们展示而不是告诉他们能做什么？因为很多情况下，用户需要发现下一个用例，如果他们想要被 AI 赋能的话。

## Codex、Work 与个人用途的融合

### 从 Codex 到 Work：不同用户的不同路径

**主持人**：每个人做事情的方式不同。我做了类似版本的游戏，没有拍照，而是扔给 Goal，18 分钟 53 秒后，得到类似版本，但没有自动研究。我用了 Codex 而不是 Work，但很有趣。我当然用 GPT 图像生成头像，这对游戏设计很有用。

**Akshay**：更广泛的收获是，我们做这些是为了测试工具。在 5.6 发布之前，我用 5.5 做过游戏，它需要我提供规则（很 niche 的游戏，自己找不到）。5.6 能自动分发规则，所以我非常想测试 5.6 的能力。随着新东西的发布，这些只是我们测试的侧面方式。这也像是私人电子邮件，并不完全隐私，但也很有价值，因为现在你可以把站点发给朋友，他们通过这个了解游戏。

### 工作与个人生活的渗透

**主持人**：这显示了工作如何轻易地变为个人，个人变为工作。我做的个人事情直接影响了我工作中的人，给他们展示了“哦，ChatGPT 还能做这个？”这大概是增长策略。

**Akshay**：是的。“展示而不是告诉”是我们尚未完全破解的一大课题：如何向用户展示他们能用产品做什么，而不是通过文章或引导来教学。

**主持人**：对我来说有职业风险，因为我以前做开发者关系，工作就是展示。但现在产品的人说，如果产品足够直观，就不需要你了。

**Akshay**：这就是模型的魔力。你可以根据用户的需求、他们的历史、他们在采用旅程中的位置，为每个人定制展示。这是一个巨大的机会。

### 分阶段实现人人可用 Agent 的愿景

**主持人**：现在定制展示似乎越来越容易。你说你们团队更广泛地关注“生产力”，现在叫“Work”。是否还有我们未覆盖到的人群？ChatGPT、Codex、Work 之外，还有更多吗？

**Akshay**：我将其视为一个序列。愿景是为每个人带来有用的 agent。我们从开发者开始，他们是早期采用者，愿意容忍更多摩擦。这是 Codex 的起点。下一个机会是通用知识工作者——开发者之外的所有其他职能。从开发者到这一群体，内在的挑战包括“展示而不是告诉”，要让产品更易理解，带来更多针对这一群体的能力如工件、计算机使用等。然后，就像我们将从开发者身上学到的经验带给知识工作者一样，下一步是将这些经验带给所有人，无论他们在生活中做什么。我们已经看到一些迹象，比如你的游戏例子正好位于乐趣/个人生活和职业生活的边界。我在工作和家里都使用 ChatGPT Work，前阵子我让它制定一个膳食计划，并保存在它所拥有的电脑环境中，方便以后查看。是否每个人都在这样做？可能还没有，因为还有一些需要完善的地方，但最终我们想让人们达到那个状态。我们已经在软件工程中建立了基础，并将同样的经验从软件工程带到知识工作，再带到所有人。

## 高级用户建议与内部实践

### 扩大想象力：不断尝试新可能

**主持人**：你有什么高级用户建议？有一群人会 24/7 使用它做所有事，而另一些人只是偶尔用于工作。有什么学习或建议来弥合差距？

**Akshay**：我看到几点。第一，拓宽你的想象力：技术发展如此之快，三个月前还不可能的事，现在竟然可以了。比如我们正在进行的内部绩效评估周期。过去人们常说不想写评估，可以用 AI 来做，但过去生成的内容很“垃圾”，聊胜于无。现在我发现模型能做得比我好得多，特别是在这个环境中：它可以拉取上下文，了解人们做了什么、有什么贡献，突出你可能没注意到的成就。它拥有所有接触点：代码、Slack、所有东西。这非常强大。只是在六个月前的评估周期中，我尝试过但毫无帮助，而现在却极其有帮助。所以持续拓展想象的边界，即使你之前尝试过，我觉得这是最大的建议。第二，你投入得越多，尤其是在 agent 可以访问你电脑上一切的环境中，你可以创建工件并保存在库中，模型持续访问它们。你给它关于你生活或工作的信息越多，它就变得越有价值。它可能会以意想不到的方式变得主动，比如从上下文中提取信息。

### 绩效评估中的 AI 使用：上下文收集而非直接输出

**主持人**：你提到绩效评估。作为管理者，我对 LLM 生成的内容非常谨慎，尤其是涉及对人的评价时，感觉你不够关心。在 OpenAI，人们可能更开放地被 GPT 评估。你们有非正式规则吗？使用礼仪是什么？

**Akshay**：我永远不会完全通过 AI 写一份评价并直接呈现给人。我指的是收集上下文。这更像 agent 搜索。因为 Codex 让人们做更多事，ChatGPT 让更多人做比以往更多的事，所以人们很容易错过一些东西。我们需要用这些工具来跟上大家的影响力，理解在哪里可以提供帮助。

### 内部案例：自动生成梗图与信息发现

**主持人**：在 OpenAI 的规模下，Slack 信息量巨大，你认为它会遗漏东西吗？

**Akshay**：可能会，但我自己也会遗漏。有时它能发现你发现不了的东西反而更好。我现在设置了 Codex 系统提示，让每个项目都有单独的 notes.md，代理会自动记录学到的东西，全局代理可以从所有笔记中拉取。有时它会说：“哦，你四个月前有这个项目，这里有一条我们已经有的笔记。”这很超人类，我根本不会去想。它可以节省分组的时间，发现已经完成的事情。虽然可能会遗漏一些我会做的事情，但当它发现一些东西时非常有用。我有一个非超级工程的解决方案：简单的 Markdown 文件，需要时就被拉取。

**Akshay**：我讲个趣事。在筹备这次发布的过程中，团队非常努力，Slack 和文档里有很多交流。团队成员设置了一个定时任务，自动查看所有信息并生成最好的梗图，发到共享频道。有两件事很酷：第一，模型随着时间的推移开始变得有趣了，一年前完全不是这样。第二，它们以令人惊讶的方式发现联系，这有助于生成梗图，因为你能看到一些让你真正感到意外又有趣的东西。这当然不是最生产力的用法，但它展示了模型正在浮现的另一种能力：发现你本来不会知道的信息。

### Open Claw 的灵感

**主持人**：另一个大事是 Open AI 的 Open Claw。我认为那是很多人第一次真正为个人生活最大化 agent，同时也跨越到工作。据我所知，Open Claw 仍是独立的，但你们有自己的 Open Claw 时刻吗？你们从 Open Claw 学到了什么，带到了 Codex 或 Work 中？

**Akshay**：有很多灵感。我确实有我的 Open Claw 时刻。

**Akshay**：我试过。ChatGPT 目前还不保管你的现金和资产，所以那部分还没有。但退休规划、财务规划、预算等，通过金融插件，已经可以在 ChatGPT 中实现。所以至少那部分已经被我替换了。

**主持人**：集中在一个空间也很好。不同的健康应用分散各处，能集中在一起很棒。

**Akshay**：这也是 Open Claw 的整体理念：拥有一个个人操作系统，ChatGPT 可能也希望成为这样的角色。

**Akshay**：我不能谈论所有细节，但取决于访问模式。如果你需要立即回答，从所有来源拉取很困难。但 ChatGPT Work 启用的很多用例并不需要即时结果，而是 agent 去执行的任务，需要一定时间。通过程序化工具调用和子 agent，部分时间可以并行化。我相信，通过 MCP 和第三方服务调用的天花板已经大幅提高，所以我们对此很兴奋。

## 子 Agent（Sub-agents）与 Ultra 模式

### 子 Agent 的设计权衡

**主持人**：你提到了子 agent。Ultra 是新模式。ChatGPT 自身有特殊界面来显示 agent，但老实说，我注意不到太多操作，只能看着。你的体验如何？对于正在构建子 agent 的其他开发者，你有什么设计问题要指出？

**Akshay**：这又回到了我之前提到的平衡：向构建者展示工具的威力，同时创造足够的抽象以免让他们不知所措。对于子 agent，我们想展示的是，你可以将一个有多个并行轨道或很复杂的任务交给 agent，模型能尝试完成它。这就是我们设计子 agent 界面的目的。还有另一个迭代版本，你可以看到他们确切在做什么，但那可能会信息过载。这是我们目前做出的双重权衡。

**主持人**：你们确实显示了很多对话。

**Akshay**：是的。

**主持人**：我认为你可以显示更多。有人想要更多。我几乎每次用 Goal 都会告诉它“尽可能使用子 agent”。我很多朋友也这样做。而有些人则希望只在特定子任务中使用子 agent。他们可能会欣赏看到子 agent 如何被使用。对我来说，主要是两个原因：一是净时间效率，扩展到子 agent；二是成本，用更小更便宜的模型。有些人希望有这种控制级别。如果你有重复性的工作，你可能想进入并微调某些子 agent。目前默认是隐藏的，有一个下拉菜单可以展开。你可以改变子 agent 使用的模型吗？我知道 Anthropic 在 Claude Code 中提供这个功能，你可以指定子 agent 用 Sonnet 或 Opus。这很简单，你通过提示告诉它。我认为这是一个可以构建但尚未实现的东西。但太多的切换开关并不好。实际上，我只在聊天中告诉它，通过提示实现。我认为抽象是好的，除非你正在构建一个重复性的工作，比如播客准备，你可能想配置更便宜更快的模型用于网络搜索。我理解一个你可能想要两者兼顾的世界。目前的默认设置（隐藏但可展开）是相当不错的。

### 子 Agent 的设备性能问题

**主持人**：很多人谈到 5.6 发布时，这个 agent 大量使用子 agent，导致 ChatGPT 应用因为处理器负担过重而崩溃。你的个人经验如何？

**Akshay**：我的没有因为子 agent 崩溃过。我们俩都有大笔记本。但我看到了讨论。另一个方面是，在发布时，我们对 Ultra 的定位不够明确，之后我们做了一些改变，要求你主动在高级设置中打开它。这也影响了反馈来源。

**主持人**：好的，重置限制。

**Akshay**：（笑）今天又重置了。

## 记忆系统与 Chronicle

### 记忆 V3 与 ChatGPT Work 的继承

**主持人**：我想谈谈 harness 的最后一部分：记忆。很多人最近在评论记忆。ChatGPT 的新记忆系统曾被认为不好，但现在好了。Samir 也在谈记忆。你能说些什么？

**Akshay**：Samir 和研究团队做了大量更新改进。当我和朋友、家人聊起他们为什么喜欢 ChatGPT 时，“它了解我，感觉是我的 ChatGPT”这一因素经常排在第一位。ChatGPT Work 和云端默认从 ChatGPT 记忆继承，所以它们会知道与你相关的上下文，并且能够写回记忆。这是同一个 V3 系统。非常强大，因为从 ChatGPT 到 ChatGPT Work 感觉像是你已经用了很多年的产品的延伸。很高兴人们认可这些改进。

### 记忆中的精度与时机

**主持人**：这是一个检索问题，对吧？是检索正确的东西，还是过度关注错误的东西？假阳性还是假阴性的问题哪个更大？

**Akshay**：我不直接负责记忆，所以不能肯定。但我认为你说的对。有两个方面：确保它了解你，以及在正确时机具有情商地主动提出那些信息，以积极而非消极的方式让你惊喜。这是一个非常有挑战性的问题，但也是一个巨大的机遇，所以我们投入了很多。

### 记忆在工作与聊天中的不同：深度与持久性

**主持人**：当你构建 ChatGPT Work 时，与普通聊天应用或 Codex 相比，你认为管理跨项目、跨会话的记忆有什么不同？四个线程在一个项目上，记忆系统如何学习？

**Akshay**：首先我要挑战一下：记忆的深度和价值的根本性在聊天和工作之间可能并没有那么大。ChatGPT 产品已经存在很久，人们已经在用它做与工作相关的事情。我发现所有那些一次性的对话累积起来，形成了一种非常持久且能代表我的表征。有时关于 ChatGPT 了解你一切的帖子会在 X 上走红，人们总是惊讶于它能知道那么多。所以我认为现有的 ChatGPT 产品中已有很大深度，这就是为什么我们认为将其带入 Work 产品是有价值的。另一点是，我们希望可以使用相同的基础原语和系统来扩展 Work 中的记忆，我知道负责记忆的团队正在努力解决这个问题。

### Chronicle：超级记忆与上下文输入

**主持人**：我想提一个我其实不怎么用的记忆元素：Chronicle（屏幕上方显示）。它类似于超级记忆？你怎么看？

**Akshay**：它的想法是，它可以学习你如何使用电脑，成为记忆的另一个输入源。目前还是实验性的，默认关闭，但我建议你尝试。它很有意思，回到我们之前的对话：ChatGPT 会错过东西吗？Slack 搜索会遗漏吗？因为信息量太大。同样的问题也适用于你在电脑上做的所有事。它可能不会知道一切，无法捕捉所有意图，但它很可能会发现一些你不知道的东西。如果它能在你执行任务时以相关的方式主动呈现这些内容，我认为会很有帮助。值得一试。

**主持人**：主要用于洞察和长期上下文？

**Akshay**：是的。洞察和构建上下文，能让你在某些任务上更高效。但很难用语言描述，需要亲身体验。

**主持人**：可以说体验很明显。“查看我的记忆或日志并添加技能”这个功能被低估了。

**Akshay**：那是自动化，你可以用 cron 重复。但从 Chronicle 本身创建记忆才是不同之处。因为开启 Chronicle 后，你会有更深层的记忆。

**主持人**：它就在那儿，我没怎么用。也许我需要更多例子。我猜你们内部大量使用，所以我总是问用例。

**Akshay**：我会建议你打开它，它会自动工作。看看它在哪里开始帮助你。我想你会惊讶的。

## 构建 AI 产品 vs 前 AI 时代：角色与测量的变化

### 速度与范围的变化

**主持人**：很好。我想我们已经大致覆盖了 ChatGPT Work。很多前创始人在 OpenAI 社区。你认为构建前 AI 和构建后 AI 有什么不同？

**Akshay**：变化太大了。从想法到能够真正构建出东西的速度令人激动。即使 5 到 10 年前，如果你很拼，也能很快构建最小可行产品，但现在你能构建的范围广得多。这让你能更快验证，与用户交流，确保走在正确道路上。这个循环比以往任何时候都更紧密，这对产品开发来说是胜利。对消费者和用户来说也是胜利，因为他们从一开始就能得到更好的产品。

### 团队规模与角色融合

**主持人**：这是否意味着你的团队更小？

**Akshay**：现在有更多事要做。人们可以单独或在小团队中完成以前需要更多人的事，但同时也面临更多任务，所以团队变得更有雄心。

**主持人**：你看到团队角色范围的变化了吗？现在理想的团队和几年前相比如何？

**Akshay**：我看到了典型的开发职能之间的界限模糊化：工程经理、产品经理、工程师、设计师等。

**主持人**：我引用一句玩笑：未来科技界只剩四种工作：AI 内容大炮（大量消耗 token 的人）、SRE（负责的人）、卖东西的成年人、以及“性感的人”。（笑）

**Akshay**：有趣。我猜测每个人都会变成 T 型人才。AI 让每个人都能成为通才，比如我过去无法完成设计，现在即使没有视觉品味，也能借助 AI 迭代出东西。但每个人都会有自己的专长，那是 T 的竖线。在 AI 帮助下，你可以从专长出发变得更好，同时你也是通才。有了这个基础，你能做的事情几乎是无限的。

### 当前瓶颈：想法与品味

**主持人**：你在专长上受什么限制？需要更多设计师？更多内容大炮？更多“性感的人”？

**Akshay**：我认为瓶颈变成了想法和品味。因为现在每个人都能构建，这确实是自下而上的野心时代。因为有太多东西可以构建，你总是受限于你能随时产生的想法和手头正在做的事情。

**主持人**：你认为模型能帮助解决这个问题吗？比如，在 UI 设计上，模型给我四种截然不同的示例，我消耗大量 token，然后综合起来。但我希望做但做不到的是“带给我新想法”。LLM 在这方面就是不行。

**Akshay**：想法有趣的一点是它们不是凭空产生的。在产品开发中，想法来自与用户交流、对摩擦的反应、反馈。所以我认为通才的价值永远存在：他们能闭环反馈，提出那些基于用户交流的扎实想法。

## 生产力团队的使命与测量

### 如何定义生产力？

**主持人**：你领导生产力团队。你如何定义生产力？

**Akshay**：我们的使命是让人们能够做以前不能做的事情。目前我们从知识工作的角度出发。当我们看知识工作，我认为人们不再被他们的角色、背景或训练所限制。无论你在哪个职能，你都能突然构建东西，突然获得原本可能无法解读的数据。这延伸到个人生活：最终我们想给你杠杆，让模型和产品能为你创造时间，去做你热爱的事情。

### 测量生产力的挑战

**主持人**：这能否转化为测量生产力的方式？你如何测量杠杆？

**Akshay**：我们还没搞清楚。部分原因是非常多样化。每个人都有不同的目标，真正的衡量标准是他们达成目标的能力。我们是否帮助了他们？没帮助？在没有预先知道目标并为个人定制的情况下，非常困难。

**主持人**：ChatGPT 的赞和踩不能说明什么。

**Akshay**：是啊，你不知道用户是讨厌回答的内容、语气，还是它是否帮助实现了目标。我们和整个行业都需要解决这个问题，因为如果这是我们的目标，那么这就是衡量成功的方式。

### 从代理指标到结果

**主持人**：你认为这里生产力是否改变了？你提到现在有更多工作、更大范围。它改变了测量的方式吗？

**Akshay**：一直以来的真正目标是知道你的团队、个人或你自己是否达成了目标或更接近目标。但过去我们使用代理指标：代码提交次数、代码行数、故事点等等。现在随着 AI，这些代理开始失效。你消耗的 token 数或拉扯请求数可能不再与团队是否达成目标高度相关。所以我们需要想出新的衡量方法。

### 给管理者的建议：关注“上场次数”的质量

**主持人**：对于正在听的管理者，给他们一个建议。

**Akshay**：对我来说，重要的是“上场次数”。不仅是数量，还有质量。我们团队是否建立了从产生想法、构建、获取反馈、验证假设、走向下一个想法的能力？能不能高效地做这件事？这关乎实际写代码、设计、规范等，也关乎团队文化。我们是否有谦虚和热情，能多次经历这个过程并保持动力？在当前技术前沿，有如此多东西要构建，这是最重要的事。

### 陷阱：将运动误认为进步

**主持人**：人们在使用 AI 测量生产力时常掉入什么陷阱？有些企业添加了很多 LLM，有了各种仪表板，但没什么改变。

**Akshay**：这本身就是陷阱。陷阱可能是把运动（motion）和进步（progress）混为一谈。由于现在的工具，运动变得前所未有地容易，但进步需要你非常刻意和明确地定义你想达成什么。这就回到了我们关于测量的问题：OpenAI 能否找到测量用户生产力的方式？这因为多样性而非常困难。但作为团队，你应该对什么是进步有一个明确而刻意的观点。如果没有，很容易混淆这两者。

**主持人**：这个关于运动与进步的讨论非常好。这将是我们未来文章中的一句引用。
