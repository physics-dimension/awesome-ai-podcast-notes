## 从模型训练到 Harness：ML 堆栈的转变

**Alex：** 我认为，今天之所以能做到这一点，是因为我们正在进入 **ML 堆栈中的一个新层级**。直到最近，我们仍然专注于让模型在它们所做的事情上变得更好。这里的“模型”指的是权重——你训练模型：最初是大型预训练，然后是微调，让模型在特定任务和思维上表现出色。我认为，过去一年向代理的转变，让我们更加意识到 **harness、工具、以及我们提供给 LLM 大脑的“身体”中所蕴含的力量**。

现在正在发生的转变是，我们开始意识到，当我们调整这些 harness 时，它们会变得非常擅长特定任务——要么做得更好，要么更高效，即用更少的 token 调用、更少的使用量，从而降低成本。**成本现在是巨大的问题**，因为前沿模型越来越贵：它们更大、更难服务、需要更多 GPU，等等。

所以这个项目来自我过去一年在 Berkeley 所做的关于发现系统的研究，即 AI 驱动发现。这个项目来自 Berkeley 的 Sky Lab，叫做 Sky Discover。它是一个试图优化和改进系统的外层循环。我特别好奇的是，如何把它推向极致：如果有一个外部系统在优化某个内部系统，那么如果你想优化这个优化方式本身，就需要一个外部的外部循环，无限递归。我认为唯一的出路是**把循环折叠起来**，让系统本身负责改进自己，我称之为“折叠循环”。

这与有一个外部观察者在系统运行时试图改变另一个系统非常不同。我希望系统能够在运行时改变自身。这就是 Exo 的论点。

## OpenClaw 的可适应性与局限性

**主持人：** 我想补充几点评论。第一个意识到这一点的人可能是 OpenClaw 的人，对吧？他们说 harness 应该修改自身来添加所需的能力，但它并不是你设想的那种完全自递归。第二，我们已经做过一期 OpenClaw 讲座，我会在描述中放链接，人们应该看看，如果和这次对话相关，我们可以聊一点。第三，我没有关注过这个。对于我的两家公司，我有一个内部 bot，还有一个外部 bot Devon 来修改内部 bot。内部 bot 没有能力修改自己。老实说，我喜欢这种分离：一个做伪事，一个做事，一个做伪事，对吧？区别显然不是魔法。就像你开车，然后打开引擎盖来修改汽车，如果需要的话，但大多数时候引擎盖是关闭的。那么问题来了：**你什么时候需要那种“哇，它未经我要求就自我修改了”的 AGI 感觉？** 这两点是我的评论。

**Alex：** 两个观点都很好。让我谈谈这两点。OpenClaw 在二月份真正火起来。你说得对，OpenClaw 真正发现的是如何让一个代理系统感觉神奇，因为它能适应你的工作流程。它确实是可适应的。但我想指出一点，**它的适应性是以一种非常特定的、狭窄的方式进行的**。

如果我们去看架构，OpenClaw 的人把它做成可扩展的地方有特定的几个：

- 一个超级动态的方式是**记忆**。所有这些代理系统都有某种记忆。实际上就是一个 memory.md 文件，写在某个地方，每次构造 LLM 调用时注入上下文，我们可以编辑那个文件。这是主要的超级动态方式。
- 另外，OpenClaw 暴露了一些你可以扩展的地方：你可以添加**技能**，你可以让代理去查看这个技能并添加它；你可以添加**工具**。
- 而且这通常由人来驱动。一个人过来说：“嘿，我想要一个技能，让我安装这个技能。”然后让 OpenClaw 去做。

所以这绝对是**自我改进和可扩展性**，记忆是一种自我改进。但代理内部还有更多东西。

## 什么是代理：策略与记忆

**Alex：** 什么是代理？顺便说，我认为值得站在同一个页面上。每个人都知道代理，但有一个共同的定义很重要。我认为代理是**包裹在用于构造上下文的机制中的 LLM 调用**。它实际上是一个大型上下文构造机器，同时它提供执行行动的方式。所以部分上下文是“我可以做的事情”，LLM 可以说“请执行这个工具或行动”，代理负责实际采取行动并反馈回来。用于构造上下文的机制，我称之为**策略**。

那么策略包括什么？

- 可以是实际组装 LLM 调用的方式：你取历史中的最后 10 条消息，还是最后 100 条？这会更贵但提供更多信息。或者取最后 10 条消息加上前 90 条的摘要，这就是紧凑化的思路。
- 这些都是静态策略决策，在 OpenClaw、Pi 或 Claude Code 的源代码中定义。

所以这就是代理是什么的策略：它能用哪些工具、有哪些技能、如何把它们纳入上下文、如何构造上下文、任何关于代理实际代码的东西。这就是 **Exo 要真正实现完全递归自我改进的东西**。它不仅是在某些点可以插入额外技能，而是改变技能本身的工作机制。

## OpenClaw 架构图与 Exo 的差别

**主持人：** 以及构成它的策略。我只是想说，如果我们共享屏幕，可能会用一些图表。现在可能是时候拉出架构图了。

**Alex：** 完全可以，让我调出来，这样更容易讲。在这里我们可以看到，这是我在“自主系统设计原则”讲座中的图，那个讲座实际上深入剖析了 OpenClaw，因为它在我开始做 Exo 前大约一个月出现。你可以看到这个架构的核心层是**网关控制器**，底层是实际的**上下文组装**，顶层是**连接器（connectors）**，也就是你与它交互的方式。我用红色标出了**插件部分**，这些是使其可定制的点，针对特定任务。

比如：

- 你想以不同方式管理记忆。比如你在做某种开发，查看大量不同文档，你可能希望记忆中有多个项目的文档，但你可能想对它们运行 RAG 来获取最相关的部分，包含在上下文中。这个记忆插件允许你指定不同的存储和索引方式。好的，由人类来设置。
- 或者有工具，你说“我想给 OpenClaw 一个额外的工具”，或者技能。还有 ClawHub 这类网站，列出你可以安装的工具或技能。

这仍然是由人来修改，你可以说“请帮我安装这个工具”。但我们试图做出的转变是：**所有其他没有标红的部分——所有连接箭头、所有组件——我们认为都需要由代理自己改进**，尤其是随着代理越来越好。因为代理越来越好，这是苦涩的教训。你不想过度专门化，因为你不希望人类决定所有架构位。随着模型变好，它知道如何为给定任务构架最合适的代理。这就是转变。

如果把 Exo 架构放在旁边，我会**在所有组件周围画红圈，说它们都可以由代理自己改变**。

**主持人：** 是的，这是最极端的版本。另一个你想让我谈的问题是什么？你想要的**显式开关还是隐式开关**？大致是这样的问题，对吧？隐式开关是最信任 AGI 自己搞清楚一切的时刻。而显式搜索是为那些不信任机器的人准备的？

**Alex：** 我会说，然后我会去讨论其他架构。但我想趁现在还清晰时谈一下。我会指出，**当你有一个外部独立代理修改内部代理时，你仍然在信任机器**。这不是你在做改变，对吧？你可能在引导它，但你对机器的信任是一样的。问题是：你是有一个外部系统来检查内部系统，还是让正在运行的系统自己检查自己？

当你把两个层合并时，很酷的是，**决定做修改的同一个系统也决定运行什么，也决定检查什么**。因此你的系统可以自己尝试事情，观察自己表现如何，观察内部运行情况，并在运行时对自己做修改。

我可以给你一个很好的例子。我们让 Exo 运行玩 Pokémon，在运行时，系统自己决定尝试检查游戏的内存，然后去映射内存。过去人们手动逆向工程，弄清楚了内存映射中哪些组件对应游戏中的不同功能。比如内存中有一些位置存储了世界坐标、当前活跃的宝可梦、你是否在战斗中——字面就是布尔值。代理能够修改 Exo 自身与游戏的集成，将这些信息输入系统消息，以便在进展中做出更好的决策。

外层循环必须考虑这个，可能尝试一个设计，告诉它，启动，看看效果，再反思。如果系统本身在演化，当它做出改变时，它可以检查事物，并利用这种运行时检查来指导其设计过程。所以我认为这是一种**更强大、更完全表达的自我改进方式**，比外部系统更好。

**主持人：** 嗯，说得对。

## Exo 的三层架构：Executor、Harness、Sandbox

**Alex：** 好的，让我谈谈 Exo 架构。这个项目真的是一个**自我改进的代理**，但这是由一个有主见的、非常仔细地划分代理的 harness 架构实现的。我想和今天我们对代理的看法作个对比。

当你想到 Claude Code 时，它既是一个代理——人们通俗地认为它是一个代理——也是一个 harness，它们捆绑在一起，你把它放到一个环境中工作。我的常见工作流程是：我启动一个 VM，进去，启动 Claude，然后在那里处理项目。我克隆一个 repo。我必须用我的 GitHub 凭据登录，这样它才能为我推送东西。然后我在这个隔离空间中工作。我相对信任它，然后我使用“跳过权限”这样危险的操作。在 VM 中，我在这里接受这一点。哦，这有点冒险，因为实际上我在里面登录过。我可能有钥匙，当然有我的 GitHub 凭据。但好在这至少不会毁了我的电脑，因为它在某个 VM 里运行。

我们提出的架构将代理的概念分解为**三个不同且重要的层**：

1. **Executor（执行器）**
2. **Exo Harness（Exo 束缚/驾驶舱）**
3. **Sandbox（沙箱）**

这些层具有不同的属性，这非常重要。

- 我们认为 **harness** 需要保存所有状态，即我们希望保护的最小集合，不被代理访问。它是代理使用但需要保护的东西。
- **executor** 包含所有策略。我们之前讨论过策略：策略包括如何组装上下文、你的提示是什么、如何做紧凑化、你的技能是什么、你的工具是什么，以及任何关于代理实际如何决定它要做什么的事情，对吧？这样我们有了一个很好的划分。
- **executor 是完全没有状态的**——一个完全无状态的过程。
- **harness 包含对话历史、可能需要的秘密（如 API 密钥）、工件或环境快照**。
- 最后，**sandbox 层是事情实际发生的环境**。

这不是超自然的。今天，Claude Code 在同一环境中运行，和被它编辑的代码在一起。你把它放到你的机器上，Claude Code 作为一个进程在你的机器上运行，编辑你机器上的其他文件。或者你把 Claude Code 放到 VM 中，它在那里运行并编辑 VM 上的文件。我们把它分开：实际动作（比如代理想运行一个 bash 命令）在 sandbox 中执行，而策略进程可以在任何其他位置运行。

但这样划分给我们带来的是：

- **隔离的执行环境**
- **受保护的状态**
- **一个显式的、无状态的、适合自我演化的层**

因此 executor 可以提出对自己的更改，而不会丢失任何历史，不会泄露秘密，因为秘密不暴露给 LLM。我们的 harness 提供了一种快照机制。这对你非常有用：你可以给 sandbox 环境拍快照，策略本身可以在运行时选择尝试做一些更改，然后回滚。这是 Exo 背后的基本架构。

我想指出这些层次给我们的东西。现在一个代理——这是理解 Exo 和 Exo harness 架构最难的部分——被分解成三部分：**它是存储在 harness 中的对话历史（状态），加上正在运行的策略（executor），加上它运行的 sandbox**。这三者一起定义了我们今天认为的代理。希望这讲得清楚。

**主持人：** 我很喜欢这个分类，很清晰。我对一些要点有疑问，但我想在进入细节之前先听完顶层。

**Alex：** 好的，我再讲一张幻灯片，让这完全具体，然后我们进入细节。同样，这是我认为实现 Exo 的架构。在这个架构中，为了使它具体：你有 sandboxes，你有一个完全有状态并保存状态的 harness，你有 executor 在上面运行。在这里你可以看到策略、所有紧凑化、工具、技能、LLM 调用等。

Exo 采取的步骤，真正让它成为一个自我改进的代理的是：**它在 sandbox 中挂载了 executor 自身的代码**。因此，LLM 可以做出的部分决策是，它可以说“嘿，去在运行时修改自己 harness 的某些方面”。我们在 Exo harness 中有一个特殊的**守护进程**，允许 executor 在运行中途被重建，并且还提供了一种浸泡过程：重建后，我们尝试启动 executor，让它前进一步，如果它意外破坏了自己，它会自动回滚到之前的状态。

这就是所需的最小组件集，因为现在你有一个 executor 可以看到自己的代码，可以编辑自己的代码，可以要求重建自己的代码并在运行中交换，最后，它受 Exo harness 保护，会回滚它。同时，这个机制可以构建新工具、编写新技能、改变上下文组装方式、调整适配器等等。**这就是让 Exo 完全递归自我改进的最后一步。**

**主持人：** 这也意味着提议的更改可以并行化，因为 executor/harness 整体在提交更改时具有原子性，关注点分离良好。如果你想回到……我落到的第一点是：最后一点是否可转移用于“teleportation（传送）”？这有多重要？传统上，人们想本地运行，然后想合上笔记本电脑，移到云端。这是人们做代理状态传送的唯一原因。这里指的还有其他东西吗？

## Teleportation 与多租户扩展

**Alex：** 是的，这是个好问题。在运行单个代理处理单个任务的世界中，你几乎没有必要传送。你要么在本地运行，要么——如果想让它在笔记本合上后继续——你必须一开始就在远程服务器运行。我明白你的意思。

好处是：如果你想扩展到并行处理多个不同任务，有多个不同对话，这是一个非常现实的需求。你和我管理邮件不需要，但一个公司可能需要。假设一个公司想为每个用户的使用日志启动一个代理对话。用户进来使用你的应用，你有一个库，记录日志到数据库。事件流传来，你希望一个代理对流进行推理。你可能希望为每个对话唤醒一个专用的 sandbox 环境，这在 Exo harness 架构中完全可行。

- 如果你要为 100 个用户做这个，没问题，一台机器可以运行 100 个容器。

## 成本优化与评估问题

**主持人：** 是的，RSI 是一个非常热的大话题。**你有没有试过告诉 Exo 只改进自己，没有目标，还是给它一个目标？** 你做什么？

**Alex：** 这是个极好的问题。让我说几句。这也来自我和 Yan 在 Berkeley 做的一些研究。我们即将发表一篇论文，正是关于这个的：**在所有优化问题中，最终的困难是你总是必须提供某种评估器**，这个评估器必须反映你的目标，否则就没有信号让事物爬山或优化。它可能会为自己找到一个信号，但它可能与你实际想要的不一致，而且这是一个危险的、有害的失败模式。

所以我们做了几件很酷的事：

1. 你可能希望你的代理运行得更便宜。推理成本真的很高。一个关键问题是：甚至如何组装上下文？包含多少历史？我可以告诉你，用 OpenClaw，我的账单因为运行 OpenClaw 而大幅上涨，因为它组装上下文的方式放入了太多东西。
2. 我们在 Exo 中做的一件事很酷：Exo harness 的对话日志不仅存储你们讨论的内容，还**标注了每条消息的成本**。因此，当 executor 可以访问上下文构造，并推理过去的对话和不同部分的成本时……

所以很早，最让我兴奋的事情之一，就是我们构建了自我改进的 Exo 后，问它：“嘿，我注意到——Discord 适配器中上一条消息花了多少钱？”它说：“16 美分。”我说：“16 美分？真离谱。去想办法降低它。”于是它在运行时重新架构了自己的 Discord 适配器。做了修改，观察，测试，真正缩小了每次 LLM 调用中包含的上下文范围——只限于某些对话和线程，而不是从 Discord 不同线程拉取消息——最终把成本降低了 **96%**。顺便说，我们之后把更改提交回去了。所以它做的修改改进了自己，降低了成本，然后我们最终把它提交到现在的实际代码中。

**主持人：** 你是否在确保没有评估回归的情况下做这个？你的框图里没有“evals”这个框。但一个 Exo harness 应该自带自己的 evals 吗？

**Alex：** 对，在 Discord 这个案例中更容易，因为它可以去测试并尝试从不同地方读取消息。当使用它时，我可以说“这里有问题”。这是一个更简单的情况。如果你去做其他任务并想改进成本，一个非常有趣的失败模式是：它可能完全说“好吧，我就是不去做，因为这是为我省钱的最便宜方式”，我们会在 AI 驱动发现中看到。

**主持人：** 这就是奖励黑客。

**Alex：** 奖励黑客，正是。所以阻止奖励黑客，你肯定想要某种 eval 类的东西，让它能检查性能是否仍在理想位置。在 Discord 中性能很容易检查：你是否回应我的消息？你是否包含了正确的上下文？能让合理响应成为可能的上下文。这更像是一种二元判断，更容易检查。

如果你有一个保险代理试图做正确决策，你可能想要某种保留评估集。你可以把它提供给代理，或者与代理合作构建内部工具，在运行时随着自身演化来检查。所以我同意你：**向代理具体说明你想要什么的问题仍然是开放的**。因此我预期我们会构建更多工具，在改进自身的同时，它也应该跟踪性能，并定义某种跟踪方式。

## 为什么 RSI 现在可能：同媒介迭代

**Alex：** 我想回答一个你没有问但可能问过的问题：**为什么我现在声称，RSI 在这种架构下是可能的，而以前不是？区别是什么？**

我想指出过去 6 个月发生的事：我们已从迭代模型权重、训练模型权重，转向迭代这个 harness 和代理层。关键区别在于：**这个媒介——这些代理/harness 层的媒介——与实际的构建材料是同一个**。

我意思是，代理 harness 只有几千行代码。而我们的 LLM 正在输出恰好在那同一空间中的 token。它们写代码，而且越来越擅长写代码。所以这是关键区别。你有 LLM，但改进实际 LLM 的过程是改变权重，是 delta。你做反向传播、梯度下降、改变权重。但你有万亿参数模型，你不能把模型的权重喂回自身，问它如何调整自己。这不扩展，不在上下文中。你可以问 LLM“嘿，给我一些训练的想法”，然后去尝试并运行。但这是不同媒介。

而现在，harness 运行时，代理正在产生和编写代码，可以在运行时改变自己的代码。这就是为什么我相信我们正在进入一个**完全自递归**的阶段。这不仅仅是自催化——即你用计算机帮助设计下一代计算机，但计算机本身是用物理芯片制成的，有层间距离，当循环回到这里时——这是完全相同的：**代码是被生产的东西，也是在运行的东西**。这就是为什么我认为这是思考 RSI 的正确层面。

**Alex：** 同意，但我指出，在那里你得到的是**自催化改进**。你使用系统帮助改进自己，但它不在同一媒介中。所以这就是我想指出的。
