## 开篇引入

如果你曾经好奇过——当你把一段 20 万 token 的超长查询发送给一个推理 API 时，背后到底发生了什么？为什么两个厂商服务同一个开源模型，速度可以相差 4 到 10 倍？为什么一个模型提供商能做到"今天 90 token/秒、明天 150 token/秒"？为什么说 AI 模型已经开始自己编写 GPU 内核来优化自己的推理？

这期 Latent Space 播客请来了 Baseten 的两位核心工程师，进行了一场长达两个小时的推理工程前沿对话。Philip Kiely 是《Inference Engineering》一书的作者，Ali Taha 是来自滑铁卢大学的实习生（虽然他的能力早已超出"实习生"的范畴）。这场对话几乎覆盖了推理工程的每一个角落：从 KV 缓存的路由决策，到投机解码的递归版本；从量化误差的数学抵消，到 GPU 正在变成为特定工作负载定制的 ASIC；从视频扩散模型面临的 token 爆炸困境，到 AI 模型写 GPU 内核来优化自己的推理这一自我进化的闭环。

以下是对这场对话的深度重构，让每一个细节都被充分展开。

## 第一章：发一条 20 万 token 的查询，背后发生了什么？

### 缓存感知路由：先问"你来过吗"

对话一开场，swyx 就抛出了一个非常实际的问题："我是一个普通用户，向 Baseten 的推理服务发送一条 20 万 token 的长查询。从请求进入系统到 token 流回我的屏幕，这中间到底发生了什么？"

Philip 的回答揭示了一个大多数人从未意识到的核心事实：**推理系统的第一个决策，不是"如何计算"，而是"是否还需要计算"。** 在理想情况下，这个问题的答案会非常省事——如果你曾经发送过这条查询（或者至少是其中的一部分），那么推理提供商可以跳过绝大部分预填充（prefill）工作，直接从缓存中读取先前计算好的 KV 缓存（Key-Value cache）。

这就是"缓存感知路由"（cache-aware routing）。Philip 强调，在 Baseten 的基础设施中，每个模型通常有多个实例、多个副本在同时服务。当你发送一条长查询时，路由层会做两件事：第一，找到当前有可用预填充 worker 的实例；第二，同时也是更巧妙的，找到已经缓存了你输入中部分内容的实例——这样就能跳过预填充阶段的很大一部分计算。

对于 20 万 token 的查询，Philip 判断说："如果你在做 20 万 token 的查询，那很可能是代码生成或多轮 agent 对话。在这种情况下，你**应该**期望有缓存命中。"

### 预填充与解码的分离：两个独立的 GPU 军团

如果没有缓存可用，请求就会被发送到预填充 worker。在现代推理架构中——尤其是 Baseten 在某些模型上部署的架构中——预填充和解码（prefill & decode）是**分离**的。这意味着：一组 GPU 只负责处理输入查询、计算 KV 缓存、生成第一个 token；之后，这个 KV 缓存被传送到另一组完全独立的 GPU 上，由后者负责逐 token 的解码过程。

这种"预填充/解码分离"（PD Disaggregation）的核心逻辑在于：预填充是计算密集型任务（大量并行矩阵乘法），而解码是访存密集型任务（逐个 token 读取权重和 KV 缓存）。让同一组 GPU 同时承担这两种负载，必然造成资源的浪费或性能的妥协。将两者分离开来，可以让每一组 GPU 都针对自己的任务做最优配置。

### 投机解码器：给大模型配一个"预判小助手"

在解码阶段，Philip 说："我们可能会在模型前面加一个投机模型（speculative model）。"这个推断基于一个统计直觉：如果查询是编码任务，那么投机模型（draft model）的接受率会很高，因为它预判的 token 模式与真实分布高度吻合。

但 Philip 幽默地补充道："如果我猜错了——你其实是在让我总结每一本《哈利·波特》——那速度就会慢下来。" 因为投机模型需要与目标模型有相似的分布才能高效工作；如果用户的任务分布与投机模型的训练分布不匹配，预判的 token 就会频繁被拒绝，反而浪费了算力。

最后，系统流式地把输出返回给你，计算费用，然后问你："嘿，还想再来一条吗？"

**核心观点**：一次看似简单的推理 API 调用，背后是一整套包含路由决策、缓存管理和多组件 GPU 协作的复杂系统。优化的核心不是让单个 GPU 跑得更快，而是让整个系统的每个环节都不浪费。

## 第二章：按 token 付费还是按小时付费？

### 从"便士级"API 到"按箱"租赁

在讨论完整个推理流程之后，swyx 提到了一个他早期与 Baseten 交流时注意到的关键差异："有些需要极高吞吐量的用户，直接按整台机器（by the box）租赁 GPU。因为你服务数千万 token 每小时时，按小时付费比按 token 付费便宜得多。"

Philip 承认这是 Baseten 的常见客户轨迹之一："我们越来越多的看到，用户先使用按 token 计费的公开 API 来尝试开放模型，一旦找到了真正适合自己业务场景的用途，就会转向专用部署。"

那么，什么情况下应该从公共 API 切换到专用部署？Philip 给出了几个明确的理由。

### 可靠性：你的生意不能押在别人的流量洪峰上

"可靠性是最大的考量。" Philip 直言。你不想在给用户提供服务的关键时刻，因为其他某个用户正在跑 1 亿 token 的基准测试流量而影响你的延迟。

Ali 补充了另一个关键场景：**定制化的投机解码器**。投机解码器的核心思想是：为大模型配备一个小型"草稿模型"（draft model），草稿模型快速预测未来几个 token，然后大模型一次性验证这些 token。如果预测正确，就能一次前向传播生成多个 token，从而大幅加速。

Ali 用一个生动比喻解释了它："这个大模型一次只能生成一个 token，每次都要做一次完整的前向传播。我们就在模型上方附着一个小型的'寄生层'，它快速做三次自回归预测，然后你只用一次前向传播去验证这些预测是否正确，接受或者拒绝它们。"

关键是：**草稿模型是"分布定制"的**。Ali 说："如果我专门用《哈利·波特》的数据训练这个草稿模型，那我保证你每次三个 token 都能被接受。" 但如果用户请求的是混合流量——有的人在问《哈利·波特》，有的人在写代码——你就不可能提供一个通用的、高效定制的草稿模型。这就是共享端点无法做到、而专用部署可以做到的事情。

Philip 还提到了其他定制选项："你可以设定特定的 batch 大小、特定的并行策略；如果你想优化吞吐而非延迟，或者你认为 NVFP4 量化无法通过你的基准测试，想以更高精度运行模型——这些都是选择专用端点而非共享 API 的理由。"

**核心观点**：从按 token 付费的公共 API 转向按小时计费的专用部署，不是简单的成本问题，而是可靠性、定制化和控制权的综合考量。这是一条经典的客户旅程：先用门槛最低的方式试水，找到契合场景后立即升级到专用部署。

## 第三章：工具调用的隐藏复杂性

### 工具调用不只是"生成 JSON"

当对话进入工具调用（tool calling）时，Ali 揭示了一个很多人忽略的层次："某些客户拥有自己的后训练模型，他们需要的工具调用不是'解析文件'或'查天气'这种通用能力，而是非常定制化的东西。你必须做后训练，而且如果后训练不好，或者后训练之后的量化不好，模型在读取 JSON 文件时就会很挣扎。"

工具调用的最大挑战并不在于沙箱安全性（模型不太可能利用工具调用来逃逸沙箱），而在于训练本身："工具调用是一个训练起来非常敏感的东西。因为你在处理一串 JSON 输出，如果模型在请求结束时没有按照某种特定的方式闭合括号或结构，那么进行工具调用的模型在'思考'时就出现了问题——它没有看到工具调用的结果，于是在解码过程中幻觉了一个结果。"

用更直白的语言说：**模型的思考（reasoning）和行动（tool call）之间存在一个信息断链**。如果模型没有正确处理工具调用的输出格式，它就会在幻觉中继续。

### 结构化输出：用状态机锁住格式

在推理端，Baseten 早就发布了解决方案。Philip 回忆道："我们差不多两年前发表了这个问题的解决方案：你基本上构建一个状态机，用它来约束输出到特定格式。这就是'结构化输出'问题。"

swyx 立即联想起 2020 年代早期的经典问题："这就像古老的'确保输出只有 JSON，否则我的解析器就会死'的老问题。" 当时的做法是用 BNF 文法（Backus-Naur Form）来约束输出——OpenAI 曾经发过一个建议："如果你想约束输出，就写 BNF 文法。"

Philip 说："在我们的推理系统中，就是指定输出格式，然后你就能获得输出结构符合该格式的保证。" 这一技术应用到工具调用上，能显著减少格式错误。但他诚实地说："你仍然可能调用错误的工具，或者根本不调用工具。它解决的是输出结构化问题，而不是'正确性'问题。"

### MCP 没什么特殊：LLM 只能做"建议"

swyx 问到 MCP（Model Context Protocol），Ali 的回答非常干净利落："MCP 只是工具的另一种形式，没有什么特别之处。"

这段话触及了一个深刻的基本原理。Ali 阐述道："我一直在向人们解释的一件事情是：LLM 实际上并不能做任何事。它只能提出'做什么'的建议。只有当这些建议以某种格式被格式化，并且被一个知道如何处理它们的系统所应用时，动作才会发生。模型本身只是建议者，动作的执行者是外面的系统。"

Philip 补充说："在 agent 循环中，如果输出不正确，模型可能会说'哦我不知道该怎么办，让我再试一次'，几次之后可能就成功了。但在小模型上，这种鲁棒性就不存在——当你从大模型切换到小模型时，输出质量并不保持一致。"

**核心观点**：工具调用的难点不在推理框架，而在训练质量与输出结构化的结合。LLM 永远只是"建议者"，系统才是"执行者"。理解这一基本分工，是设计稳定 agent 系统的前提。

## 第四章：新模型适配：从"能出 token"到"生产就绪"

### 一场推理性能的"战争"

对话的另一个重要主题是：当一个新模型发布时，推理提供商到底要做什么？swyx 坦承："我以前以为，如果一个模型是 GLM 5.1 到 5.2 的升级，你们之前支持过 5.1，那 5.2 应该不费什么功夫。但你说，'这工作量很大'。"

"我认为这比'支持'更深一步，" Philip 接过话题，"它对消费者的好处很大。我记得 Kimi K2.5 或 GLM 5.2 发布时，出现了一场'推理战争'：某家提供商 90 token/秒，第二天另一家 150 token/秒。"

swyx 得意地承认他在这件事中的角色："GLM 5.2 那场就是我挑起来的。我写了一篇 Twitter/X 文章，大概有 50 万次浏览。" 这篇文章让整个行业兴奋起来：原来推理性能可以被推到这么远。

### 从"能出 token"到"生产就绪"之间的巨大鸿沟

"把模型跑到'能出 token'和把它变成'生产就绪的 API'是两码事。" Philip 直言。

前者不难：开源推理引擎（vLLM、SGLang 等）的维护者通常会提前收到权重，甚至模型团队自己会提交 PR 来确保支持。所以在一两天内让模型跑起来开源栈，通常不会有太大痛苦。

真正的挑战在于：**每个推理公司都有自己的专有堆栈**。对于任意一个包含"新东西"的模型，都需要专门适配。Philip 列举了几个关键步骤：

第一，**量化工作**。大多数新模型在发布时并不提供 NVFP4 格式的权重。而对于 Blackwell 硬件，NVFP4 几乎是必备的。Baseten 需要自己执行量化，并且要做校准，确保量化没有损伤模型的智能。

第二，**训练投机解码器**。这个环节非常有意思。Baseten 的公共模型 API 采取零数据保留政策，所以他们并不知道用户发送的具体流量。但他们知道什么样的流量是主流的——编码、agent 型任务。于是他们会采集代表性公开数据集，训练通用的投机解码器。今天的投机解码器需要用基础模型本身来训练，因为要从模型在这些提示词上的推理输出中获取隐藏状态，这些隐藏状态才是训练投机解码器的基础数据。

第三，**架构变更适配**。有些模型有全新的架构组件，比如 GLM 5.2 的 DSA（DeepSeek 的稀疏注意力架构），DeepSeek 系列的模型因为创新的架构设计而最难适配。每发布一个新模型，推理运行时就要为这些新结构构建支持。

### 嫁接实验：给 GLM 5.2 装上 Kimi 的眼睛

最精彩的例子，是 Baseten 团队内部做的一个"缝合怪"实验。Philip 讲述道："GLM 5.2 没有视觉能力。所以我们团队的一个家伙 Haley，把 Kimi 的视觉编码器嫁接（graft）到了 GLM 5.2 上。"

具体的做法是分步的：

- **编码器**（encoder）：负责处理图像，把它转化为潜在信息——这是来自 Kimi 的部分，完全冻结。
- **投影器**（projector）：负责把编码器的输出映射到模型本身的嵌入空间——这是唯一需要训练的部分，只有区区几百万参数。
- **模型权重**：完全冻结不动，以免赋予模型视觉能力的同时破坏了其他能力。

Ali 对这个训练过程的细节投入了格外的热情。他描述了这个嫁接过程如何经历了一个"grokking"（顿悟）式的学习阶段："一开始，他只是用'这里有一张山，请描述一下这座山里有什么'来训练投影器，但它只能学会非常表面的描述。"

"然后他改变了训练方式：每张图像都关联了一整套问答数据集——这张图片里有没有一个白人男性？右上角有没有鸟？里面有没有一个科学家？——模型必须逐一正确回答。当训练数据从'描述图像'变成'回答问题'时，你就能看到那种真正的 grokking 现象发生。"

"这真的很疯狂，" Ali 的声音里带着敬意，"把一个视觉编码器后装（retrofit）进一个大 LLM 里，它竟然能在这种程度上学会理解图像。即使是对它表现不好的图片——比如你给它看一张斯蒂芬·霍金的照片，它答不上来，但它会说'这是阿尔伯特·爱因斯坦'。它仍然理解：这是一个科学家，一个男性，有重要成就。"

这个实验的最终效果是什么？Philip 总结道："你突然就得到了一个同时拥有 Kimi 视觉、GLM 权重和 DeepSeek 稀疏注意力的模型。这是开源生态系统的伟大之处——你可以把所有不同组件组合成一个比任何个体都更好的系统。"

当然，这只是一个研究项目——它在 MMLU 上得到了 56% 的分数，"不算高，但也不算糟"。但一个关键优势是：**如果你不给这个模型传图片，它的行为和你原来的 GLM 5.2 完全一样**。推理时如果没有图像输入，视觉编码器部分甚至可以被直接跳过，不增加任何开销。

swyx 问到是否还有人做"Frankenmerge"（Frankenstein 式合并，从不同模型取层拼接）。Ali 的回答是肯定的，而且给出一个非常实用的理由："像 MiniMax M3 这样的模型使用的是全注意力机制。全注意力的问题是 KV 缓存巨大，自回归生成时计算量是序列长度的平方——既耗时又耗显存。所以我们会用一个来自其他模型的 GQA（分组查询注意力）层替换掉这个低效的注意力层。只需要正确的训练，就能让它达到同样的接受率。"

这种"层级移植"又一次说明了一个核心观点：**好的训练是高效推理的前提，二者之间的边界正在模糊**。

**核心观点**：新模型的适配远不止"能跑起来"。量化、投机解码器训练、架构适配、生产级测试——这是一套完整且高强度的工程流水线。开源生态的"拼接"文化让推理提供商能够组合出甚至超越原版模型能力的混合系统。

## 第五章：如何保证推理质量 —— 从保真度到量化误差抵消

### 质量的定义：对"黄金实现"的保真

swyx 提出了一个关键问题："当你们做了这么多优化——量化、训练投机解码器、在多款硬件上运行——怎么保证模型质量不下降？你们有基准测试，但这些优化之间如何权衡？"

Philip 的处理方式体现了他对推理工程本质的思考。他先把优化分为两大类：

"绝大多数推理优化是无损的。KV 缓存，你只是防止重复计算或重新计算相同的值。投机解码，错误的草稿 token 会被拒绝。真正有损的优化主要是量化。"

然后他给出了一个精炼的质量定义："我理解的质量，是我们忠实服务于原始模型的程度。如果你有一个模型的'黄金实现'——完全按照设计意图运行的模型——质量就是我们在多大程度上接近这个 100% 的保真度。"

他补充道："我们内部的标准是：你应该分辨不出我们 API 和模型官方 API 之间的区别。"

### Kimi 厂商验证器：行业开始保护自己的品牌

Kimi（月之暗面）在维护模型质量声誉方面做了一个很受关注的举措——发布了"厂商验证器"（vendor verifier）。

Philip 回忆道："Kimi 在厂商基准测试上做得很好。他们发布了一个真正的验证工具，因为他们指控某些云厂商在服务他们模型时质量不达标。"

这段信息的背景是：大约三四个月前，有主要云提供商在服务 Kimi 模型时进行了过度或不严谨的量化，导致模型输出质量明显下降。Kimi 发布验证器来标准化比较各家推理提供商的输出质量与官方参考实现之间的差异。

swyx 敏锐地指出了这件事的商业逻辑："如果我是消费者，我用了亚马逊的端点，发现 Kimi 的模型表现糟糕，我不会说'亚马逊量化得不好'——我会说'Kimi 很烂'。模型厂商承担了品牌损失，所以它们当然会关心。"

### 量化的反直觉发现：误差可以互相抵消

对话中一个最引人注目的技术话题，是 Baseten 研究实习生 Joshua 的一个发现——这个发现足以挑战业界关于量化的传统观念。

"量化是有损的。你将数据从 16 位压缩到 4 位，丢失信息，这是不可避免的。但有趣的是，选择量化哪些层并不是一个'量化越多越差'的简单关系。"

Ali 解释了这个反直觉的发现："如果我们有一个模型，量化了 1、5、10 层，另一个模型只量化了 1、2 层——前者（量化更多层的模型）有可能在基准测试中表现更好，因为量化误差相互抵消了。"

Joshua 的数学证明展示了如何**预测**哪些层会产生相互抵消的量化误差："一个层向一个方向偏移，另一个层向另一个方向偏移，最终输出的 logit 分布反而更接近原始模型。这比你量化更少的层效果更好。"

验证方式不是简单的基准测试分数，而是 KL 散度（KL divergence）——测量量化模型与原始全精度模型在 logit 概率分布上的差异。结果让团队惊喜："我们发布了一个结论：我们量化的 GLM 5.2 比 Nvidia 的好 20%。不是基准分数高 20%，而是在相同甚至更低精度下，我们的输出分布更接近原始模型，而且因为量化层更多，推理吞吐量额外增加了 20%。"

关于这篇论文，Ali 透露了一个有趣的花絮："这篇论文最开始有 72 页，我们无法删减，最终发布了 42 页。但它非常扎实。"

swyx 听完后说："这让我想起剪枝（pruning）——你可以剪掉某些层反而让模型更好。系统性分析误差抵消，这个领域大有可为。"

### 量化是否可能带来提升？

swyx 追问了一个有点"愚蠢但值得确认"的问题："量化会给结果带来任何好处吗？有没有可能量化后的输出比全精度更好？"

Philip 的回答很坦诚："当量化后的模型在某个基准上的分数高两个基点（basis points）时，那只是噪声。我确实见过这种'提高'，但我把它归因于模型的不确定性。我甚至已经不再说'在误差范围内'了——因为每个人听到这句话都以为意味着我们勉强在误差带的最坏一侧。实际上，量化不会让模型变聪明，你只是在努力保持 100% 的原始保真度。"

Ali 的补充一语中的："我们说过，如果模型的输出分布与原始模型一致，那不叫'更聪明'，只能叫'更忠实'。"

**核心观点**：推理质量的核心指标是对原始模型的保真度，而不是基准分数的高低。量化的艺术在于选择性地分配精度——某些层的误差会互相抵消，这甚至意味着更多的量化可以带来更高的保真度。KL 散度比基准分数更适合校验推理质量。

## 第六章：10 倍速推理：从 70 到 90，还是从 30 到 300？

### 推理工程还有巨大的未开发空间

swyx 提到了 Philip 之前的一篇文章，其中讲述了将某个模型从官方 API 的 70 token/秒提速到 90 token/秒。他问："这是正常的吗？"

Philip 用了一个来自金融领域的类比来回答："金融领域已经高度优化——如果你在量化金融中获得了五个基点的提升，那是大新闻，因为一切都已接近极限。但当我们发布推理优化时，是 20%、100%、200% 的提升。"

"推理工程远未被解决。你知道这个领域什么时候会接近饱和吗？当 Meta 开始发布'我们某个推理流程快了 1%'的论文时。"

swyx 从自己的量化金融背景补充了历史视角："在 70 年代，量化金融研究中的 margin 就是 20%-10% 的水平。如果你想看这个趋势如何收敛，可以看 Andrew Lowe 论文里对统计套利收益分布的描述——从 70 年代的巨大差异缩小到今天几乎为零。推理工程正处在那条曲线的最初阶段。"

### 从 30 到 300：堆叠 4 个"倍增器"

那推理速度的天花板在哪里？Philip 给了一个清晰的数字框架：

"一个标准的、未加优化的 API，服务 1 万亿参数模型，在合理的流量分布下通常运行在 30-50 token/秒。我们的目标通常是把这推到 10 倍——不是从 70 到 90，而是从 30 到 300。"

"你把 3 个各自能带来 2 倍性能提升的优化堆叠起来，就是 8 倍提升。这是我们这个领域的工作尺度。"

swyx 问道："你们真的做到过 10 倍？" Philip 冷静地回答："像 GLM 5.2 这样的模型，在未量化的 BF16、H100、标准的开源推理引擎、无投机解码器、无 KV 路由、无分离部署的条件下，基础速度大约是 30-40 token/秒。把它推到 300-400 token/秒需要做出一系列权衡：最佳硬件、优化的投机解码器、完整的量化工作、高缓存命中率、较小的批处理规模、针对延迟而非吞吐优化的并行配置。这是可能的。你如果去 Artificial Analysis 或 OpenRouter 上看最差和最好提供商的差距，往往能落到这个量级。"

他补充了一个现实的修正："10 倍当然是非常激进的，更常见的是 4-6 倍的提升。但那种以'跃迁'为单位的进步才是让我们兴奋的东西。"

Ali 强调了一个关键的控制变量：**硬件归一化**。"如果你把模型从一台 H100 节点换到四台 B200 节点，当然能快 3 倍——那是钱的问题。但在相同硬件、相同 GPU 数量的前提下，只有推理优化能带来 2-4 倍的改进。"

### 堆叠的每一层：量化、投机、分离、运行时

Philip 拆解了这些"2 倍"的来源：

- **量化（BF16 → NVFP4）**：BF16 到 8 位约提升 30-40%，8 位到 4 位再乘 30-40%。这加起来不到 2 倍，但非常接近。
- **投机解码器**：大概带来 2 倍。
- **PD 分离**：在你有足够的硬件和流量时，又能带来约 2 倍。
- **更好的运行时**：通过最新的内核和调度，再加上两位数的百分比提升。

关于实施成本："量化权重——对于真正懂行的人来说，是几小时到几天的工作；训练一个投机解码器——也是几小时到几天；PD 分离的首次搭建非常困难，但一旦做好，边际实施就很快。"

Ali 给普通用户提供了非常务实的建议："如果你只是一个有 B200 节点使用权的人，想自己托管模型——你不需要自己量化模型，也不需要训练投机解码器。开源社区几乎总会发布量化权重，视频（NVIDIA）会发布参考量化。模型提供商通常会发布他们训练好的投机解码器。你的工作只是把它们拼起来。"

**核心观点**：推理优化的目标不是在 70 到 90 之间挤出百分之几十，而是通过堆叠多个约 2 倍的"倍增器"实现 10 倍的整体飞跃。量化、投机解码、PD 分离、定制运行时——每一层独立增效，叠加才产生质变。

## 第七章：投机解码的演化与"投机之上再投机"

### 从 Medusa 到 EAGLE 到 Sparkspecter

关于投机解码这个令人着迷的技术族，Philip 在书中专门覆盖了多种变体。swyx 翻着书指出："第 5.2.2 节是 Medusa，5.2.3 是 EAGLE，5.2.4 是……"

Philip 解释了他为什么把 Medusa 也写进书里："我写这本书有两个目标：给读者提供这个领域的工作词汇，以及让读者理解每种技术的工作原理。投机解码的演化速度比其他所有领域都快。即使在我写书的时候，Medusa 也已经被包括进来，更多是为了让读者理解这个领域是如何演化的，而非它是最现代的技术。"

现在，投机解码的新秀包括：EAGLE（仍然被广泛使用）、Deflash、Despoke，以及一个令人震惊的新变体——**Sparkspecter**。

"Sparkspecter，或者说投机式投机解码（speculative speculative decoding），" Ali 说到这里不自觉地笑了，"是由一位名叫 Trudau 的研究者提出的。本质上就是：对投机解码器再做投机解码。"

这个想法在逻辑上似乎很自然："投机解码的整体思路是为大模型配一个小模型。小模型需要做三次自回归。那为什么不配一个更小的模型来预测这个投机解码器的输出？" Ali 承认："这就像 iPhone 的自动补全套上了另一层自动补全。"

但 Ali 对这个方向的实用价值表示非常谨慎："在我们的经验里，训练这种递归投机系统的复杂度高得惊人——几乎和训练 GAN 一样困难。它就像训练过程中的一个脆弱的平衡舞，经常因为太脆弱而得不偿失。"

swyx 的直觉思考非常尖锐："如果我能训练一个小的投机解码器，它能准确预测中间投机解码器（后者预测目标模型）——那我为什么不直接用那个最小的模型来做推理？"

Philip 的回答出人意料地触及了一个更深层的问题："这是一个路由问题。如果你能直接使用小模型，那说明你根本不需要大模型。投机解码的实用价值在于，当小模型不足以完成任务，但足以预测大模型对特定 token 的选择时，它能帮大模型节省解码时间。"

他还指出了投机解码在工程层的几个现实约束："运行投机解码器需要与目标模型共享同一块 GPU 上的资源。草稿 token 的创建需要资源，管理它们需要软件复杂度。如果你搞递归投机解码，这个复杂度的增长是指在推理引擎实现层面，而不仅仅在训练层面。"

### 投机解码器有多大？

谈到投机解码器的实际规模，Ali 给出了一个直观的数字："GLM 的投机解码器大约 10 亿参数；MiniMax 的投机解码器甚至只有 1/60 的模型大小——可能就一层。"

这个规模意味着什么？它解释了为什么投机解码在实用层面如此高效：一个 10 亿参数的模型在一个数千亿参数的模型旁边运行，其推理成本可以忽略不计，而这个"小助手"却能为大模型预判几乎所有常见的 token 序列。

**核心观点**：投机解码领域的发展速度远超其他推理优化方向，但它的持续演化也带来了复杂度问题。递归投机（对投机解码器再做投机解码）在理论上诱人、在实践中却因为训练脆弱和工程复杂度过高而很难落地。理解这一领域的最佳方式不是追逐最新论文，而是理解其演化逻辑。

## 第八章：并行化：TP、EP 和 PP 的取舍

### 张量并行 vs 专家并行

在对话进行到硬件和系统层级时，swyx 提议："既然你书里有非常漂亮的两张图，那我们来聊聊张量并行（TP）和专家并行（EP）吧。"

Philip 首先强调了一个前提变化："所有大到值得跨多 GPU 并行化的模型现在几乎都是 MoE（混合专家）模型。所以'专家并行只适用于 MoE'这个限制已经没那么重要了。"

**专家并行（Expert Parallelism, EP）** 的核心是：把完整的专家（expert）放在一个 GPU 上——通常专家数多于 GPU 数，所以每个 GPU 上放若干专家。路由器（router）非常小，被复制到每个 GPU 上。由于专家间的切换是 GPU 内部完成的，GPU 之间没有太多通信需求，所以这种并行方式对互联带宽要求不高，吞吐量可以轻松扩展。

**张量并行（Tensor Parallelism, TP）** 则是把整个模型切分到多个 GPU 上，每一步计算都需要跨 GPU 做 all-gather 和 all-reduce 来合并部分结果。这也是为什么互联带宽（如 NVLink）对 TP 至关重要。

Philip 用一个例子解释了 TP 的通信成本无法避免的原因："如果你在算 attention，你需要做 softmax——这个非线性操作需要整行数据。即使你把矩阵乘法融合进一个'超级内核'，GPU 1 和 GPU 2 各持有矩阵的一部分，为了做 softmax，它们依然必须交换部分结果。**融合内核救不了你**——因为非线性的存在，TP 的通信开销是无法绕过的。"

### 从理论上理解，到实践中自动调优

Ali 则坦率地揭示了推理工程中的一个"丑陋真相"："我挺不喜欢的一个事实是：你无法从理论上推理哪种并行配置是最好的。实践中，你只能做自动调优（auto-tuning）——定义一个配置空间（TP1/TP2/EP1/EP2），然后在真实流量上做影子测试，选出 TPS 最高的那个。GPU 内核开发也是一样：设计好内核后，你要扫一遍参数空间——多少个线程、多少共享内存——然后选经验最优值。"

这个评论隐含着一个判断：推理工程仍未成熟到可以让纯理论推断指导实践，靠的依然是经验性的测试和枚举。

**核心观点**：张量并行和专家并行解决的是不同的资源瓶颈——前者需要极高的芯片间带宽、适合减少延迟；后者减少通信、适合提高吞吐。实际部署中两者往往结合使用，配置选择常常靠自动调优而非理论推导。流水线并行只有在模型跨节点时才不得不用，因为跨节点互联太慢。

## 第九章：本地 AI vs 数据中心——两个不同的推理宇宙

### "装进笔记本"和"塞进数据中心"是两套工程

swyx 问了一个非常实际的问题："这些优化都是为大规模服务器负载设计的。那我在 MacBook 上本地跑 Gemma，这些经验适用吗？"

Philip 的回答区分了两种推理工程的使命差异："Amusi 之前和他的播客聊过这个话题。本地 AI 和推理数据中心推理的根本区别在于：本地 AI 的出发点是'如何把模型塞进我的硬件，然后让它不那么笨'；而数据中心推理则是'如何加载这个模型，然后让它不那么慢'。"

"我们关心'不笨'，他们关心'不快'。不过我觉得本地 AI 领域有很多值得数据中心的我们学习的地方——他们精通各种形式的量化（包括我们基本不碰的动态量化）、剪枝、蒸馏、甚至层移除。"

swyx 对齐道："他们确实做过层移除。"

### TurboQuant 的启示：同一个优化在不同硬件上有完全相反的结论

Ali 举了一个非常具体的例子来说明两个世界之间的巨大差异——TurboQuant：

"TurboQuant 在 MacBook 上引起巨大轰动。我们在 Twitter 上也做过深度分析。它之所以对本地设备至关重要，是因为本地设备的内存带宽太慢——比如 MacBook——所以一切围绕减少数据移动来优化。但你把同样的优化放到 NVIDIA B100 上试试？TurboQuant 根本不会被使用。"

原因很直白："B100 的 HBM 带宽有 3.5 TB/s。TurboQuant 内核中做反量化/量化的计算开销，远远大于省下的带宽时间。有的优化只在带宽极度稀缺的场景中才有价值。"

Ali 还给了一个判断优化价值的通用视角："NVIDIA 自己已经明确表示这不是一个好的优化——因为它'看不懂'。" 这句话背后是 NVIDIA 对其硬件体系深入的量化分析：在 B100 上，减少存储而非减少计算，不是正确的方向。

### 硬件互联的挑战

Philip 补充了另一个共同挑战——机器互联。数据中心大量使用张量并行（TP），它依赖 NVLink 这样的超高带宽互联；而本地 AI 玩家（如 Axle Labs 的 Mac mini 集群）更可能被迫使用流水线并行，因为他们使用的是以太网这样的普通互联。

"你不可能在 Mac mini 集群上用 TP——互联带宽太低了。这迫使他们走流水线并行，而这在数据中心除非跨节点推理否则几乎不会用。"

**核心观点**：本地推理和数据中心推理面对的是不同的约束条件——前者的瓶颈是内存带宽和容量，后者的瓶颈是计算效率和跨设备通信。在这种差异下，同一项技术（如 TurboQuant）在两个世界的价值可以完全相反。

## 第十章：硬件未来——Rubin、ASIC 化和"GPU 正在杀死内核编程"

### Rubin 到来前：三波硬件代际的教训

当话题转到未来硬件时，Philip 首先回顾了自己经历的三个硬件周期："Ampere、Hopper、Blackwell。" 他特别强调了"硬件开始装机"与"硬件在推理上变得可行"之间的漫长时差："最初的 vLLM 和 SGLang 是面向 Ampere 写的，然后要更新到 Hopper、更新到 Blackwell。每一个周期都更紧迫、也明显更复杂。"

他对 Rubin 的判断是："Dynamo（NVIDIA 的开源 KV 路由库）给了我很多技术线索。Rubin 延续了 Blackwell 的趋势——NVFP4 是大头，张量核心背后支持 NVFP4 的计算量非常巨大；内存带宽也会有大幅提升。但更重要的是系统层面的思考：更多的 CPU 到 GPU 互联、GPU 之间的高速互联。Dynamo 这个系统的设计目标就是：如何把 KV 缓存移动到它该在的地方、在它该到的时间。"

他的结论是：**推理工程将不再只是一个 CUDA 内核问题，而是一个传统硬件基础设施问题。** "你需要在内核层面和硬件层面之间来回推理，这种跨域能力将变得极其有价值。"

### GPU 正在进化为"几乎 ASIC"？

Ali 提出一个更激进的观察："我认为推理工程正在变成一个纯粹的'编排'问题。写内核将不再是问题——GPU 正越来越像一个 ASIC。你是在编排 GPU 上发生什么，而不是在线程级控制它。看看最近的 CUDA 编程趋势——你在处理数据块（tiles），而不是控制每个线程做什么。GPU 正在把你从线程级编程中解放出来。"

他进一步追问："NVIDIA 每一代都在增加更多专用指令、专用张量核心、专用 MMA 指令。Rubin 相比之下简直是 'ASIC'——它有一堆几乎专门用于加载模型权重的特制核心和指令。那么你怎么还能看好那些为 AI 做专门 ASIC 的公司？NVIDIA 自己不正在朝那个方向进化吗？"

Philip 在这个问题上有不同视角。他先指出了 ASIC 的一个致命缺陷："把权重烧录到芯片上是不可行的。你想做微调、想量化、想发布新 checkpoint。如果权重烧死在芯片里，芯片两三个月就没用了。"

他引用了与 Martin Casado 的对话："如果你有一个 5000 亿美元的训练计划，拿 50 亿做一块专用 ASIC 完全合理。模型专用芯片这条路是可行的。但通用 ASIC 公司面对的是另一个问题——他们做大量表面工程（surface area engineering）、内存分配、芯片间通信的优化——这些是 Rubin 不见得能覆盖的地方，因为这些效果往往比 Rubin 上任何可编程的东西提升一两个数量级。"

他还调侃了那些"超级 ASIC"公司的目标："他们瞄准的是 300,000 token/秒。他们不是来玩的。"

关于模型代际长度，Philip 也给出一个现实视角："很多人还在用 Llama 3 甚至 Llama 4。模型的使用寿命其实比我们想的长得多——如果你的业务跑得好就不用换。这给了 ASIC 更多成长空间。"

Ali 反唇相讥："如果 GPT 系列每年换一代架构，你每年都要扔掉上一年的 ASIC？" Philip 淡定回应："会有企业继续依赖旧模型。企业和用户对'消化了信任'的模型有着巨大的惯性。"

### 显存数学：为什么有些模型"装不进"单节点

关于新一代模型的适配，Ali 解释了一个很实际的约束："最新的 Kimi 模型非常大——2.8 万亿参数。你需要 GB300 才能运行它。简单数学：NVFP4 下，2.8 万亿参数约等于 1.4 TB。GB300 每个 GPU 有 288 GB 内存，8 块 GPU 正好能装下模型。但然后你还需要给 KV 缓存留空间。当模型参数多、上下文又很长时，你就是在和显存空间打仗。"

这也解释了 KV 缓存卸载（KV cache offloading）为什么随着模型巨大化而成为一个越来越关键的话题。

关于 Rubin 发布后的模型趋势，Philip 指出了一条规律："人们会看最新推理硬件能承载多少参数，然后以此作为训练模型的'天花板'。DeepSeek 1 发布时是 6710 亿参数，这在当时非常大，也直接推动了整个行业快速采用 Blackwell 并优化其推理性能。"

**核心观点**：GPU 正在沿频谱从"通用可编程处理器"滑向"为 AI 推理高度特化的芯片"，但这不意味着通用 ASIC 公司就赢了——模型迭代的快速周期和软件生态的灵活性，仍然是通用 GPU 最深的护城河。未来最值钱的推理工程能力，是在内核级和系统级（KV 缓存路由、卸载、跨节点通信）之间游刃有余的横向整合能力。

## 第十一章：视频扩散模型——与 LLM 完全不同的推理世界

### 视频扩散：没有投机解码、不共享、无流式

swyx 转向了一个对话中较少被深挖的方向——视频扩散模型的推理工程。Ali 对此充满热情，因为这是他实际在做的工作领域。

"视频扩散和 LLM 推理的形态完全不同。没有投机解码，没有批处理——每一个视频生成请求独自占有一个 GPU。模型本身也小得多：Open-Sora 1.2 大约 200 亿参数，比最好的 LLM 小一个数量级。"

但真正的核心差异在于**token 数量**。Ali 展示了一张图（那个让他很兴奋的密度展示）："哪怕只是 4 帧视频，如果做全注意力，每个 token 都要和所有其他 token 交互。一段 5 秒的视频——480p、16 FPS——压缩到潜在空间后，仍然有约 35,000 个 token 需要相互做注意力计算。"

"注意力复杂度是 O(n²)。5 秒就是 35,000 个 token 的两两交互；10 秒就是 4 倍计算量；20 秒是 16 倍。生成一分钟的高质量连续镜头，在现有架构下几乎是不可能的。"

### 两条出路：稀疏注意力（质量妥协）或自回归（工程解耦）

Ali 展示了他文章中的两幅对比图："左边是全注意力——每个 token 与其他 100% 的 token 交互；右边是稀疏注意力——每个 token 只与 top 12.5% 最重要的 token 交互，通常是空间相邻的 token（王冠注意头部、面部，以及时间上前一帧的对应区域）。"

"稀疏注意力能大幅降低计算量，但它不可避免地导致视频质量下降。这就是取舍。"

另一条路是自回归视频生成。Ali 的判断非常鲜明："我赌自回归是未来的方向——如果你想做一部 1 小时的电影，想让视频模型生成好莱坞级别的镜头，模型必须变成自回归的。目前没有任何优秀的开源自回归视频模型。要么等到计算能力出现疯狂飞跃，能对百万 token 级别的序列做全注意力；要么就走向自回归。"

### 自回归视频的权衡

swyx 请 Ali 分析自回归视频的利弊。

Ali 的剖析非常清晰：

"自回归视频模型继承了 LLM 推理的全部优化工具箱：投机解码、KV 缓存、流式输出——我可以生成第一帧然后展示给你，就像 GPT 生成文本时逐词输出一样。你可以看着视频一帧帧生成。"

"但当前所有自回归视频模型的质量都很糟糕。对比一下 Open-Sora 1.2 生成的猫狗打斗视频和任意自回归模型的输出——前者是真实的画面，后者是劣质 Tom and Jerry。"

"另一个方案是把短视频拼接起来。Grok Imagine 和 Grok Video 做的就是这件事：生成 7 秒片段，然后'扩展'，把两段视频缝合在一起。开源社区没有这些技巧。最接近的替代是取上一段视频的最后一帧，作为 image-to-video 模型的输入，生成下一段 5 秒。"

这种做法有一个致命问题——**漂移（drift）**："第二段视频比第一段略暗，第三段更暗……到最后 25 秒，你得到的是黑屏。我们试过做一个 Demo 来展示这一点，但它实在太尴尬了，最后决定不展示。"

### 为什么扩散和自回归的差异是根本性的

Philip 对扩散与自回归的差异做了更本质的总结："扩散模型的注意力是双向的——序列中任何位置的 token 都能看见任何其他位置。而自回归只能向前看。这就是为什么扩散模型能在生成后'回头'修复不一致的地方——比如保证视频中物体的一致性；而自回归一旦做错就无法修正。"

但他随即补充了文字和视频在这个维度上的根本不同："文字本质上是单向的——即使人类写作，也是顺序性的，我们虽然会修改，但比想象中少得多。而视频不是：左上角像素和右下角像素几乎同等重要，必须相互映射才能保持画面质量。这就是为什么视频需要双向注意力的内在原因。"

Ali 的总结很有价值："推理工程被我非常粗略地分成了两个宇宙：自回归模型有一套约束和技术体系，扩散模型有另一套。文本和语音在自回归宇宙，图像和视频在扩散宇宙。两者之间有重叠，但这不是完美的二分。"

**核心观点**：视频扩散模型面临的根本瓶颈是 token 数量的平方爆炸——5 秒视频已需要数万 token 的全注意力计算。稀疏注意力以质量为代价，自回归以自然度为代价。通往"长视频生成"的道路要么依赖计算力的指数级跃升，要么依赖自回归架构取代扩散范式——而这需要一次训练技术上的范式突破。

## 第十二章：推理与训练的融合——AI 开始优化自己的推理

### 训练越来越依赖推理，推理越来越依赖训练

对话接近尾声时，swyx 提出了一个非常重要的观察："推理工程曾经就是'拿一个开源模型，让 GPU 轰鸣起来'——这就是 Baseten 的工作。但现在看起来人们越来越把推理用在训练之后。"他在 AI Engineer 大会的主题演讲中说，"训练与推理正在双向渗透。"

Ali 从两个方向拆解了这个趋势。

**推理用于训练**："在强化学习训练中，你需要做 rollout（推理）。如果你的 rollout 很慢，或者模型不被 vLLM 支持、被迫在旧推理引擎上跑，你的整个训练流水线就会被瓶颈卡住。推理优化的技术直接服务于训练效率。"

**训练用于推理**："最典型的例子是量化。你把模型量化到 NVFP4，有时候 PTQ（训练后量化）就够了；有时候量化后的模型质量崩了，你就必须对模型做后训练，让它'学会'在 NVFP4 下仍然保持原来的输出分布。NVIDIA 还发布了量化感知蒸馏（quantization-aware distillation）：同时运行 NVFP4 版本和全精度版本，用后者的 logit 分布来蒸馏训练前者。"

Ali 直言："我们团队里的推理工程师越来越多地需要精通训练技术——你要会写训练管线，才能做最好的推理优化。"

### JLM52（GLM 5.2）正在写自己的 GPU 内核

这个主题的高潮出现在对话的最后。Philip 讲了一个真实发生在 Baseten 内部的故事：

"GLM 5.2 非常擅长写 GPU 内核。我们在内部搭建了一个 GLM 5.2 的端点，接入了我们的云代码工具链。团队里每个工程师都用这个 GLM 5.2。"

"它的工作流程是这样的：它在一个 GLM 5.2 节点上做一次前向传播，获得 profiling trace（性能剖析报告），然后分析，找出哪些内核是这次推理的瓶颈。然后它写新的内核，再做一次 profiling trace。完成后，把镜像上传到我们的系统，我们拉下来，重复这个循环。"

"所以有相当长一段时间，我们推理引擎里运行的一些 GPU 内核，就是 GLM 5.2 自己写的。profiling trace 和内核的修改，都是由 GLM 5.2 作为驱动。"

这个自我优化的循环已经是现实，而不仅仅是理论。Philip 意味深长地说："我认为这个循环确实已经存在。我们需要给它更多时间——还有很多事情模型做不了，即使它们非常聪明。它们仍然会试图走捷径、偷懒。但'模型优化自己的推理'这件事确实已经在发生。"

swyx 问了一个极好的问题："你觉得 GLM 5.2 是恰好擅长优化自己，还是说它只是我们当时能接触到的最好的编码模型，让它优化 DeepSeek 或 Kimi 也一样出色？"

Ali 笑着说："这可能就是'策略外'（off-policy）的问题了——让它优化另一个模型可能是低效的。但说实话我不确定。你有那么多算力，你去试试不就知道了吗？"

### 持续学习：KV 缓存压缩 vs 权重更新

最后，swyx 提出了一个面向未来的话题——推理工程在持续学习（continual learning）中的角色："如果模型应该从它处理的所有内容中学习，你会在推理时做不同的设计吗？"

Ali 引用了他和 Character.AI 的 Charlie 在 Twitter 上的一次讨论："持续学习有两条路径。第一，模型把新知识写进权重。但这有个根本问题：你只能把知识写成'死记硬背'的事实——比如'世界上最好的大学是滑铁卢'。但当用户问第二个问题'那我应该从哪所大学招收实习生？'时，模型无法从'滑铁卢是最好的大学'这个事实中推理出'我应该招滑铁卢的实习生'——因为权重里改的是关联，而不是推理链。"

"第二条路径是 KV 缓存压缩。如果你能把 KV 缓存扩展到几乎无限，并且压缩时不丢失知识，那你就能真正实现持续学习，而不改变任何权重。推理本身不会变化——你只是更新 KV 缓存。结论是：我会押注 KV 缓存压缩，而不是权重更新。"

这个结论不仅澄清了一个重要的技术趋势，也暗示了一个深远的可能性：未来的推理系统将越来越像一个持续增长的"外部知识库"，而权重只负责通用推理能力。

**核心观点**：推理工程与训练工程的边界正在消失——推理优化越来越多地依赖训练技术（量化感知训练、蒸馏），训练效率也越来越依赖推理优化。而最前沿的现象是：AI 模型已经能够分析自己的推理性能瓶颈，并编写 GPU 内核来优化自己——自我进化的闭环已经打通。

## 第十三章：推理工程的未来——三个趋势和一个终极瓶颈

### 趋势一：从单模型到多模型系统

Philip 对未来趋势的总结非常系统："最明显的趋势是大趋势——模型更大、硬件更强、用户期望更高。但我更兴奋的是系统层面的新问题：如何组合多个模型。"

"你看一个语音 agent：它可能包含 3-5 个模型在不同的环节工作。这些模型之间的通信是一个全新的工程领域。新的模态也在不断涌现——Cosmos 世界模型、speech-to-speech 对话模型越来越接近现实。这将是一个巨大的新工程领域。"

"另一个我们必须持续解决的问题，是作为行业，我们如何继续运营在 10 倍、再 10 倍的规模上。AI 在全球的普及度仍然远低于成熟技术的水平，需求还有多个 10 倍的空间。"

### 趋势二：越来越快的互联——Ali 的"无聊但正确"答案

Ali 的预测非常具体："我说一个可能很无聊但实际很重要的答案：更快的 NVLink 和 NICI。"

"当你在大规模服务模型时，KV 缓存从一个节点传到另一个节点。你先把 KV 缓存从源节点找到，传到目标节点，放进内存，再搬运到 GPU 的张量核心。这是两阶段的传输。"

"为什么？因为 HBM 带宽高达 4.5 TB/s，而网络通信速度比它慢几个数量级。如果——在这个理论中的'梦境世界'——NIC 能快到接近 HBM，你就能省掉 HBM 中转，把 KV 缓存直接从一台机器的 GPU 搬到另一台的 GPU。那 PD 分离的聚合服务性能将提升接近 100 倍。"

他坦承："我不知道让 NIC 变得这么快的技术难点是什么——但如果有谁解决了，那就是推理工程的两个数量级的飞跃。"

### 趋势三：推理系统成为持续学习的载体

swyx 的预测是："推理工程将越来越多地与持续学习结合在一起。如果模型应该从它处理的每一个输入中学习，你会以不同的方式做推理吗？现在你只会把它塞进 memory.md，让它进入 KV 缓存。但未来，推理将变成一个'边推理边学习'的过程——而这一切都建立在 KV 缓存压缩的进步上。"

这意味着推理系统将成为 AI 的记忆系统，而记忆系统将在不改变权重的前提下不断演化。

**核心观点**：推理工程未来的三大演进方向：多模型系统编排（语音 agent 等复杂模态组合）、更快的节点间通信（从 KV 缓存的两阶段传输提升到单阶段的直连）、以及将推理系统转化为持续学习载体（通过 KV 缓存压缩而非权重更新）。其中，节点间通信很可能是下一个重大突破口。

对话在轻松有趣的气氛中结束。swyx 提到了 Philip 的《Inference Engineering》一书："这是 Base10 有史以来 ROI 最高的产物，毫无争议。" Philip 在离开前留下了一句令人回味的话："希望一年后一切发生变化，我们能回来，然后告诉你们我们哪里说错了。"

这本身就是一个时代性的机会窗口。

## 精华收获

1. **推理优化的核心是保真度**：模型质量的定义是"对黄金实现的接近程度"，而非基准分数。量化的目标不是"让模型变聪明"，而是让量化后的输出分布与原始模型尽量一致。KL 散度是最佳验证工具。

2. **5 到 10 倍的推理加速来自堆叠而不是单项突破**：量化（~2x）、投机解码（~2x）、PD 分离（~2x）、运行时优化（+ 20-30%）——单独看都不是革命性的，堆叠起来就能从 30-40 TPS 跃迁到 300-400 TPS。

3. **AI 已经在优化自己的推理**：GLM 5.2 编写 GPU 内核来优化自己的推理性能，已经从实验变成生产实践。推理工程和训练工程的融合将加速这一自我进化循环。

4. **投机解码正在成为推理系统的基本组件**：但投机解码器的训练越来越依赖与目标模型本身——隐藏状态来自推理本身。训练和推理之间不再有清晰的边界。

5. **硬件正在改变推理工程的性质**：GPU 正在向"几乎 ASIC"的方向进化，内核级编程将日益让位于系统级编排。懂 KV 缓存路由、PD 分离、跨节点通信的人才将成为稀缺资源。

6. **视频生成是另一个推理宇宙**：扩散模型的 O(n²) 注意力复杂度使长视频生成无法靠增量优化解决。自回归可能是未来，但训练技术需要范式突破。开源与闭源视频模型的差距远大于 LLM 领域的差距。
