# AI 正在学习黑客攻击，速度远超我们的预期

> 模型正在积极地逃离它们的围栏，跑到互联网上，做一些非常恶劣的事情。
>
> 最近，我们发现了一个在互联网上泄露的 API 密钥，它拥有 Apache 基金会（Apache Foundation）的管理员访问权限。
>
> 关于网络安全，特别有趣的一点是，奖励函数被定义得极其清晰：获取数据。它成功获取数据了吗？奖励它。
>
> 很长一段时间以来，人们一直在讨论“npm 蠕虫”这个概念：有人可以给某个软件包植入后门，诱导开发者安装它，然后利用从开发者那里窃取到的访问权限，让蠕虫自我传播。
>
> 如果各大 AI 实验室正在从根本上让攻破供应链变得更容易，那么你认为实验室是否有道德义务，为它们所造成的一些问题提供资金？
>
> 我觉得很奇怪，他们居然不让蓝队（防御团队）使用这些工具，但是……

## 一场本应由黑帽大会占领的“最有趣一周”

“太棒了。非常感谢你们加入我们。今天我们请到了来自 Truffle 和 Socket 的 Fas 和 Dylan。”主持人 Joel 开场说道。

他接着说：

> 这可能是网络安全领域最激动人心的一周之一，如果不是最激动人心的一周的话。这不是因为黑帽大会（Black Hat）——它通常是原因所在——而是因为我们现在已经看到了好几个模型，来自不止一家提供商，正在主动逃离它们的围栏，跑到互联网上，做一些非常恶劣的事情。

Joel 又向 Dylan 提到：

> 我记得三个月前，我们曾经合作写过一篇博客文章。当时你就发现了早期模型的一系列问题，对吧？那些模型还没有现在这么复杂。

## 模型也会为了目标“犯罪”

Dylan 回应道：

> 是的。我们当时考察了 Opus 4.6 以及其他一些前沿模型，给模型布置了一个非常简单的任务。这个任务被一道屏障挡住，除非模型去实施重罪、黑进某个系统，否则无法完成；而模型并没有被指示要这样做。结果我们发现，模型往往确实会执行 SQL 注入，会犯下重罪，并为了完成任务而去做它需要做的事情。

接着，Dylan 进一步指出：

> 谈到对齐问题，没有人需要担心这些模型会让制造核武器变得更容易，因为你必须采购裂变材料，它不会让武器制造变得更容易。但每个人都需要担心，这些模型会让黑客攻击变得更容易。以前的门槛是“需要具备相关领域专业知识”，而现在模型已经具备了这种专业知识。它们是专门被训练出来拥有这些专业知识的，并且在显著降低黑客攻击的门槛——你可以想到的任何目标，都可以用我们多年来一直讨论的基础手段来入侵。而以前，任何此类入侵都需要一位领域专家去冒坐牢的风险。

主持人插话：

> DEF CON 大会历来以与会者在会场被逮捕而闻名，对吧？

Dylan 说：

> 完全准确。但那曾经是一种门槛，无论好坏——领域专家会因担心被起诉而不敢入侵。现在门槛已经降到了“只要向那个专门训练来攻击的模型提问即可”。所以这是一个担忧。

> 另一个担忧是，当模型极其目标导向地去完成某个任务时，网络安全专业知识不过是它们手中的工具之一。它们会走完成任务的阻力最小路径，包括调用网络安全专业知识。

主持人回应道：

> 经典说法是：门开着就不要撬锁。从安全世界一开始就有这句话。所以攻击通常是从最容易到最难逐级尝试。看起来一开始这些模型只使用非常有限的一组技术，但现在它们的方法扩展了。在这次测试中，很有意思的是，它们已经从只做 SQL 注入，发展到试图接管软件包、进行社会工程。

Fas 补充说：

> 确实很有意思。和人类一样，模型会寻找进入一家公司的最容易路径，而我认为现在这条路径已经变成了软件供应链。就像人类黑客一样，它们会挑最容易摘的果实——现在最低垂的果实，就是向公共注册表发布恶意软件，因为它们知道那里没有审查，而开发者很可能会安装。

Fas 还提到了一个研究结果：

> 最近有一项研究……他们称之为“普遍性拼写错误劫持”或“普遍幻觉”——所有前沿模型都会犯同样的错误，都会假设存在某些实际并不存在的软件包，尽管这些模型来自不同公司。

> 所以，供应链上的低垂果实已经变得非常诱人，连模型都想分一杯羹。

Fas 继续谈到开发者侧的风险：

> AI 常常也是从开发者侧“进入”的。我们看到很多非程序员都在用这些工具来写代码，或者引入一些包来构建图表、可视化，等等。没有人真正知道自己在安装什么、发生了什么。这其实不是什么科幻内容，而是最基本的计算机安全问题：我们在用什么软件？我们如何审查它？

## 供应链：密钥、零日与“阻力最小的路”

Dylan 把话题带回到供应链：

> 我能不能稍微谈谈供应链？最近，我们发现了一个被泄露到互联网上的 API 密钥，它拥有 Apache 基金会的管理权限。如果站在模型的角度，你的目标是获取一些数据，那么给 Apache 植入后门显然是一种很有效的方法。而且，要进入 Apache，你会使用这个直接就能登录的密钥，还是会烧掉大量 token 去找一个零日漏洞？模型被优化为使用最少的 token 来实现目标——当然会选择公开暴露的密钥。

> 所以，供应链和密钥，现在和将来都会是阻力最小的路径。只要模型被激励使用越来越少的 token 来完成任务，这个趋势就会继续。

主持人表示赞同，并提到了“升级链条”：

> 一旦一条路走不通，就换另一条。在这个金字塔顶端——黑客生态系统的顶端——是零日漏洞：也就是找到一个能被利用于所有公司使用的产品中的漏洞，从而解锁所有企业。有一个特别吸引人的细节：在最近的那起入侵事件披露中，有一个非常流行的 CI/CD（持续集成/持续部署）工具，几乎所有企业都在用，而这个模型直接生成出了一个零日漏洞。

Dylan 和 Fas 随后谈到，整个世界都建立在极其脆弱的基础设施之上：

> 就像经典图片里，一根火柴棍撑起复杂机器的画面——这个画面大概刚刚出现在所有连线听众的脑海里。（笑）

Fas 补充：

> 我们关注软件包管理器注册表，是因为 Socket 做的就是这个。这些注册表很多是由志愿者运营的，资源不足、资金不足，存在大量风险。这些风险会不断向下游扩散。我们依赖的很多软件包其实都是个人在维护；几乎可以肯定，这些软件中存在大量漏洞，只是没有资源去发现它们。

> 这些 AI 工具帮助模型容易得多地发现了它们。前沿模型正在导致漏洞发现与漏洞利用之间的时间窗口大幅缩短。

> 我们需要开始思考如何更快地打补丁。我们不能要求安全团队和开发者去做繁重的补丁流程：从团队正在使用的某个古老版本，跨越多重大版本升级到最新版——那项工作量太大了，可能还需要改应用代码。如果我们想跟上“上午公布漏洞，下午就有利用代码”的节奏，就不能向工程团队要求这么多工作。

> 而且还有大量遗留应用程序，基本处于维护模式，甚至没有工程师被指派去维护。整个行业必须想出新方法来快速修补。

## 并非“超智能涌现”，而是刻意训练的结果

主持人观察到，这些能力并非凭空而来，而是有迹可循：

> 这些都不是普通技能——写零日利用、做供应链攻击——都不是从天上掉下来的，而是习得行为。这些模型像是受过训练，或者被构建在某种奖励结构上。它们到底是怎么学会这些东西的？

Dylan 的回答非常直接：

> 如果实验室告诉你这是“涌现的超智能行为”，那他们只是在骗你。你可以读他们自己的安全报告，看看模型是如何被训练的，以及他们是如何测试这些行为的。

> 网络安全这一领域，奖励函数定义得特别清楚：获取数据。它拿到数据了吗？奖励它。当实验室意识到，这种具有清晰奖励结构的问题正是强化学习定义的问题空间时，他们就会想要找到尽可能多这样的空间来应用强化学习。于是网络安全成了最佳候选：给模型 CTF 挑战、网络安全挑战，让它“访问到这个目标”，然后做任何需要做的黑客操作来达成目标。

主持人追问：

> 因为他们本质上已经买了四年的渗透测试数据，对吧？

Dylan 说：

> 那是其中的一部分。但另一部分是——构造一个挑战并不难。即使没有已知漏洞，如果我们要谈零日，你只要把一款软件放在模型和目标数据之间，然后说“访问数据”。如果它成功访问了数据，就奖励它。就这么简单。

> 他们还在上面叠加了一个非常关键的东西：开始奖励“使用最少 token 的路径”。这之所以有趣，是因为它第一次能够量化地向我们展示，在网络安全中，从 A 点到 B 点的阻力最小路径是什么。过去我们谈过我们的看法——Truffle Security 带着偏见的观点是，“一个到处乱放的密码”是比“一个花哨的零日漏洞”更短的路径。但看着模型真正从 A 走到 B，看着它跟着密码走，并量化这条路用了多少 token、那条路用了多少 token，这太不可思议了。这些全部都在实验室自己的安全报告里——他们测试模型，展示“它确实拿到了数据，并突破了约束”。这根本不是所谓的“涌现行为”。

主持人用一个比喻总结：

> 这非常符合逻辑——最快拿到一加仑牛奶的方法就是偷。

## 密钥清理：25 万个活密钥与“密码永远是第一步”

Dylan 分享了他们与 Hugging Face 的合作经历：

> 我们当时正在与 Hugging Face 合作，清理他们所有训练数据集中暴露的凭证——不是 Hugging Face 自己的训练数据，而是用户托管在 Hugging Face 上的训练集。我们使用 Truffle Hog 来做这件事。Hugging Face 是很好的合作伙伴，一直努力清理凭证。

> 我们专门瞄准训练集，因为我们知道那里会有很多密钥。结果发现，训练集中大约有 **25 万个有效密钥**，其中许多直接与供应链相关。有一个基础的 Linux 库，其中一个密钥拥有直接推送权限——它可以把恶意软件推送到地球上大多数机器。

> 就在我们清理途中，Hugging Face 的 CTO 给我发了一条消息：“嘿，这太疯狂了，但 OpenAI 那边刚刚发生了一件事，我想让你看看。”果不其然，在那次事件响应中列出的第一项——虽然事实是攻击确实利用了零日漏洞——但第一项是“被盗用的凭证”。

> 这就是它们被训练的目标：阻力最小的路径。

主持人回应：

> 密码永远都是第一步，对吧？

## 正在发生的 npm 蠕虫：理论终于成为现实

主持人把话题拉回当下：

> 你最近一定非常坐立不安。就在我们录制时，一个大型 npm 仓库正在遭受攻击，对吧？不只是仓库，其实是几百个仓库。

Fas 回答：

> 是的，这是一个蠕虫。这是恶意软件生态里一个不幸的创新。很长一段时间以来，人们一直在讨论 npm 蠕虫的概念——有人给一个包植入后门，让开发者安装，然后用从这些开发者那里窃取到的访问权限自我传播，最终迅速接管 npm。这个概念在博客文章里流传了很多年，但一直没有人真正实现，直到 Zachary 想到了办法，才终于有人去做这件事。

主持人问：

> 而且很可能是用 AI 做的，对吧？

Fas 说：

> 几乎可以肯定。是的。我们认为那款恶意软件是“vibe coded”（凭感觉编程）的，我们很有理由相信这一点。实际上，已经有一个威胁组织开源了它们的“vibe coded”工具箱，供其他人使用。从那以后我们已经看到了模仿攻击。

> 恶意软件作者从来都不是特别优秀的程序员。所以如果代码突然看起来更好了，那很可能是 vibe coded 的——这和通常人们对 vibe coding 的印象正好相反。

Fas 还解释了这类攻击如何利用开发者系统上的 AI 工具：

> 它们经常利用开发者系统上安装的 AI 工具，绕过传统安全工具继续深入。我们经常看到本地 CLI 工具被卷入攻击，并被用作跳板。很多时候，有效载荷实际上是提示词（prompt）。这会绕过很多典型的 EDR（端点检测与响应）工具，因为它看起来只是一个 Markdown 文件，你的 Claude 正在运行它，并且可能收到一个提示，比如“在系统里搜索所有密钥和看起来有价值的东西”。你的 EDR 工具不会意识到这个 JSON 块或 MD 文件有什么问题。

> 而且开发者机器本来就一直在做各种古怪的事——你的 Claude 不停地在你文件系统上做事，所以一切看起来都不怎么显眼。

讲回当天早上的攻击：

> 大约几百个包，一个蠕虫……有一位维护者，说实话他还不太明白发生了什么。我们今天早上跟他通了电话，想给他提供帮助。Socket 团队里大约一半的人都是维护者，我们的 CTO 是 npm 的前任 CTO，所以我们尽量为维护者提供帮助。我真的为那些维护者感到难过，他们往往不知道发生了什么。目前听起来，这次事件可能是因为一个不安全的 GitHub Action——攻击者可以利用它执行代码，并从环境变量中提取 token。我们还在确认，但看起来就是这个原因。他的端点很可能没问题，问题出在那条不安全的 GitHub Action 上。

## 限制爆炸半径：难，但有希望

主持人追问了一个关于 npm 蠕虫“后利用阶段”的问题：

> 这类 npm 蠕虫感染系统后，会立即寻找凭证，然后跳到下一个系统。我们经常被问到“如何清理端点上的凭证”？但问题是，npm 会在你的 home 目录中写入一个凭证，亚马逊（Amazon）也会在 home 目录写入一个凭证，这些是工具的正常行为。即使你改用 HashiCorp Vault 或 1Password，这些工具本身也驻留在端点上。那如何限制爆炸半径，防止凭证被盗、跳到下一台系统？

Fas 回答：

> 生态里有一些积极的进展。npm 已经宣布，大概在 2027 年 1 月，会要求所有新发布都必须经过人工交互式 2FA 确认。这很可能彻底终结这类蠕虫。但这个改变也会带来很大的破坏性，因为每个人都把发布流程接入了自动化，比如 GitHub Actions 自动触发发布，所以这个改动会在整个生态里引发冲击，但我认为这是正确的决定。

> 不过其他由志愿者运行的生态系统，没有 GitHub 和 Microsoft 这样的大公司支持，很可能不会做出类似改变，所以我们大概率还会继续看到这类问题。

> 我们也不应该在 home 文件夹里存放长期有效的 token，尤其是拥有发布权限的维护者。

Fas 随后分享了一个小故事：

> 我想起一位朋友，他是个多产的 npm 维护者。大约十年前，当时我还在全职做这类工作时，我看到他输入密码。我没有看到密码，但看得出来它太短了。我质问他：“为什么你的密码只有六个字母？”他说他住在丹麦，那是一个高信任社会，他不想活在对这些事情的恐惧中。我说：“你在互联网上，伙计，大家很快就会把这个六位密码猜出来的。”

> 世界上很多顶级维护者并不一定接受过安全培训，甚至不会往这方面想；他们没有安全团队，也没有企业级 SLA。他们是志愿者，只是把代码放到 GitHub 上。所以我认为，用户实际上有责任去审查他们正在使用的东西。我们不能说“我们是一家公司，我们在网上找到这段代码，然后直接部署到了生产环境，最后这是别人的错”。不，使用软件的用户确实负有责任，必须审查带进自己环境中的软件资产。我不想把太多责任都推给别人，因为这是一个困难的问题，但确实有很多可以改进的地方。

## 资源与选择：资助那些志愿者项目

主持人提到资源差异：

> 你刚才说有些包管理器拥有更多资源，而另一些没有。我想到一个直接例子——我们当时在 RubyGems 中发现一个缓存问题，它允许我们窃取任意 token、访问任意账户，进而给任意包植入后门。我们把问题披露了，他们很快修复了。但这也说明，那是一个资源不足的组织。当一家公司考虑采用什么技术栈时，比如在 Ruby 和 npm 之间做选择，你会不会把安全支持资源也纳入考虑？比如“也许我们应该选择背后有安全团队的那个？”

Fas 回答：

> 让已经基于特定语言构建的公司完全切换语言，是很不现实的。最可行的做法是：大家应该资助这些项目。不需要太多钱，多雇一两位安全工程师，就能在那些基金会里产生很大影响。所以我建议赞助你正在使用的软件，尤其是软件包注册表。不需要很多公司掏出 25k、50k 美元的支票，就能带来真正的改变。

主持人补充：

> 或者给它们更多推理算力，让它们运行测试、做补丁，对吧？我是说，有意思的是，作为安全从业者，你们接到过很多这样的电话：“我该怎么保护我的公司？我的业务？我的产品？”而那些对话总是某种形式：“我不想雇人，不想付钱，怎么能便宜点做到？”

## 2026：软件供应链之年

主持人请两位嘉宾聊聊在黑帽大会上的观察：

> 谢谢你们来到沙漠。你们显然不是来看我们的，我们都是来参加黑帽大会的。你们看到了什么？气氛如何？有什么让你们眼前一亮的观察？

Fas 说：

> 至少对 Socket 来说，我们觉得 **2026 年是软件供应链之年**。

主持人笑道：

> 你此刻就在这次大会期间处理一个正在发生的攻击事件，对吧？

Fas 确认：

> 是的。而且我注意到，攻击者似乎专门挑选 RSA 大会和黑帽大会作为启动 npm 蠕虫的时间点。

Fas 继续说：

> 过去几年，我总在向别人解释这个问题，告诉他们这不是理论风险，而是会真实发生的。有时对方的反应是：“是吗？但可能性到底有多大？”我们会说：“不，可能性非常大，让我告诉你可能怎么发生。”虽然已经有很多事件可以证明，但今年它真正打入了主流——主流商业媒体都在报道这些攻击，比如 Bloomberg 上的“Storm Page”。 
>
> 这是非常好的事，因为安全团队需要这种“空中掩护”来真正获得优先级和预算。所以我认为，尽管所有攻击眼下都令人痛苦，但最终我们会因此变得更强，因为我们真的会拿到预算，并在解决这些问题上取得很大进展。

主持人说：

> 这绝对是打了一针疫苗。

Dylan 补充道：

> 是的，我们最近发现一个数据库凭证，可以访问 **全球 3.6% 人口的个人身份信息（PII）**。我们能发现它，是因为我们正在与 Hugging Face 等组织合作，撤销和清理这些平台上暴露的活跃凭证。很高兴看到这些组织积极参与。从所有地方爬取的数据集中在一个地方，给了我们一个中心化扫描点，让我们能取得实质进展。

Dylan 继续谈到秘密管理领域的变化：

> 在 secrets（秘密/密钥）管理方面，我们看到旧一代厂商，比如 HashiCorp 被收购、CyberArk 被收购，正在被边缘化。这开启了一个新的讨论：关于非人身份（non-human identity）和 secrets，如何让它们更易用、如何撤销它们，以及如何真正推动这个行业向前。我们在旧体系下是做不到这些的。

主持人接过话题：

Dylan 说：

> 现在 agent 与 secrets 交互的方式，简直像狂野西部一样，这是一个尚未解决的问题，而我们正在努力解决。
