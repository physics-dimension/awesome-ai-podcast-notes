### 一、开场的震撼宣言：三段提示词，替代三个付费 SaaS 工具

`[视频 开场部分]`

**核心观点**

Riley 用"昨天我用三个提示词构建了一个应用，替代了三个我每年支付数千美元的 SaaS 工具"作为开场，瞬间点明 ChatGPT Sites 的核心价值主张——软件构建的门槛正在被 AI 彻底抹平。

**深度阐述**

视频的第一句话就极具冲击力："今天，我要向你展示在 ChatGPT 内部构建任何你想要的应用有多容易。昨天，我构建了一个应用，它替代了三个我为此支付了数千美元的 SaaS 工具，而我只用了三个提示词（three prompts）就完成了。" 这句话的分量在于：它不是关于"生成一段代码片段"的演示，而是关于"构建一个真实业务工具"的完整叙事——有数据、有团队协作、有内容生产用途，不是玩具，是生产力。

这个应用名为 **Social Scrape**。Riley 这样描述它的功能："它可以分析所有短视频平台。它可以从 Instagram 或 TikTok 抓取完整的视频、所有的统计数据（stats）和文字记录（transcript），并将所有这些信息存储在网站中，我的整个团队都可以用它来创作内容和广告。" 细想一下，这个应用所替代的 SaaS 工具是什么：一个负责下载视频的工具、一个负责分析账号数据的工具、一个负责团队素材库协作的工具。三个工具的工作被压缩进了一个自定义应用里。

Riley 强调了一个许多观众可能不知道的事实："ChatGPT Sites 内置了数据库、托管、认证、存储和自定义域名。" 这五个词听起来轻描淡写，但它们构成了现代 Web 应用的全部骨架——数据库管数据持久化、托管管线上可达、认证管用户身份、存储管多媒体文件、域名管品牌入口。在过去，配置这一整套基础设施需要一名全栈工程师至少数天的工作，而现在，它们是"开箱即用"的默认能力。

**个人感受**

Riley 的兴奋感是真实可感的。他不止一次用 "literally anyone can build"（任何人都能构建）来强调这件事的门槛之低，言语间带着一种"发现新大陆"的惊叹。作为一个内容创作者而非程序员，他显然真切地感受到了这种技术解放带来的力量。

**延伸思考**

"替代三个 SaaS 工具"是 AI 应用平台时代的一个重要信号：当构建定制软件的成本趋近于零，通用型 SaaS 的定价逻辑将面临根本性挑战。如果你的团队每月为多个工具付费，而每个工具只解决一个简单的数据操作问题，那么"用 AI 构建自己的微型应用"将成为越来越有吸引力的替代方案——这可能是未来几年软件行业最深刻的暗流之一。

### 二、GPT Work 是什么？ChatGPT 与 Codex 之间的"中间地带"

`[视频 概念讲解部分]`

**核心观点**

ChatGPT Work 是 OpenAI 产品矩阵中处于普通 ChatGPT 与专业开发者平台 Codex 之间的产品，你可以把它理解为一个"云端带电脑的智能体"。

**深度阐述**

在正式构建应用之前，Riley 花了一点时间帮观众建立起对 **ChatGPT Work** 的认知框架，因为 Sites 功能就生长在这个土壤之上。

"你可以几乎把 ChatGPT Work 看作 ChatGPT 和 Codex 之间的中点。" 他给出了一个三层的产品定位：
- **Codex**：OpenAI 面向开发者的智能体平台，用于高强度的编码任务，是专业程序员的重型武器。
- **ChatGPT**：日常对话、常规问答的入口。
- **ChatGPT Work**：介于两者之间，既不是纯聊天，也不是纯编码环境，而是能处理更复杂任务的中间形态。

如果这个比喻还不够直观，Riley 提供了第二个更传神的思考框架："你也可以把 ChatGPT Work 想象成云端的一个有电脑的智能体（an agent in the cloud with a computer）。" 这个比喻非常精准——它不是在聊天窗口里生成文字，而是拥有一个真实的运行环境（一台云端的计算机），可以执行任务、操作文件、调用工具、构建和部署产品。

Riley 还提到一个关键的背景信息：大约一个月前，OpenAI 把 ChatGPT 应用和 Codex 应用合并到了同一个平台，所以你如今可以直接在 ChatGPT 桌面应用中访问 GPT Work。这意味着"聊天"、"写代码"和"建应用"之间的边界正在消融，你可以在同一个窗口里完成从想法到产品的完整闭环。

**视觉/结构信息描述**

Riley 在桌面版 ChatGPT 中开启了 "Work tab"（工作标签页），展示了 ChatGPT Work 的界面；同时在手机端也展示了同一个入口——强调该功能跨设备可用。

**延伸思考**

"云端的智能体 + 电脑"是理解 AI 智能体未来形态的关键钥匙。传统 ChatGPT 是"对话即服务"——你问它答；而 Work 是"环境即服务"——AI 拥有一个可以真实执行操作的计算机环境。从"副驾驶"到"独立执行者"，这是 AI 能力定位的一次静默但巨大的跃迁。

### 三、@sites：一个符号召唤出完整的应用平台

`[视频 @sites 功能演示部分]`

**核心观点**

在 ChatGPT Work 中，只需 @ 提及 sites，AI 就会自动构建一个具备托管、数据库、认证、存储、共享能力的完整网站——这是 Sites 功能最核心的交互方式。

**深度阐述**

在展示了 Work 界面之后，Riley 亮出了王牌——@sites 功能。他的演示命令极其简短："Hey, please build a @sites that does blank"（嘿，请构建一个 @sites 来做某事）。就这么简单。"This will automatically build a hosted site"——系统会自动构建一个托管站点，意味着它是真实地存在于互联网上的。

Riley 详细拆解了这个 @sites 指令背后打包的能力：
- **数据库（database）**：数据被存储在应用内部，无需单独配置数据库服务；
- **认证（authentication）**：用户可以登录系统，身份验证被内置；
- **存储（storage）**：可以像任何正常应用一样上传图片和视频；
- **分享（sharing）**：你可以直接把这个站点分享给任何人使用。

在传统开发中，实现以上任何一项功能都需要引入对应的技术栈：前端框架（React/Vue）、后端服务（Node/Python）、数据库（PostgreSQL/MongoDB）、认证中间件（Auth0/Firebase Auth）、对象存储（S3/Cloudinary）、域名与部署（Vercel/AWS）……而现在，这一切被压缩成了一个 "@sites" 的提及符号。Riley 还特别推荐了构建 Sites 的最佳场所——ChatGPT 桌面应用，因为桌面端与 GPT Work 集成最深、体验最完整（不过他也展示了手机端同样可以 @ mention sites，说明该功能已经全平台覆盖）。

**个人感受**

Riley 形容这是 "one of the coolest features"（最酷的功能之一）。从他用词中的情绪可以感受到，"@ 一下就能得到一个完整网站"所带来的魔法感，即使对已经熟悉 AI 工具的他来说依然是令人兴奋的体验。

**延伸思考**

@ 符号正在成为 AI 交互中"能力引用"的标准隐喻（如 @sites、@codex、@skills）。这非常类似于编程中的命名空间或模块导入——用户不需要了解底层实现，只需要知道"@ 某个名字就能调用一套能力"。这种交互范式的标准化，可能深刻影响未来所有 AI 操作系统与用户之间的沟通方式。

### 四、目标画面：昨天构建的 Social Scrape 成品

`[视频 成品演示部分]`

**核心观点**

在构建之前，Riley 先展示了前一天的成品效果——一个可以抓取任意社交平台视频、显示统计数据、播放内容、复制字幕并下载视频的完整应用，为观众建立了清晰的"目标画面"。

**深度阐述**

在动手构建之前，Riley 选择先展示"昨天"的成果——这不仅是为了炫耀，更是为观众设定一个清晰的目标："这就是我们将要构建的东西。" 这个成品的功能链路完整而实用：

第一，**抓取**。"我能够抓取任何社交媒体平台的视频，然后它们会显示在这里。" 他现场播放了一段抓取到的视频，视频里传来 "category in" 的声音——那是被捕获内容的一部分。第二，**多账号覆盖**。他展示了同时抓取了 Rowan Cheung（一位知名的 AI 领域创作者）的视频，画面中传来 "Japanese scientists just…" 的片段，表明应用可以同时管理多个内容来源。第三，**字幕提取**。"我也可以点击 transcript（文字记录），复制文字稿。" 这对内容创作者来说极为实用——研究竞品文案、提取灵感素材都不再需要手动转写。第四，**真实托管与下载**。"这个视频被托管在这个 ChatGPT Sites 上，我可以 literally 下载这个视频。" 这句话暗示着 Sites 拥有真实的媒体存储与分发能力，视频文件存放在平台之上，任何授权用户都能将其下载。

**视觉/结构信息描述**

应用界面：抓取到的视频以卡片/列表形式展示；点击视频可直接播放；每个视频条目附带了统计数据和 transcript 按钮；页面上还有明显的下载按钮。

**延伸思考**

"抓取 → 存储 → 展示 → 下载 → 团队协作"这条链路，本质上就是内容情报工作的完整流程。将一个日常高频的工作流打包成一个定制应用，正是 AI 原生时代"工作即应用"的雏形。将来，我们可能不会再去"购买一个 SaaS 工具"，而是"让 AI 为我构建一个工具"——因为后者往往更贴合自己的流程。

### 五、核心机密：那段构建 Social Scrape 的完整提示词

`[视频 提示词解析部分]`

**核心观点**

Riley 公开了构建 Social Scrape 的完整提示词——它实际上是一份自然语言版的产品需求文档：定义了前端样式、权限模型、数据输入方式、数据模型、外部技能集成和种子数据。

**深度阐述**

这是整个视频中最具教学价值的部分。Riley 把他实际使用的提示词逐句呈现在屏幕上，我们可以拆解出它的完整逻辑结构：

**第一层：前端设计规格。** "构建一个 GPT Sites，拥有一个漂亮的全白前端，中间是一个大的手机边框在中心。" 一句话定义了应用的整体视觉和布局——不是传统的网页形态，而是模拟手机体验的沉浸式界面，这与短视频消费场景完美匹配。

**第二层：权限与团队认证。** "这个应用将是我与团队共享的。网站允许团队中的任何人登录、认证，并查看我创建的展示内容。" 这定义了应用的访问控制模型——开放给团队成员，但需要身份验证。

**第三层：内容输入双通道。** "我应该能够手动上传短视频到网站，或者通过点击手机边框下方的一个图标，复制一段提示词并交给任何智能体，智能体可以把视频上传到应用中。" 这里的设计非常精妙：应用不仅接受人工上传，还为 AI 智能体预留了上传接口——人类和 AI 都是内容供给者。

**第四层：存储与数据模型。** "应用应该有视频存储和数据库，这样每个视频的所有统计数据都在里面。" 数据字段包括视频文件、点赞/评论等统计数据，以及字幕文本。

**第五层：技能集成——此处体现了架构设计的智慧。** "这个应用将配合一个 scrape creator 技能使用，该技能使用 Scrape Creators 的 API。我不会把它加到应用或网站本身，而是让智能体去抓取创作者数据，它会创建一个以创作者名字为标题的播放列表，然后我就可以在托管应用中播放它抓取的视频。" 抓取能力作为外部技能存在，与应用解耦；站点只负责存储和展示。这实际上是一种服务端与展示端分离的架构思想（类似后端 API 与前端应用的分离），虽然 Riley 可能并没有刻意学习过软件架构。

**第六层：种子数据与功能要求。** "先从 Riley Brown 2025 年最好的、非赞助的视频开始，把它们放到应用里。应用还应该有一个下载按钮，这样应用内任何人都可以下载视频。" 既定义了初始内容，也补充了功能清单。

这就是全部。Riley 将其粘贴到 ChatGPT Work（桌面应用 + 新版 Sites 功能）中，然后启动运行。

**深度洞察**

这份提示词最了不起的地方，在于它在不知不觉中完成了一份标准的 PRD（产品需求文档）：UI 样式、权限模型、数据流、数据模型、外部集成、初始化数据、功能清单，一应俱全。在传统开发流程中，写出这份 PRD 可能需要一个产品经理花上两天，而程序员实现它则需要数周。在这里，它就是一段可以被 AI 直接"编译"成应用的自然语言。

**个人感受**

Riley 作为内容创作者，没有专业的技术背景，但他的提示词展现出令人惊讶的"产品直觉"——他知道要把抓取（skill）和展示（site）分开，知道要定义数据统计字段，知道要设定初始内容。这印证了一个趋势：当构建工具足够强大时，**产品思维比技术技能更重要**。

### 六、25 分 8 秒后：第一个版本的诞生

`[视频 首次运行部分]`

**核心观点**

提示词运行了 25 分钟 8 秒后，Social Scrape 的第一个版本诞生了——它成功抓取了 Riley 的六条视频，通过了 ChatGPT 安全登录验证，可以通过浏览器直接访问，虽然界面有些粗糙，但功能完整。

**深度阐述**

"好的，它工作了 25 分钟 8 秒。" Riley 点击 "Open in browser"（在浏览器中打开），一个真实的 Web 应用出现在眼前。这个 25 分钟的数字值得玩味——在传统开发中，从零构建一个带认证、数据库、文件存储和多媒体播放的 Web 应用，至少需要数天到数周时间；在这里，它只是后台任务的一次运行时长。

当页面打开时，首先迎接用户的是安全登录界面："这个网站使用 ChatGPT 的安全机制来安全地验证你的身份。" 用户只需点击 "Continue with ChatGPT"（继续使用 ChatGPT 登录），就能用自己的 ChatGPT 账号进入应用。这揭示了一个重大便利：**Sites 的认证系统直接复用了 ChatGPT 的身份体系**——你不需要维护任何用户数据库，不用管密码重置、邮箱验证、会话管理，OpenAI 已经替你处理好了这一切。

登录完成后，应用开始 "loading reels"（加载视频）。结果令人惊喜又带着一丝"果然如此"的会心一笑："我可以看到它抓取了我六条视频……它看起来和昨天我创建的那个应用非常相似。" 但 Riley 也大方承认第一个版本并不完美："它有点粗糙（a little bit clunky），但别担心，我们待会儿会修复它。"

**个人感受**

Riley 对第一版瑕疵的态度非常务实——没有任何气馁或懊恼，而是轻描淡写地说了句 "no worries, we will fix it"（别担心，我们会修复的）。这种"先构建再迭代"的心态，正是 AI 开发时代最重要的心智模式：因为修改成本极低，所以完美主义没有意义，先跑起来再说。

**延伸思考**

25 分钟 vs 数周的效率提升，改变的不仅是速度，更是项目的经济模型。过去，构建一个软件意味着人天成本、机会成本和管理成本；现在，最大的成本仅仅是你组织提示词的思考时间。当失败成本趋近于零，你将可以像做实验一样，一个下午尝试十个想法——这是创新者在过去梦寐以求的自由。

### 七、注释式迭代：在页面上"指指点点"就能改应用

`[视频 注释修改部分]`

**核心观点**

Sites 最惊艳的隐藏特性是"注释驱动迭代"——在浏览器中打开站点、进入 annotate 模式、直接点击界面元素并写下修改意见，AI 会自动修改代码并重新部署站点。

**深度阐述**

"这是修改东西最简单的方式之一。" Riley 展示了这个令人上瘾的工作流：在浏览器中打开自己的站点，点击一个 **annotate**（注释）按钮，然后可以直接点击页面上的任何元素、写下修改意见，每条意见会作为一个评论（comment）被添加。

他现场提交的第一轮修改请求包括三条：
1. **"视频应该是全屏的，点赞和评论应该像 TikTok / Reels 那样作为叠加层显示。"** —— 这是一个典型的 UI/UX 修改需求；
2. **"顶部栏不要那么高（make top bar less tall）。"** —— 纯布局微调；
3. **"把下载按钮做得更好一点，它看起来很奇怪。"** —— 视觉美化。

Riley 逐一点击相关的界面元素、附上这些文字指令，然后点击 "make these changes"（做这些修改）。注意这里的交互本质：**修改请求全部以自然语言附着在可视化元素上**。他不需要知道 CSS、不需要理解组件结构、不需要搜索代码文件——只需要像一个给设计师写审阅意见的客户一样，指出"这里不对，改成那样"。

当 AI 完成修改后，Riley 在浏览器中刷新页面——"现在它是全屏的了。我们可以直接看下一个视频。" 视频播放时传出 "Is programming going to be replaced by vibe coding?"（编程会被"氛围编码"取代吗？）的音频——这是一条抓取的真实内容。接着他展示："这个视频有 10K 点赞，我可以看到所有统计数据。" 数据正确显示，叠加层工作正常。

**视觉/结构信息描述**

annotate 模式的交互流程：用户点击页面元素 → 出现输入框 → 输入修改意见作为评论 → 提交后 AI 编辑应用代码 → 刷新页面查看更新。叠加层效果为 TikTok/Reels 式（视频全屏铺满手机画框，点赞数与评论数悬浮显示在右侧）。

**延伸思考**

"可视化注释 + AI 自动改代码"代表了一种全新的软件调试范式，可以称之为"设计反馈闭环"。传统开发中的改布局需要开发者理解 DOM 树、CSS 优先级、响应式规则；而这里的用户只需要具备"视觉审美"和"表达能力"。这实际上把"产品经理提需求 → 开发改动 → 验收"的瀑布式流程，压缩成了几秒钟的即时循环。

### 九、底层原理：Skills 技能与外部 API 的协作机制

`[视频 原理讲解部分]`

**核心观点**

Social Scrape 的抓取能力来自外部服务 Scrape Creators 的 API，通过 ChatGPT Work 的"技能（Skills）"机制接入——用户只需把 API key 交给 AI 并说明需求，技能即可自动创建并复用。

**深度阐述**

在完成了全部演示后，Riley 觉得有必要解释这套系统的底层运作方式——它是怎么"抓到"那些视频的？他提到："当你在使用 Codex 或 GPT Work 时，你可以使用一些叫做 plugins 和 skills 的东西。"

具体到他的工作流，他所依赖的技能叫 "**scrape creators**"（抓取创作者）。"我在发现 GPT Sites 之前就大量使用这个技能了。" 这个技能的能力正是你之前看到的效果——从任何社交媒体账号抓取数据。

接下来 Riley 揭开了技能的神秘面纱："这个工作方式的原理实际上是使用了一个外部 API。" 他详细演示了接入流程：

1. 打开 Chrome 浏览器，搜索 "Scrape Creators API"——这是一个第三方提供的抓取服务；
2. 在 Scrape Creators 官网注册并获取一个 API key；
3. 回到 ChatGPT Work 或 Codex，告诉它："我想创建一个使用 Scrape Creators 的技能。请帮我创建它，这是我的 API key"；
4. 把 key 粘贴进去——完成。

就这么简单。Riley 还很坦诚地补充了一句："这在技术上不是最佳实践（not best practice），但这就是我创建技能的方式。" 他指的是把 API key 直接写进技能配置而不是走更规范的安全流程——不过正如他后面展示的，Sites 设置面板中也提供了环境变量（environment variables）功能，更讲究的用户可以在那里管理密钥。

技能创建完成后，你便可以让智能体从任何社交媒体平台拉取数据。Riley 强调："这非常有用。然而，展示（这些数据）一直是很烦人的部分——这就是我把它放进一个网站的原因。" 这句话点破了整个视频的核心动机：**抓取数据从来不是问题，展示和分享数据才是。** Sites 解决的是"最后一公里"问题——把抓取到的数据变成团队可用的界面。

他最后总结道："我现在有一种更好的方式来展示用 scrape creators 技能（通过其 API）拉取的数据。" 并承诺把所有用到的技能和服务的链接放在视频描述中供观众复刻。

**架构洞察**

拆解 Social Scrape 的完整架构，可以发现一个清晰的模块化设计：
- **数据获取层**：Scrape Creators 外部 API + "scrape creators" 技能（负责抓取视频、统计、字幕）；
- **数据存储层**：ChatGPT Sites 内置数据库（负责结构化数据的持久化）；
- **文件存储层**：Sites 内置存储（负责视频文件的托管）；
- **展示与交互层**：Sites 托管的前端界面（全白 + 手机边框 + 播放器 + 下载按钮）；
- **身份认证层**：ChatGPT 安全登录（负责团队成员的访问控制）。

这五层架构，在传统开发中对应着一整支团队的工作成果；在 AI 原生开发中，它只是"三句提示词"。

**延伸思考**

Skills 机制是 AI 应用生态的"应用商店"前身——任何拥有 API 的服务都可以被打包成一个可被 AI 调用的技能。当越来越多的服务以技能的形式接入 AI 平台，"调用工具"将像"调用函数"一样成为 AI 的基本操作，而那一天的商业竞争焦点将是：谁的服务能被 AI 最顺畅地发现和调用。

### 十、站点管理后台：域名、环境变量、分析与数据库

`[视频 设置演示部分]`

**核心观点**

ChatGPT Sites 内置了完整的站点管理后台：所有站点统一管理，支持自定义域名、环境变量配置、流量分析和可视化数据库浏览——专业级控制能力全部开放给零代码用户。

**深度阐述**

视频的最后一个技术环节，Riley 展示了 Sites 功能的设置面板。他说："在我离开之前，我想谈一件事——站点设置（site settings）。"

首先，如何管理所有站点？非常简单：在 ChatGPT 左侧面板中点击 "sites" 选项，就能看到所有已经创建的站点列表。对于任意一个站点，点击右侧的三个点（⋯）菜单，选择 "settings"（设置），就进入了管理面板。

设置面板中包含了五个专业级能力：

**1. 域名管理。** "我可以在这里修改域名。我们还可以添加自定义域名（custom domains）。" 这意味着你可以不用为站点配置 DNS、SSL、CNAME 等繁琐步骤，域名服务被内置；如果你想绑定自己的品牌域名，也只需在这里操作。

**2. 应用名称。** Riley 在演示中把站点从默认名改成了 "Social Scrape"——改名即时生效。

**3. 环境变量。** "如果你想把那些 API 密钥添加到你的应用中，你可以在这里添加。" 这是前面"not best practice"部分的正确解法——环境变量是存储 API key 等敏感配置的标准机制，应用内代码可以安全地读取它们，而不被写入版本库。

**4. 数据分析。** "你还可以访问应用的分析数据（analytics）。" Riley 展示了当前的流量情况："现在我是唯一使用这个站点的人，所以每日流量非常少……我实际上还没有把它发给我团队里的任何人，因为我们是刚构建完的。" 他的坦诚（以及"还没发给团队成员"这个细节）让整个演示更加真实可信。

**5. 数据库浏览器。** "在数据库部分，我们可以看到应用中的所有数据。" 这是最令开发者兴奋的功能之一——Sites 内置了数据库的管理界面，用户可以像使用数据库管理工具一样直观地浏览所有记录。Riley 展示了实际数据："你可以看到 Real Riley Brown 和 Callaway verified。他们有 avatar key（头像键），你可以看到他们的创建时间。" 在视频数据表中，"这里是所有的视频。这里有视频的标题文字（caption）、文件名（file name）、内容类型（content type）——这就是你的应用所有数据存储的地方。"

**视觉/结构信息描述**

设置面板包含多个区块/标签页：基本信息（名称/域名）、环境变量、Analytics、数据库。数据库浏览器展示两张数据表——创作者表（含 avatar key、创建时间）与视频表（含 caption、文件路径/名称、content type、创建时间等字段）。

**延伸思考**

环境变量 + 数据库浏览器这两个看似"高级"的功能，实际上是 OpenAI 的一个战略暗示：这个平台的目标用户并不只是零代码小白。通过逐步开放底层控制能力，OpenAI 正在把专业开发者也吸引到同一个平台上。未来，产品经理、设计师、开发者和业务人员可能在同一个 ChatGPT 工作环境中共同维护同一个站点——协作的边界正在消失。

### 十二、更进一步：Web MCP 与 $35,000 挑战赛

`[视频 结尾赞助部分]`

**核心观点**

**深度阐述**

那什么是 Web MCP？Riley 用了一段相对平实的话来解释："Web MCP 让你的网站暴露一些工具（tools），让 ChatGPT 和 Codex 可以发现并在实时的页面上直接使用，而你可以在旁边跟着并引导它。"

拆开来看：MCP（Model Context Protocol）是让 AI 模型与外部工具连接的开放协议；Web MCP 则把这个协议延伸到浏览器中的实时网页上。启用之后，你的网站就不再只是一堆"给人看的界面"，而是同时变成"AI 可以操作的工作台"——ChatGPT 或 Codex 能像一个人一样"看着"你的页面、发现页面上可用的功能（例如抓取按钮、搜索框、数据筛选器），并在你的口头引导下直接执行操作。想象一个场景：你在电话里指挥 Codex 在你的数据仪表盘上做筛选、排序、导出，而它真的能"看着"页面完成这些动作——这就是 Web MCP 的体验。

Riley 同步公布了相关活动信息："10 天 Web MCP 挑战赛正在举办，总奖金池为 $35,000 现金。" 参赛者可以构建一个全新的支持 Web MCP 的项目，也可以给一个已经创建的站点添加 Web MCP 支持。报名链接在视频描述中。

最后，Riley 致谢了 OpenAI 对本次视频的赞助，并像往常一样与观众道别："我会在下一个视频里见到你们。"

**延伸思考**

Web MCP 是 MCP 协议演进中顺应自然的一步——从"桌面工具"到"网站工具"。当 AI 可以在实时网页上发现并调用工具时，互联网上的每一个网站都可能变成 AI 的能力来源。这对"AI 原生应用"的定义将产生深远影响：未来的网站也许不仅要为用户设计界面，还要为 AI 设计"工具接口"。而 $35,000 的奖金池说明 OpenAI 正在有意识地加速这个生态的萌芽。

## 精华收获

回到 Riley 最核心的那句话：昨天他还在为三个 SaaS 工具支付数千美元，今天他用三段提示词构建了替代品。这个视频最大的价值不在于教会你某一个具体功能，而在于让你亲眼看到一种新的现实正在形成——**构建软件的权利正在经历大众化**。

以下是这篇深度解析提炼出的核心行动建议：

1. **用 @sites 开启你的第一个应用。** 打开 ChatGPT Work，输入"@sites 帮我构建一个……"（团队素材库、客户信息面板、项目进度看板……），托管、认证、数据库、存储全部自动就位。

2. **把产品需求写成自然语言提示词。** 参考 Riley 的结构：前端样式（全白、手机边框）→ 权限模型（团队成员登录）→ 数据输入方式（手动上传 + 智能体上传）→ 数据模型（视频 + 统计 + 字幕）→ 外部能力（技能/API）→ 种子数据与功能（初始化内容 + 下载按钮）。AI 会把这份"需求文档"直接变成可用的应用。

3. **用注释迭代，而不是重新生成。** 在浏览器中打开你的站点，进入 annotate 模式，直接点击界面元素并写下修改意见——"顶部栏太高"、"按钮不好看"、"改成全屏"——AI 会精确修改并自动重新部署。这是目前最接近"即时开发"的体验。

4. **用 Skills 接入外部 API。** 找到你需要的服务（如 Scrape Creators），获取 API key，让 AI 为你创建技能。从此抓取数据就像聊天一样简单——而 Sites 解决最难的"展示"问题。

5. **善用站点设置后台。** 在设置中管理域名、修改名称、配置环境变量（API 密钥的正确存放之处）、查看分析数据和浏览数据库——平台的底层控制力远比表面看起来更强大。

6. **改变信息传递的思维。** 下次给团队成员发信息前，停下来问自己：**"我能发送的最好的界面是什么？"** 也许一个两分钟构建的迷你应用，比一份 50 页的文档更有力量。

7. **尝试 Web MCP。** 更新到最新版 ChatGPT 桌面应用，让你的站点变成 AI 可以实时操作的"工具台"——这可能是下一波 AI 应用创新的入口。
