## 核心思路：像给新员工提供条件一样设置 Claude Code

我对于 AI 员工及其设置方式的思考其实非常简单：如果你想让 Claude Code 表现得像一名员工，你就要给它一个新人加入公司时你会提供的那些基本条件。这很合理，对吧？

它需要以下这些基本要素：

- **工作区（Workspace）**：在这里叫代码仓库（repo），产品文件存放的地方，也是 Claude 真正执行工作的地方。
- **记忆（Memory）**：本质上就是放入项目的上下文，让 Claude 理解你在构建什么、客户是谁、当下什么最重要、好的工作成果什么样，以及你已经吸取了哪些教训，避免重复犯错。
- **简报（Brief）**：在 Claude 开始修改之前，先让它通过**计划模式（Plan Mode）**理解任务，先查看上下文、思考方案，再动手。
- **任务单（Ticket）**：一个清晰的小型任务分配，有可见的完成终点，而不是模糊的指令。
- **眼睛（Eyes）**：让 Claude 不仅能编辑文件，还能打开应用、点击流程、检查真实用户体验。
- **审查（Review）**：让改动在重要内容上线之前，真正按照你的标准接受检查。
- **日程（Schedule）**：通过**例行程序（Routines）**给 Claude 分配循环工作，如晨间简报、每周问题审查、拉取请求审查。
- **权限（Permissions）**：让 Claude 知道哪些事可以自主完成，哪些事必须征求许可，守住高风险决策。

这就是整体地图：**工作区、记忆、任务单、眼睛、审查、日程和权限**。如果你能做到这些，Claude Code 就不只是一次性的聊天工具，而更像你公司的**运营层**。

## 第一部分：搭建工作区（Workspace）

### 选择项目文件夹

在 Claude Desktop 中，进入 **Claude Code** 板块。我个人更喜欢在桌面应用中使用它，比在终端里用要轻松得多，所以今天就用桌面应用。你需要选择一个项目文件夹，也就是 Claude 实际运行的地方。

为了演示，我们来看一个我从 **ideabrows.com** 上发现的点子：一个面向**医疗水疗中心（med spa）**的**错失线索响应器**。大致场景是：有人填写了表单、给商家发了私信、在非工作时间打来电话询问价格，但商家回复太慢——这就是一个能产生现金流的软件业务机会。

### 推荐的项目结构

如果要创建一个应用，我想要的目录结构是：

- `/app`：产品代码所在地；
- `/context`：业务上下文，也就是“商业大脑”；
- `/customers`：销售电话记录、支持备注、客户异议和客户语言；
- `/spec`：产品规格；
- `/demo`：演示流程、Loom 录制脚本、截图等；
- `/routines`：重复性任务的提示词。

根目录还需要三个 MD 文件，它们就是你的**操作手册**：

- `CLAUDE.md`：告诉 Claude 如何工作；
- `roadmap.md`：告诉 Claude 当下什么最重要；
- `review.md`：告诉 Claude 在交付前如何判断工作质量。

**第一个要点：当项目能自我解释时，Claude 会变得有用得多。**

### 一键创建工作区的提示词

具体如何设置？最佳方式是用下面这个提示词：

> 帮我把这个代码仓库设置成一个 AI 员工工作区（Help me set up this repo as an AI employee workspace）。

然后加上：创建或更新 `CLAUDE.md`、`roadmap.md`、`review.md`、`/context`、`/customers`、`/spec`、`/demo`、`/routines`。

接着提供业务上下文：

- **产品**：面向医疗水疗中心的错失线索响应器；
- **买家**：医疗水疗中心的老板/经营者；
- **痛点**：团队回复太晚，入站线索变冷；
- **承诺**：赶在客户预约别家之前，回复每一个错失的线索；
- **当前目标**：构建一个简单的落地页和演示流程。

再补上一句很有帮助的话：**“如果存在会实质改变设置的缺失上下文，请先问我，并保持第一版简单。”**

Claude 会先问你几个“高杠杆”问题，再以合理默认值填充其余内容，并保持 V1 简单。它还会说：**“我会先问你几个高杠杆的问题，你的回答会影响我如何构建演示流程和客户规格文件夹，其余内容我会用合理的默认值填充，并保持 V1 简单。”** 你快速回答后，它会把你整个工作区设置好。这样你是在为自己铺路——如果没有优化的 MD 文件和目录结构，Claude Code 之后会这里磕一下、那里绊一下。

## 第二部分：优化大脑——CLAUDE.md、roadmap.md、review.md

工作区脚手架搭建完成后，还需要进一步优化三个核心文件。

### 优化 CLAUDE.md：定义工作风格与质量标准

要让它更像 AI 员工，你必须给它一种**工作风格**。就像你雇了一个员工，你会说：“我希望你这样工作。”

你可以加入这些规则：

- 我希望小而可审查的改动；
- 当任务影响产品行为时，编辑前先解释计划；
- 保持改动聚焦；
- 沿用现有代码风格；
- 改动后运行相关检查；
- 总结改了什么、测试了什么、哪些需要人工审查。

同时加入**业务上下文**：这个产品帮助医疗水疗中心更快响应错失的入站线索；买家是老板/经营者。还要给出**承诺**和**质量门槛**：

- 落地页应在 5 秒内清晰易懂；
- 演示流程应在桌面端和移动端都能运行；
- 要使用客户的具体语言。

这样做是在指导它、辅导它，让它知道你的工作方式，以及你眼中的成功长什么样。

### 优化 roadmap.md：定义本周目标与范围

接下来，告诉 Claude 这周要专注什么。例如：

> 当前目标是构建一个简单的演示，展示医疗水疗中心如何挽回错失线索。本周专注：落地页、候补名单表单、演示流程、向 10 位医疗水疗中心老板发送 Loom 录屏。

同时要明确**不在范围内**的内容：

- 支付；
- CRM 集成；
- 管理后台；
- 多用户权限。

这样做的目的是希望它专注于 MVP，并超出你的预期。

### 优化 review.md：建立你的审查标准

`review.md` 承载着你的标准。以下是一份审查清单：

- 改动是否符合当前路线图？
- 改动是否足够小、便于审查？
- 主要用户流程是否仍然可用？
- 是否存在移动端布局问题？
- 表单错误是否正确处理？
- 是否存在支付或生产数据风险？
- 是否增加了不必要的复杂性？

针对落地页，再加几条：

- 首次访问者能否在 5 秒内理解这个产品/主张？
- CTA 是否可见？
- 文案是否针对买家？
- 页面是否使用了客户会实际使用的措辞？

你在让 Claude 知道：**你不能直接交付垃圾，我们不能发布“AI 糟粕”。** 像 Opus 4.8 或 Fable 5 这样的模型，只要有正确的 MD 文件、正确的结构和正确的大脑，就能做得非常好，但它确实需要这些护栏。

## 第三部分：通过 Plan Mode 提供简报（Brief）

当你给一个真人一项重要任务时，你不会直接把任务扔过去，对吧？你会先沟通，解释清楚目标、重点、限制和验收标准。这就是**计划模式（Plan Mode）**的用途。

Plan Mode 让 Claude 环顾项目、阅读上下文、思考任务，并在修改文件之前向你展示方法。例如，我想请 Claude 在落地页上添加一个候补名单表单。我不会只说“添加一个候补名单表单”，而是给它一份真正的简报：

> 使用计划模式。我想在落地页上添加一个候补名单表单。首先检查当前应用、`CLAUDE.md`、`roadmap.md` 和 `review.md`。然后告诉我：需要修改的文件、最小而干净的实现、用户体验、风险、我们如何验证它，以及你打算在第一版中故意省略什么。在编辑前等待我的批准。

**为什么这个指令很重要？** 因为它在收集上下文，而收集上下文是获得最高质量输出的关键。

这个计划可能不完美，但你可以根据它给出反馈，比如“只保留前端，因为这只是个演示”，或者“连接 Supabase，因为我想要真实提交”，或者“表单不够简单，只要姓名、邮箱、公司就好”，也可以说“先别碰支付或数据库”。

Claude 会给出完整的计划：需要修改的文件、最小而干净的实现（比如 **Next.js + TypeScript**）、用户体验、一句话承诺、风险（如垃圾信息与滥用）等。然后你可以**接受、拒绝或修改**。

总的来说，任何时候做有意义的产品工作，你都会想先做计划。这就像那句老话：**“量两次，剪一次”**。

## 第四部分：清晰的任务单（Ticket）

Claude Code 很擅长执行，但它需要知道“完成”是什么样。这就是任务单：**一个小而清晰、带有可见终点线的任务分配**。

如果你在管理一个人，你不会说“嘿，去改进一下产品”，而是会说一个具体任务，例如：

> 在落地页上添加一个候补名单表单。它应该收集姓名、邮箱和公司，提交后显示一个简单的成功消息，并且与当前品牌形象保持一致。

这就是一份好任务单：它给了 Claude 工作内容、范围、预期用户体验和边界。

更多好任务单的例子：

- 使用现有设计系统创建一个定价页，并与首页保持一致；
- 修复邮箱验证后跳转重定向的 bug；
- 把这五个客户异议转成一个更锐利的落地页板块。

模糊的任务单（如“把应用做得更好”“让这个更有传播性”“加上 AI”“构建整个东西”）会让 Claude 去猜什么重要。一旦它开始猜，你就不再是管理工作，而是在清理工作。**Fable 5** 在猜测意图方面做得非常出色，但清晰的 ticket 依然是获得最佳效果的关键。

### 保持任务单小，让 diff 可管理

批准计划后，可以这样保持 Claude 专注：

> 将改进后的计划作为一项聚焦的变更来实现。保持改动足够小，以便我在差异视图（diff view）中审查。编辑后运行相关检查。在桌面预览中打开应用。总结改了什么，告诉我你测试了什么，以及还有什么需要人工审查。

**什么是 diff？** 简单说，它展示更改前后的差异。Claude 编辑、复制、添加、删除文件时，diff 会精确展示发生了什么变化。Claude 桌面应用的 diff 视图非常可视化：你可以点击查看变更文件、留下评论、请 Claude 修正任何看起来不对的地方。

规则很简单：**一次给 Claude 一个清晰的任务单——一个任务、一条终点线、一个可审查的变更。**

## 第五部分：给 Claude 一双眼睛（Eyes）

这是 Claude Code 真正开始像“运营者”的地方。所谓“眼睛”，不只是可视化预览，而是 Claude 在构建完成后**检查自己工作**的能力。

好员工做任务后会检查任务：打开产品、点击流程、运行测试、查找错误、检查控制台、寻找边界情况，并问：“这对客户真的有用吗？”这就是我希望与 Claude Code 建立的循环：**构建、运行、使用、测试、改进**。

### 桌面预览的价值

桌面预览尤其重要，因为产品工作高度依赖视觉：

- 落地页可能加载出来了，但仍然让人困惑；
- 表单可能可以提交，但体验仍然别扭；
- 按钮可能在页面上，但很难被注意到；
- 标题可能解释了产品，但没有切中买家痛点。

Claude 还能做更多：运行测试套件、检查控制台日志、检查网络错误、验证表单是否真正提交数据。

### 让 Claude 检查实际体验

在 Claude 构建完候补名单表单后，可以这样提示：

> 启动应用并检查候补名单流程。在桌面预览中打开落地页。从首次看到它的医疗水疗中心老板的角度检查体验。然后验证实现情况。告诉我：买家在前 5 秒内理解了什么？哪些地方让人困惑或缺乏信任感？候补名单表单是否正常工作？提交后会发生什么？最后，做一次聚焦的修改，改进影响力最大的问题。

实际执行时，Claude 会测试空提交、验证空状态、检查成功状态、后端记录、控制台和网络错误。它甚至使用了四个工具来读取页面和操作系统。最终它发现问题：**页面要求陌生的医疗水疗中心老板交出邮箱，却没有说明候补名单是什么，或者他们是否会收到垃圾邮件。** 它给出的优化是：**在 CTA 处添加预期管理微文案。**

“眼睛”被低估了。一旦你把它纳入流程，你会获得更好的 QA，最终得到更好的产品。

## 第六部分：审查机制（Review）

当 Claude 能快速构建东西时，瓶颈就转移到了判断上：它是否解决了正确的问题？修改了正确的文件吗？有没有制造奇怪的边界情况？产品对客户是否更清晰？

审查可以分两层。

### 第一层：自己的阅读

打开 Claude Desktop 中的 **diff 视图**，查看 Claude 接触过的文件，问自己几个问题：

- 这符合任务单吗？
- 这符合计划吗？
- 有什么令人意外的地方吗？

意外的改动通常就是风险所在。如果 Claude 本应添加候补名单表单，却突然改了权限、路由和数据库，你要立刻知道。

### 第二层：让 Claude 对照你的标准审查

使用之前创建好的 `review.md` 作为标准，可以这样提示：

> 以 `review.md` 为标准。审查当前变更，找出生产问题、损坏的边界情况和令人困惑的用户流程。将问题分为“必须修复”（must fix）、“应该修复”（should fix）和“可以上线”（okay to ship）。重点关注 bug、用户困惑、安全风险、不必要的复杂性、超出任务单范围的文件变更，以及任何违反路线图的内容。

Claude 会输出“必须修复 / 应该修复 / 可以上线”的分类清单，并问你是否现在修复某些问题。这个“必须 / 应该 / 可以”的格式非常有用。

此外，日常审查可以用 `/review` 命令；如果涉及高风险变更（如身份验证、支付等），可以用 `/ultra review`——它会为代码仓库启动一个远程 ultra review 会话，适合在发布生产环境之前使用。

## 第七部分：日程安排（Schedule）——让 AI 员工主动工作

到目前为止，Claude 都在你坐着时帮助你工作。但一个真正的员工还有**重复性责任**：查看客户笔记、关注新问题、整理待办事项。这些工作看似琐碎，却正是推动公司前进的动力。

因此，你可以用 Claude Code 的 **Routines（例行程序）** 创建定时任务。

### 晨间简报

第一个建议的 routine 提示词：

> 每个工作日的早上 7 点，阅读 `/customers/context`。如果连接了 GitHub，打开 GitHub issues。然后创建或更新 `/context/morning-brief.md`，包含：来自最新笔记的客户最大痛点、一个产品风险、一个今天推荐的构建任务、一个我今天应该问客户的问题。不要编辑生产代码，不要打开拉取请求，保持 500 字以内。

这个任务有用且可控：不改变产品、不碰生产环境、不构建随机功能，只是阅读业务、查看当前工作，给你一个更锐利的每日出发点。设置只需要几秒钟。

### 每周运营审查

更进一步的 routine：

> 每周五下午 3 点，审查开放的问题和最近的客户笔记，将相关问题分组或识别重复项。为本周提出一个最高杠杆的修复建议，并将摘要发布到 `/context/weekly-ops.md`。不要编辑代码。

这样你不会让问题堆积起来。Claude 会帮你看到模式，比如一些你没注意到的客户投诉或共性的入门问题，它就像一位**幕僚长**，帮你确定每周优先级。

### 拉取请求自动审查循环

最后添加一个循环：

> 当拉取请求打开时，使用 `review.md` 审查它。只对可能产生 bug、破坏用户流程、安全问题或令人困惑行为的评论留言。然后发布简短摘要：哪些看起来不错，哪些需要注意，以及是否已准备好人工审查。

完成这些后，每天早上 Claude Code 都会告诉你什么重要，每个 PR 都会对照你的标准被检查。这就是“夜班”概念：工作不断被整理，反馈被总结，风险被浮出水面，下一步任务越来越清晰。

## 第八部分：并行代理（Parallel Agents）

你不想一次只做一件事。梦想是让多个代理同时做多件事——相当于复制出 5 个、10 个、15 个、20 个员工。**这是可能的。**

在 Claude Desktop 中，代码标签页可以运行**独立会话**。每个会话都有自己的上下文和一组变更，并借助**工作树隔离（work tree isolation）**，这些变更可以保持分离，不会混在一起。

### 示例：三个并行任务

想象早上你想推进三件事：

1. **技术任务**：邮箱验证后的跳转重定向坏了，需要修复；
2. **产品任务**：落地页 hero 区域太模糊，需要让医疗水疗中心老板在 5 秒内理解价值；
3. **销售任务**：把一堆客户笔记变成一个更锐利的演示脚本。

这三个是完全不同的工作：一个是调试，一个是产品与文案，一个是销售赋能。在旧工作流里，你只能一个接一个做；在 AI 员工工作流里，你可以给每个任务一个独立的 Claude 会话，使用相同的产品上下文，产出非常清晰的交付物：

- Bug 会话返回：根本原因、更改的文件、运行过的检查、以及你在 diff 中应该看什么；
- 落地页会话返回：hero 的前后对比、使用的客户语言、预览中发生了什么变化、为什么新版本更清晰；
- 演示会话返回：它提取的客户笔记、试图处理的异议、以及你在录制前应该审查什么。

### 示例提示词

**Bug 会话：**

> 处理邮箱验证后的跳转重定向 bug。在提出修复之前，先使用项目上下文文件。先解释你认为的 bug 原因以及需要检查哪些文件。在我批准计划后，实施最小而干净的修复。完成后，告诉我根本原因、更改的文件、运行过的检查或测试、你在 diff 中应该审查什么，以及任何让你觉得不确定的地方。

**Hero 改进会话：**

> 改进落地页 hero，让医疗水疗中心老板在 5 秒内理解价值。使用 `CLAUDE.md`、`roadmap.md`、`review.md` 和最新的客户笔记。把改动集中在 hero 区域，除非有小的辅助性改动是必要的。完成后给我前后对比等。

**销售脚本会话：**

> 阅读最新的客户笔记，把它们变成一个简短的演示脚本——面向错失线索响应器。尽可能使用客户的原话。演示应展示痛点、产品时刻和回报。完成后给我演示脚本等。

核心要点是：**给每个会话一个清晰的任务、相同的项目上下文和一个具体的交接方式。** 你醒来后挑选三个最有用的工作流，让 Claude 以你真正能审查的方式推进每一个，而不是收获一大堆需要花时间理顺的混杂改动。

## 第九部分：权限管理（Permissions）

权限是真正有风险的部分。我对待权限的方式就像对待**授权**：有些事 Claude 可以自由做，有些事应该先问，有些事必须留在人手里。

### 三类操作

**安全操作（safe actions）：**

- 读取文件；
- 检查代码库；
- 提出计划；
- 运行本地测试；
- 编辑小功能分支；
- 更新文档；
- 创建草稿拉取请求。

**先询问的操作（ask first actions）：**

- 安装依赖；
- 修改数据库迁移；
- 触碰身份验证；
- 修改支付逻辑；
- 删除文件。

**人工专属操作（human-owned actions）：**

- 生产部署；
- 客户数据决策；
- 计费决策；
- 安全敏感变更。

即使你有 AI 员工，高风险的事情仍然需要人类主导。

### 设置权限模式

在 Claude Desktop 中，你可以根据想要的控制程度选择**权限模式**。建议从保守开始：对较大更改使用计划模式，在学习阶段使用人工审查。随着代码仓库大脑、审查清单和任务范围越来越强，再逐步让 Claude 跑得更快。

这就是管理模式：**给 AI 工作空间和边界，而不是直接“YOLO 模式”**——那太冒险了。把权限作为策略来思考，才能真正规模化你的 AI 员工团队。

## 第十部分：技能、连接器与钩子（Skills, Connectors, and Hooks）

这是最后一块，它会让 Claude Code 从通用工具变成专属于你公司的定制系统。

### 技能（Skills）

Skill 本质上是一种**可重复执行的工作方式**。如果你发现自己反复输入同样的提示词，那就值得把它变成一个 skill。

例如，在医疗水疗中心项目里可以做这些 skill：

- **落地页拆解技能**：每次使用时，Claude 像医疗水疗中心老板一样审视页面，检查 5 秒清晰度、找到模糊文案、寻找缺失的信任信号、检查 CTA，并建议一个聚焦改进。
- **客户笔记技能**：读取最新通话或支持记录，提取客户原话、反复出现的异议和购买触发因素。这让 Claude 不再只基于你的观点，而是基于真实客户语言来构建产品，也可以用于写广告文案。
- **演示脚本技能**：获取最新产品状态和客户笔记，变成简短演示——痛点、产品时刻、回报。这类技能每周能节省数小时。

你可以自己创建 skill，也可以从技能市场下载。作者表示，如果大家感兴趣，可以进一步深入讲解不同的技能市场。

### 连接器（Connectors）

连接器给 Claude 提供更好的上下文：接入 **GitHub、Linear、Google Drive、Slack** 等工具。简单说，就是一个插件，让你连接各种外部系统。

### 钩子（Hooks）

钩子是围绕工作的**护栏**：

- Claude 编辑代码后运行格式化；
- PR 摘要之前运行测试；
- 变更上线之前运行关键检查。

把 skills、connectors、hooks 与路线图、审查标准、客户笔记、例行程序结合起来，Claude 就会变得非常贴合你的公司。这些东西就像业务的“能量增强器”，并能形成一种**护城河**——因为一个真正好的系统会让你从 Claude Code 获得持续高质量的产出。

## 7 天行动计划：从零搭建你的 AI 员工

你可以用 7 小时、70 分钟、7 天或 31 天来完成，取决于你的技术基础和时间。以下是以一周为视角的完整计划。

### 第一天：创建 repo 大脑

创建 `CLAUDE.md`、`roadmap.md`、`review.md`、`/context`、`/customers`。写下客户、问题、当前目标，以及“完成”的定义。

### 第二天：运行计划模式

选一个小型产品任务，让 Claude 在编辑前检查代码仓库。产出包括：一个计划、一份文件列表、风险清单、验证步骤。

### 第三天：构建一个可见的改进

候补名单表单、定价页、演示流程或入门 bug——选择一个**足够小、便于审查，又足够真实、可以展示给真实客户**的任务。

### 第四天：使用预览循环

让 Claude 在桌面预览中打开应用，点击流程，检查移动端，改进清晰度。

### 第五天：审查工作

打开 diff 视图，阅读前后变更；让 Claude 对照 `review.md` 审查；对重大改动使用 `/review` 流程。

### 第六天：发给 10 个人

把 Loom 录屏、演示或落地页发给一些可能在意的人，然后把他们的回复放进 `/customers` 仓库。

### 第七天：创建第一个例行程序

从晨间简报开始，让 Claude 阅读客户笔记和问题，推荐一个有用的构建任务。

### 最终闭环

完成七天计划后，你就拥有一个活跃的循环：

- 客户反馈 → `/customers`；
- 产品方向 → `roadmap.md`；
- 工作风格 → `CLAUDE.md`；
- 质量标准 → `review.md`；
- 小任务 → 计划模式；
- 变更 → 预览与审查；
- 重复性工作 → 定时例程。

**这就是 24/7 的 Claude Code 员工设置。** 一旦你这样理解它，Claude Code 就不再像一个聊天框。产品、客户反馈、文档、演示、审查、重复性工作，全都生活在这个运营循环中，并随着时间推移不断优化。
