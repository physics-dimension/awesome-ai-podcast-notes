### 什么是技能（Skill）？—— AI 的 SOP（标准作业程序） `[章节 0:00-2:30]`

**核心观点**
技能的本质是将你完成某项任务的标准作业流程（SOP）打包成一个 Markdown 文件，让 AI 能够精确复制你的工作方式，从而“一击即中”地输出你想要的结果，告别反复调校的“AI 生成垃圾”（Slop）时代。

**深度阐述**

Remy 在节目一开始，就用一个非常贴切的类比为我们揭开了技能的神秘面纱：**“技能本质上就是 AI 的 SOP”**。他通过对比有无技能两种方式下的提案生成过程，清晰地展示了技能的价值。

**没有技能的“旧世界”**：你需要开启一个新的对话窗口，要求 Claude 为你写一份提案。因为 AI 对你一无所知，它给出的第一版结果大概率不会让你满意。于是，你不得不开始一轮又一轮的“调教”：解释你喜欢的颜色、Logo 的摆放位置、价格应该放在底部而不是顶部…… 经过一番“拉锯战”，你终于得到了一份还算满意的提案。但问题的关键来了——**下周你再需要一份新提案时，一切都要重头再来**。AI 会忘掉你的所有偏好，除非你一直在同一个会话中，但这又会引发其他问题（如上下文过长、混乱等）。这是一个极度低效、且令人沮丧的循环。

**拥有技能的“新世界”**：技能允许你将自己完整的做事方式打包成一个 Markdown 文件，供 AI 阅读。它就像一个精确的操作手册。Remy 在现场进行了一个演示，他直接对 Claude 说：“为 Greg Isenberg 创建一个关于创业点子赞助通讯的提案。” 结果如何？AI 调取了他之前构建好的“提案生成技能”，瞬间生成了一份完全符合他要求的品牌化提案。Remy 强调：“我甚至不需要重新解释任何一件事。”

这正是技能的核心价值：**它把“反复调教”变成了“一次封装，永久使用”**。

为了让我们更好地理解 AI Agent 是如何使用这些技能的，Remy 给出了一个极具画面感的比喻。他让我们把 Agent 想象成“你雇佣过的最能干的员工”：
- **他的办公桌**：是他的电脑，连接着所有工具（如 MCP）。
- **他的指令文件**：是在执行每个任务前都会阅读的说明文件。
- **他的书架**：上面摆满了各种 SOP 书籍，这就是技能库。每本书的“书脊”上都有书名和简单描述，帮助他快速找到目标。当他确定需要哪本书时，就会把它抽出来，阅读里面的详细步骤，然后按部就班地执行任务。

一个精心打磨的技能，每周可以为你节省大约 2 个小时。当你把工作中的各类重复性任务都封装为技能时，积累起来的效率提升将是“游戏结束”级别的竞争优势。

> 重要原话: "skills are literally just SOPs for AI" （技能本质上就是 AI 的标准作业程序） `[章节 0:00-2:30]`

**个人感受**

Remy 在描述这个过程时，言语中充满了掌控感和兴奋。他强调自己“对事情有非常具体的要求”，一旦他找到了完美的做事方法，就会把它固化为一个技能，然后“每次都能一击即中”。这不仅仅是一种效率工具，更是一种将个人经验和智慧“实体化”、“资产化”的方式。这种“一次输入，终身受益”的爽快感，正是技能让人着迷的地方。

**延伸思考**

这个“书架”的类比非常精妙。它暗示了未来 AI Agent 的工作模式：Agent 不仅是一个执行者，更是一个知识库的管理者和应用者。个人和公司的核心竞争力，将越来越体现在你拥有多少个高质量、可执行的“SOP”上。这也引出了一个问题：如果技能是 AI 时代的“数字资产”，那么我们该如何建立个人和团队的资产库？

### 技能的困境：“微软 Word 时代”的 AI `[章节 2:30-4:30]`

**核心观点**
尽管技能极其强大，但当前我们正处于一个“AI 单机游戏”时代。每个人构建的技能都孤立地存在自己的电脑里，难以跨团队高效分享和管理，这严重阻碍了 AI 生产力的规模化。

**深度阐述**

在充分展示了技能的威力后，Remy 话锋一转，指出了当前面临的最大挑战：**AI 目前仍然非常“单机”（single player）**。

你的团队成员都在各自的电脑上使用 Claude 或 Codex，如果他们构建了一个出色的技能，这个技能就只是“活”在他们的机器上。“要正确地分享它是非常非常困难的，”Remy 说道。

为了让我们更好地理解这个困境，他引入了一个精彩的历史类比：**微软 Word 时代**。在个人电脑普及初期，你用 Word 创建了一个文档，它存储在你的电脑里。如果你想把它发给别人，你需要导出、发邮件，然后对方那里就有了一个副本。久而久之，你会有多个不同的副本在四处流传，根本没有一个“中央信息源”（Central Source of Truth）。如果修改了其中一个，其他副本并不会同步更新。

随后，Google Docs 解决了这个问题。它提供了一个云端文档，所有人都可以同时在里面协作，这就是一个中央信息源。

Remy 断言，**我们当前就处于“技能的微软 Word 时代”**。每个人都在创造有巨大价值的技能，但它们却像孤岛一样散落在个人电脑中。你构建了一个出色的技能，然后呢？你如何与团队分享？你如何确保他们使用的是最新版本？你如何管理团队的技能资产？

**个人感受**

Remy 对这个问题的描述非常精准：“如果你把技能分享给团队，而每个人都在改进它（你也确实应该不断改进），你最后会得到 10 份不同的副本，却没有一个中央信息源。” 这不仅仅是技术上的不便，更是一种智力资产的巨大浪费。这种混乱状态，会极大地限制一个团队从 AI 中获取的整体价值。

**延伸思考**

这个“Word 时代”的类比深刻地揭示了技术发展中的普适规律：任何生产力工具，都必然会从“个人效率”走向“协作效率”。就像单机游戏终将被网络游戏取代一样，单人使用的 AI 技能也必然会向团队共享、协作的模式演进。谁能更早地建立这种“多人游戏”的基础设施，谁就能在未来的竞争中占据先机。

### 破解之道：GitHub 仓库 + 插件（Plugin）架构 `[章节 4:30-7:00]`

**核心观点**
Remy 分享的解决方案是：将所有技能集中存放于一个 GitHub 仓库中，并将其打包为一个“插件”（Plugin），从而为团队技能建立一个拥有版本控制的“中央信息源”。

**深度阐述**

既然问题是缺乏中央信息源，那么解决思路就是创建一个中央信息源。Remy 找到的最佳方案，是利用程序员们最熟悉的工具：**GitHub**。

他首先解释了为什么是 GitHub：“你可以把 GitHub 想象成 Google Drive，只不过它是用来分享代码的。” 他用一个实际的仓库（repo）演示，这个仓库被命名为 “团队技能”（Team Skills），里面的技能按照部门（Department）进行分类，例如品牌（Brand）、内容（Content）、市场（Marketing）等。这样一来，你立刻就有了一个存放公司所有技能的、唯一的中央信息源。

但仅仅把技能放在一个共享文件夹里还不够。难点在于，如何让团队成员的 Claude Code 或 Codex 轻松地访问到这个仓库？Remy 的答案是：**把它制作成一个插件（Plugin）**。

这是整个环节中最关键的概念。Remy 解释道：“插件实际上就是技能（Skills）、MCP 和钩子（Hooks）的捆绑包。” 你可以构建一个只包含技能的插件，也可以构建一个包含上述任意组合的插件。而 Remy 的解决方案，就是一个将技能“打包”起来的插件。

**为非技术背景人士的“祛魅”**：

Greg 敏锐地察觉到，很多人听到“代码仓库”和“插件”会本能地感到恐惧，认为这需要很高的技术门槛。Remy 对此进行了“祛魅”：作为一个完全没有开发背景的人，他强调，**只要你能理解“GitHub 就是一个存储文件的云盘”，以及“插件是让 AI 访问这些文件的一种方式”，你就掌握了全部所需的背景知识**。

为了让整个过程简单到任何人都可以操作，Remy 特意准备了一个提示词（Prompt），这个提示词可以在视频结束后提供给观众，观众可以直接将其交给 Claude，让 AI 自动完成将现有技能文件夹转化为符合要求的 GitHub 仓库和插件配置的全部工作。这意味着，你甚至不需要自己编写任何一行 JSON 配置文件。

> 重要原话: "as long as you can understand that GitHub is just a place to store your files on the cloud and then a plugin is just a way for Claude to access them, that's pretty much all you need to know." （只要你能理解 GitHub 只是云端存放文件的地方，插件只是让 Claude 访问这些文件的方式，那你需要知道的就是这么多了。） `[章节 4:30-5:15]`

**个人感受**

这个部分极大地降低了听众的心理门槛。它告诉我们，在 AI 时代，很多看似“极客”的操作，其核心思想其实非常简单。我们不必被工具的表面复杂性吓倒，而是应该专注于理解其背后的逻辑，并善用 AI 来为我们处理那些枯燥的技术细节。

**延伸思考**

Remy 用 AI 来构建 AI 工具链的方法，本身就是一种“技能”的应用。他不仅是在分享一个解决方案，更是在示范一种“元技能”——如何利用 AI 去解决复杂的工程问题。这种“让 AI 构建 AI 基础设施”的思维模式，将是未来每个知识工作者的核心能力之一。

### 安装插件与赋予团队力量：从仓库到个人终端 `[章节 7:00-9:30]`

**核心观点**
Remy 通过现场演示，展示了团队成员如何通过几个简单的终端命令安装插件，并启动“自动更新”功能，从而确保每个人都能即时获得最新的团队技能。

**深度阐述**

Remy 随即打开了他的终端，进行了一场快速且直观的现场演示，展示了团队成员安装这一系列技能的全部过程。

**步骤一：安装插件**。在 Claude Code 中输入 `/plugin`，会出现一个简单的管理菜单。点击“市场（Marketplaces）”，只需添加你 GitHub 仓库的链接，你的“团队技能”就会出现在列表中。这个过程被 Remy 比喻为“应用商店”：**市场（Marketplace）就像应用商店，插件（Plugin）就像里面的 App**。

**步骤二：按需分配**。由于技能按部门进行了分类，团队可以根据角色安装不同的插件。例如，他不一定希望负责文案的同事安装财务（Finance）部门的技能插件。这种“按需分配”的机制，为公司内的 AI 权限管理提供了极大的便利。他展示了一个例子：点击“通讯（Newsletter）”插件，里面会包含多个技能，如“每周研究”、“引言撰写”、“故事生成”和“TLDR”等。

**步骤三：开启自动更新（Auto-Update）**。这是整个流程中至关重要的一环。Remy 强调，所有安装者都必须开启“自动更新”。这一功能保证了当技能在中央仓库被修改时，所有团队成员的本地 AI 环境都能同步更新，从而彻底解决了之前“文件副本无法同步”的噩梦。

**跨平台兼容**：

当 Greg 询问这种方法是否仅限于 Claude Code 时，Remy 给出了更为振奋人心的答案。他本人已经分别在 Claude Code 和 Codex 中测试并使用了这个插件体系，效果完全一致，可以即插即用。他在 Codex 中演示了同样的操作，可以轻松看到并调用这些团队技能。这意味着，团队中可以有人使用 Claude，有人使用 Codex，都能无差别地共享同一个知识库，这极大地增加了系统的实用性和灵活性。

**技术背后的简单性**：

Remy 坦诚，他完全不知道这些 JSON 文件是如何让 AI 将这些技能识别为插件的具体技术原理，但他表示：“我不需要知道。我只是让 Claude 帮我设置好了。” 这再次印证了他“人控逻辑，AI 控技术”的实践哲学。

> 重要原话: "The marketplace is kind of like the app store you're installing. And then the plugins themselves are kind of like the apps." （市场就像是你在安装的应用商店，而插件本身就类似于应用。） `[章节 8:00-8:30]`

**个人感受**

观看整个演示过程，你会感受到一种难以置信的流畅感。从打开终端到技能安装完毕，整个过程不到一分钟。这标志着 AI 技能的分享已经从“技术人员的专属技能”演变成“任何团队成员都可以轻松完成的一步操作”。

**延伸思考**

这个系统最强大的地方在于**“自动更新”和“按角色分配”**。它已经初步具备了企业级软件管理的特征：集中控制、版本管理、权限分配。这不仅仅是分享技能的方案，更是未来企业构建内部 AI 能力平台的蓝图。我们正在见证 AI 基础设施从“个人计算机时代”向“企业内部 IT 系统时代”的转变。

### 团队与个人技能库的分离：Remy Skills 的私人沙盒 `[章节 9:30-11:30]`

**核心观点**
在团队共享技能之外，Remy 还维护着一个独立的、仅属于自己的“个人技能仓库”（Remy Skills），用于存放不适合团队共享的个人偏好、实验性技能和云端 Agent 所需的技能。

**深度阐述**

共享是主题，但 Remy 也展示了系统中同样重要的另一面：**区分“团队资产”和“个人资产”**。

他分享了自己会维护另一个名为 “Remy Skills” 的单独仓库。在这个仓库里，存放着两类内容：
1.  **纯粹的个人技能**：这些技能过于个性化，无法在团队中复制。例如，他的“收件箱分类技能”（Inbox Triage Skill），这个技能教会 Claude 如何处理他的邮件；以及他的“晨间简报”（Morning Brief），这完全基于他的个人 App 使用习惯。这些技能就像牙刷，每个人都需要自己的那一支。
2.  **实验性/待定技能**：从互联网上下载的、还在尝试阶段的新技能。它们尚未经过实战检验，不适合大规模部署到团队，这里就像一个“个人沙盒”。

**为什么要这么做？**

当 Greg 追问，如果不对团队分享，为什么还要用 GitHub 仓库来管理这些个人技能？难道本地管理还不够吗？Remy 给出了几个深刻的理由：
- **单一信息源**：他喜欢将所有东西都放在一个地方。
- **云端访问**：这是最关键的一点。他现在会在云服务器（VPS）上运行自动化代理（如 Hermes 代理）。这些云端代理需要能够访问他的技能，而不是依赖他本地电脑的文件系统。将技能放在云端仓库，意味着他的 AI 代理可以在任何地方调用相同的知识库，而不仅仅是在他自己的电脑前。
- **版本控制**：拥有 Git 的历史记录，方便回溯和比较改动。
- **灾难备份**：这与接下来他的一个惨痛故事直接相关。

> 重要原话: "I'd rather them be somewhere on the cloud. So if I'm running like a Hermes agent on a VPS or some sort of cloud agents, they have a method to access my skills rather than them sit like all locally on my file system." （我宁愿把它们放在云端。如果我在 VPS 或某种云代理上运行 Hermes，它们就有办法访问我的技能，而不是让技能只保存在我的本地文件系统里。） `[章节 10:00-10:30]`

**个人感受**

Greg 在听完这个做法后，感慨道：“我是说，这也很有道理，比如你本地电脑上的东西可能会被损坏，而且它现在在云端了。” 这句话引出了 Remy 一段至今仍让他心有余悸的经历。

**延伸思考**

Remy 的“个人技能库”模式揭示了一种极为超前的工作哲学：**技能是你的知识资产的备份和延伸**。它们不应该被锁在某个物理设备里，而应该储存在可访问、可复用、可进化的云基础设施中。这也回答了，为什么即使不分享，将技能放在云端仓库依然是更优越的管理方式。

**深度阐述**

Remy 的经历完美地证明了将技能放入 Git 仓库的必要性。在这个系统下，即使本地文件再次出现问题，云端仓库的版本控制也能确保所有技能的安全性。

**个人感受**

Remy 对这个故事的讲述带着一种真实的后怕和懊悔，他反思道：“不备份真的太愚蠢了。” 这种坦诚的分享拉近了他与观众的距离。在这样的高速迭代时代，这种“翻车”经历几乎是每个人都会遇到的。它在提醒我们，效率不仅是“快”，更是“稳”和“可靠”。

**延伸思考**

这个故事颇具警示意味：我们将越来越多的“思考过程”和“工作方法”交给了 AI，那么这些“数字大脑”的安全性就必须得到最高级别的重视。将技能视为公司或个人的核心知识产权资产，并为其配备相应的管理、备份和分发基础设施，是每个重度 AI 用户都必须补上的重要一课。也许，“100% 云化 + 版本控制”的模式，就是对 AI 时代数据安全焦虑的一种终极解法。

### 技能设计哲学：厚技能（Thick Skills）与薄代理（Thin Agents） `[章节 15:00-17:30]`

**核心观点**
Remy 奉行“厚技能、薄代理”的设计哲学：保持 AI 代理的指令文件精简，而将所有的专业知识、背景和步骤全部封装在技能中，让技能成为主要的“策略外挂”。

**深度阐述**

面对 Greg 关于“如何决定创建多少技能”的疑问，Remy 给出了他清晰的个人框架。

**“只要不涉及物理劳动，就能自动化”**。Remy 的核心理念是，只要不是“洗盘子”这类物理性任务，公司中的任何线上流程都可以通过一个出色的技能或者一系列技能链条实现自动化。在他看来，任何他每天重复执行的任务，都值得“技能化”，因为“我不想再碰它了”。

**关于技能链的设计原则**：当一个流程较为复杂时，他会将其拆分为多个技能并串联运行（如“标题-缩略图-描述”的 YouTube 发布流程）。但这个拆分的原则并不是盲目的，而是基于一个简单的判断：“如果在以后，我会有单独运行其中某个子流程的需求（比如我只想要一个缩略图），那么我就会把它做成一个技能链。”

**“边缘案例”的反思**：Greg 询问了如何利用记忆功能来自动化创建技能的过程。Remy 分享了一个他最近加入所有技能文件的“自我改进循环”提示词。这个提示词要求 AI 在每次技能运行结束时，反思“是否有任何步骤失败或需要变通？用户是否纠正或拒绝了任何有意义的输出？你是否发现未来运行可能需要的任何东西？”然后只提出有意义的改动建议。在每次技能运行后，AI 通常会给出一到两条小的改进建议，Remy 只需简短的“批准”或“拒绝”，这个“自我改进循环”就让技能在一次次使用中变得越来越强大，这被他称为“超级好用”的功能。

**“厚技能，薄代理”**：Remy 引用了他朋友 Russ Mike 的理念，强调了他的核心哲学：**“薄代理，厚技能”（Thin Agents, Thick Skills）**。这意味着要尽量保持 AI 代理（即其核心指令文件）的简洁和瘦身，而将所有的专业知识、详细的步骤和上下文都填充到技能里面，使技能变得“厚实”。因为技能承担了绝大部分的策略和指导，代理只需要专注于执行。Remy 相信，在这种架构下，即使是新手，只要能执行技能，也可以完成任务，个人能力对任务质量的制约会大幅降低。

> 重要原话: "I'm big like same as Russ Mike says that I'm like thin agents, thick skills." （我非常认同 Russ Mike 所说的，薄代理，厚技能。） `[章节 16:30-17:00]`

**个人感受**

这段“厚技能、薄代理”的哲学是整期节目智力密度最高的地方。它点明了技能系统的本质：**将“人”的隐性经验（知道什么是好的）显性化，并以标准化的格式注入到 AI 的执行管线中**。它不是简单地把 AI 当作“自动填充工具”，而是把 AI 当作一个有能力执行你的“方法论”的“超级执行者”。

**延伸思考**

“决策下放到技能”这一概念，深刻地改变了 AI 应用的设计架构。在传统架构中，策略写在主提示词里，就像公司的规章制度都写在员工手册里，管理僵化且低效。“厚技能”则更像现代组织中的“工作流程”和“SOP 系统”，每个技能都是一个独立的、可维护和可优化的自动化模块。这也意味着，在未来的 AI 时代，团队里的竞争力，将不再仅仅依赖于个人“写提示词”的技巧，而更多地取决于个人和团队**构建高质量、可落地“技能”的能力**。

### 什么是技能（Skill）？—— AI 的 SOP（标准作业程序） `[章节 0:00-2:30]`

**核心观点**
技能的本质是将你完成某项任务的标准作业流程（SOP）打包成一个 Markdown 文件，让 AI 能够精确复制你的工作方式，从而"一击即中"地输出你想要的结果，告别反复调校的"AI 生成垃圾"（Slop）时代。

**深度阐述**

Remy 在节目一开始，就用一个非常贴切的类比为我们揭开了技能的神秘面纱：**"技能本质上就是 AI 的 SOP"**。他通过对比有无技能两种方式下的提案生成过程，清晰地展示了技能的价值。

**没有技能的"旧世界"**：你需要开启一个新的对话窗口，要求 Claude 为你写一份提案。因为 AI 对你一无所知，它给出的第一版结果大概率不会让你满意。于是，你不得不开始一轮又一轮的"调教"：解释你喜欢的颜色、Logo 的摆放位置、价格应该放在底部而不是顶部…… 经过一番"拉锯战"，你终于得到了一份还算满意的提案。但问题的关键来了——**下周你再需要一份新提案时，一切都要重头再来**。AI 会忘掉你的所有偏好，除非你一直在同一个会话中，但这又会引发其他问题（如上下文过长、混乱等）。这是一个极度低效、且令人沮丧的循环。

**拥有技能的"新世界"**：技能允许你将自己完整的做事方式打包成一个 Markdown 文件，供 AI 阅读。它就像一个精确的操作手册。Remy 在现场进行了一个演示，他直接对 Claude 说："为 Greg Isenberg 创建一个关于创业点子赞助通讯的提案。" 结果如何？AI 调取了他之前构建好的"提案生成技能"，瞬间生成了一份完全符合他要求的品牌化提案。Remy 强调："我甚至不需要重新解释任何一件事。"

这正是技能的核心价值：**它把"反复调教"变成了"一次封装，永久使用"**。

为了让我们更好地理解 AI Agent 是如何使用这些技能的，Remy 给出了一个极具画面感的比喻。他让我们把 Agent 想象成"你雇佣过的最能干的员工"：
- **他的办公桌**：是他的电脑，连接着所有工具（如 MCP）。
- **他的指令文件**：是在执行每个任务前都会阅读的说明文件。
- **他的书架**：上面摆满了各种 SOP 书籍，这就是技能库。每本书的"书脊"上都有书名和简单描述，帮助他快速找到目标。当他确定需要哪本书时，就会把它抽出来，阅读里面的详细步骤，然后按部就班地执行任务。

一个精心打磨的技能，每周可以为你节省大约 2 个小时。当你把工作中的各类重复性任务都封装为技能时，积累起来的效率提升将是"游戏结束"级别的竞争优势。

> 重要原话: "skills are literally just SOPs for AI" （技能本质上就是 AI 的标准作业程序） `[章节 0:00-2:30]`

**个人感受**

Remy 在描述这个过程时，言语中充满了掌控感和兴奋。他强调自己"对事情有非常具体的要求"，一旦他找到了完美的做事方法，就会把它固化为一个技能，然后"每次都能一击即中"。这不仅仅是一种效率工具，更是一种将个人经验和智慧"实体化"、"资产化"的方式。这种"一次输入，终身受益"的爽快感，正是技能让人着迷的地方。

**延伸思考**

这个"书架"的类比非常精妙。它暗示了未来 AI Agent 的工作模式：Agent 不仅是一个执行者，更是一个知识库的管理者和应用者。个人和公司的核心竞争力，将越来越体现在你拥有多少个高质量、可执行的"SOP"上。这也引出了一个问题：如果技能是 AI 时代的"数字资产"，那么我们该如何建立个人和团队的资产库？

### 技能的困境："微软 Word 时代"的 AI `[章节 2:30-4:30]`

**核心观点**
尽管技能极其强大，但当前我们正处于一个"AI 单机游戏"时代。每个人构建的技能都孤立地存在自己的电脑里，难以跨团队高效分享和管理，这严重阻碍了 AI 生产力的规模化。

**深度阐述**

在充分展示了技能的威力后，Remy 话锋一转，指出了当前面临的最大挑战：**AI 目前仍然非常"单机"（single player）**。

你的团队成员都在各自的电脑上使用 Claude 或 Codex，如果他们构建了一个出色的技能，这个技能就只是"活"在他们的机器上。"要正确地分享它是非常非常困难的，"Remy 说道。

为了让我们更好地理解这个困境，他引入了一个精彩的历史类比：**微软 Word 时代**。在个人电脑普及初期，你用 Word 创建了一个文档，它存储在你的电脑里。如果你想把它发给别人，你需要导出、发邮件，然后对方那里就有了一个副本。久而久之，你会有多个不同的副本在四处流传，根本没有一个"中央信息源"（Central Source of Truth）。如果修改了其中一个，其他副本并不会同步更新。

随后，Google Docs 解决了这个问题。它提供了一个云端文档，所有人都可以同时在里面协作，这就是一个中央信息源。

Remy 断言，**我们当前就处于"技能的微软 Word 时代"**。每个人都在创造有巨大价值的技能，但它们却像孤岛一样散落在个人电脑中。你构建了一个出色的技能，然后呢？你如何与团队分享？你如何确保他们使用的是最新版本？你如何管理团队的技能资产？

**个人感受**

Remy 对这个问题的描述非常精准："如果你把技能分享给团队，而每个人都在改进它（你也确实应该不断改进），你最后会得到 10 份不同的副本，却没有一个中央信息源。" 这不仅仅是技术上的不便，更是一种智力资产的巨大浪费。这种混乱状态，会极大地限制一个团队从 AI 中获取的整体价值。

**延伸思考**

这个"Word 时代"的类比深刻地揭示了技术发展中的普适规律：任何生产力工具，都必然会从"个人效率"走向"协作效率"。就像单机游戏终将被网络游戏取代一样，单人使用的 AI 技能也必然会向团队共享、协作的模式演进。谁能更早地建立这种"多人游戏"的基础设施，谁就能在未来的竞争中占据先机。

### 破解之道：GitHub 仓库 + 插件（Plugin）架构 `[章节 4:30-7:00]`

**核心观点**
Remy 分享的解决方案是：将所有技能集中存放于一个 GitHub 仓库中，并将其打包为一个"插件"（Plugin），从而为团队技能建立一个拥有版本控制的"中央信息源"。

**深度阐述**

既然问题是缺乏中央信息源，那么解决思路就是创建一个中央信息源。Remy 找到的最佳方案，是利用程序员们最熟悉的工具：**GitHub**。

他首先解释了为什么是 GitHub："你可以把 GitHub 想象成 Google Drive，只不过它是用来分享代码的。" 他用一个实际的仓库（repo）演示，这个仓库被命名为 "团队技能"（Team Skills），里面的技能按照部门（Department）进行分类，例如品牌（Brand）、内容（Content）、市场（Marketing）等。这样一来，你立刻就有了一个存放公司所有技能的、唯一的中央信息源。

但仅仅把技能放在一个共享文件夹里还不够。难点在于，如何让团队成员的 Claude Code 或 Codex 轻松地访问到这个仓库？Remy 的答案是：**把它制作成一个插件（Plugin）**。

这是整个环节中最关键的概念。Remy 解释道："插件实际上就是技能（Skills）、MCP 和钩子（Hooks）的捆绑包。" 你可以构建一个只包含技能的插件，也可以构建一个包含上述任意组合的插件。而 Remy 的解决方案，就是一个将技能"打包"起来的插件。

**为非技术背景人士的"祛魅"**：

Greg 敏锐地察觉到，很多人听到"代码仓库"和"插件"会本能地感到恐惧，认为这需要很高的技术门槛。Remy 对此进行了"祛魅"：作为一个完全没有开发背景的人，他强调，**只要你能理解"GitHub 就是一个存储文件的云盘"，以及"插件是让 AI 访问这些文件的一种方式"，你就掌握了全部所需的背景知识**。

为了让整个过程简单到任何人都可以操作，Remy 特意准备了一个提示词（Prompt），这个提示词可以在视频结束后提供给观众，观众可以直接将其交给 Claude，让 AI 自动完成将现有技能文件夹转化为符合要求的 GitHub 仓库和插件配置的全部工作。这意味着，你甚至不需要自己编写任何一行 JSON 配置文件。

> 重要原话: "as long as you can understand that GitHub is just a place to store your files on the cloud and then a plugin is just a way for Claude to access them, that's pretty much all you need to know." （只要你能理解 GitHub 只是云端存放文件的地方，插件只是让 Claude 访问这些文件的方式，那你需要知道的就是这么多了。） `[章节 4:30-5:15]`

**个人感受**

这个部分极大地降低了听众的心理门槛。它告诉我们，在 AI 时代，很多看似"极客"的操作，其核心思想其实非常简单。我们不必被工具的表面复杂性吓倒，而是应该专注于理解其背后的逻辑，并善用 AI 来为我们处理那些枯燥的技术细节。

**延伸思考**

Remy 用 AI 来构建 AI 工具链的方法，本身就是一种"技能"的应用。他不仅是在分享一个解决方案，更是在示范一种"元技能"——如何利用 AI 去解决复杂的工程问题。这种"让 AI 构建 AI 基础设施"的思维模式，将是未来每个知识工作者的核心能力之一。

### 安装插件与赋予团队力量：从仓库到个人终端 `[章节 7:00-9:30]`

**核心观点**
Remy 通过现场演示，展示了团队成员如何通过几个简单的终端命令安装插件，并启动"自动更新"功能，从而确保每个人都能即时获得最新的团队技能。

**深度阐述**

Remy 随即打开了他的终端，进行了一场快速且直观的现场演示，展示了团队成员安装这一系列技能的全部过程。

**步骤一：安装插件**。在 Claude Code 中输入 `/plugin`，会出现一个简单的管理菜单。点击"市场（Marketplaces）"，只需添加你 GitHub 仓库的链接，你的"团队技能"就会出现在列表中。这个过程被 Remy 比喻为"应用商店"：**市场（Marketplace）就像应用商店，插件（Plugin）就像里面的 App**。

**步骤二：按需分配**。由于技能按部门进行了分类，团队可以根据角色安装不同的插件。例如，他不一定希望负责文案的同事安装财务（Finance）部门的技能插件。这种"按需分配"的机制，为公司内的 AI 权限管理提供了极大的便利。他展示了一个例子：点击"通讯（Newsletter）"插件，里面会包含多个技能，如"每周研究"、"引言撰写"、"故事生成"和"TLDR"等。

**步骤三：开启自动更新（Auto-Update）**。这是整个流程中至关重要的一环。Remy 强调，所有安装者都必须开启"自动更新"。这一功能保证了当技能在中央仓库被修改时，所有团队成员的本地 AI 环境都能同步更新，从而彻底解决了之前"文件副本无法同步"的噩梦。

**跨平台兼容**：

当 Greg 询问这种方法是否仅限于 Claude Code 时，Remy 给出了更为振奋人心的答案。他本人已经分别在 Claude Code 和 Codex 中测试并使用了这个插件体系，效果完全一致，可以即插即用。他在 Codex 中演示了同样的操作，可以轻松看到并调用这些团队技能。这意味着，团队中可以有人使用 Claude，有人使用 Codex，都能无差别地共享同一个知识库，这极大地增加了系统的实用性和灵活性。

**技术背后的简单性**：

Remy 坦诚，他完全不知道这些 JSON 文件是如何让 AI 将这些技能识别为插件的具体技术原理，但他表示："我不需要知道。我只是让 Claude 帮我设置好了。" 这再次印证了他"人控逻辑，AI 控技术"的实践哲学。

> 重要原话: "The marketplace is kind of like the app store you're installing. And then the plugins themselves are kind of like the apps." （市场就像是你在安装的应用商店，而插件本身就类似于应用。） `[章节 8:00-8:30]`

**个人感受**

观看整个演示过程，你会感受到一种难以置信的流畅感。从打开终端到技能安装完毕，整个过程不到一分钟。这标志着 AI 技能的分享已经从"技术人员的专属技能"演变成"任何团队成员都可以轻松完成的一步操作"。

**延伸思考**

这个系统最强大的地方在于**"自动更新"和"按角色分配"**。它已经初步具备了企业级软件管理的特征：集中控制、版本管理、权限分配。这不仅仅是分享技能的方案，更是未来企业构建内部 AI 能力平台的蓝图。我们正在见证 AI 基础设施从"个人计算机时代"向"企业内部 IT 系统时代"的转变。

### 团队与个人技能库的分离：Remy Skills 的私人沙盒 `[章节 9:30-11:30]`

**核心观点**
在团队共享技能之外，Remy 还维护着一个独立的、仅属于自己的"个人技能仓库"（Remy Skills），用于存放不适合团队共享的个人偏好、实验性技能和云端 Agent 所需的技能。

**深度阐述**

共享是主题，但 Remy 也展示了系统中同样重要的另一面：**区分"团队资产"和"个人资产"**。

他分享了自己会维护另一个名为 "Remy Skills" 的单独仓库。在这个仓库里，存放着两类内容：
1.  **纯粹的个人技能**：这些技能过于个性化，无法在团队中复制。例如，他的"收件箱分类技能"（Inbox Triage Skill），这个技能教会 Claude 如何处理他的邮件；以及他的"晨间简报"（Morning Brief），这完全基于他的个人 App 使用习惯。这些技能就像牙刷，每个人都需要自己的那一支。
2.  **实验性/待定技能**：从互联网上下载的、还在尝试阶段的新技能。它们尚未经过实战检验，不适合大规模部署到团队，这里就像一个"个人沙盒"。

**为什么要这么做？**

当 Greg 追问，如果不对团队分享，为什么还要用 GitHub 仓库来管理这些个人技能？难道本地管理还不够吗？Remy 给出了几个深刻的理由：
- **单一信息源**：他喜欢将所有东西都放在一个地方。
- **云端访问**：这是最关键的一点。他现在会在云服务器（VPS）上运行自动化代理（如 Hermes 代理）。这些云端代理需要能够访问他的技能，而不是依赖他本地电脑的文件系统。将技能放在云端仓库，意味着他的 AI 代理可以在任何地方调用相同的知识库，而不仅仅是在他自己的电脑前。
- **版本控制**：拥有 Git 的历史记录，方便回溯和比较改动。
- **灾难备份**：这与接下来他的一个惨痛故事直接相关。

> 重要原话: "I'd rather them be somewhere on the cloud. So if I'm running like a Hermes agent on a VPS or some sort of cloud agents, they have a method to access my skills rather than them sit like all locally on my file system." （我宁愿把它们放在云端。如果我在 VPS 或某种云代理上运行 Hermes，它们就有办法访问我的技能，而不是让技能只保存在我的本地文件系统里。） `[章节 10:00-10:30]`

**个人感受**

Greg 在听完这个做法后，感慨道："我是说，这也很有道理，比如你本地电脑上的东西可能会被损坏，而且它现在在云端了。" 这句话引出了 Remy 一段至今仍让他心有余悸的经历。

**延伸思考**

Remy 的"个人技能库"模式揭示了一种极为超前的工作哲学：**技能是你的知识资产的备份和延伸**。它们不应该被锁在某个物理设备里，而应该储存在可访问、可复用、可进化的云基础设施中。这也回答了，为什么即使不分享，将技能放在云端仓库依然是更优越的管理方式。

### 惨痛教训：Claude 删除了他的 150 个技能 `[章节 11:30-12:15]`

**核心观点**
Remy 分享了一段真实的创伤经历——Claude 误删了他包含 150 多个技能（代表 500 多小时工作成果）的本地文件夹，因没有备份而全部丢失。这件事促使他采用了今天的云端 + 版本控制方案。

**深度阐述**

Remy 向 Greg 讲述了他下定决心采用这套系统背后的一个重要故事："大约两个月前，Claude 删除了我的 Claude 文件夹，里面存有 150 个技能，那可是至少 500 多个小时的工作成果。而我当时没有备份。那感觉糟透了。"

这不仅仅是一次数据丢失，更像是一次沉重的打击。Remy 称这段经历让他留下了"创伤后应激障碍"（PTSD）。这件事也让他意识到，仅仅依赖于本地文件的脆弱性。

Greg 对此报以深刻的理解，他回应："所以，你的意思是，不要成为两个月前的 Remy，而要成为今天的 Remy。我们正以极快的速度前进，都想尽快从 AI 中获取最大价值，有时候因为跑得太快，反而会忽略某些关键的事情。安全是一大问题，备份是另一大问题。很高兴你经历了这一切。"

Remy 的经历完美地证明了将技能放入 Git 仓库的必要性。在这个系统下，即使本地文件再次出现问题，云端仓库的版本控制也能确保所有技能的安全性。

**个人感受**

Remy 对这个故事的讲述带着一种真实的后怕和懊悔，他反思道："不备份真的太愚蠢了。" 这种坦诚的分享拉近了他与观众的距离。在这样的高速迭代时代，这种"翻车"经历几乎是每个人都会遇到的。它在提醒我们，效率不仅是"快"，更是"稳"和"可靠"。

**延伸思考**

这个故事颇具警示意味：我们将越来越多的"思考过程"和"工作方法"交给了 AI，那么这些"数字大脑"的安全性就必须得到最高级别的重视。将技能视为公司或个人的核心知识产权资产，并为其配备相应的管理、备份和分发基础设施，是每个重度 AI 用户都必须补上的重要一课。也许，"100% 云化 + 版本控制"的模式，就是对 AI 时代数据安全焦虑的一种终极解法。

### 面向未来的技能平台：可视化 UI 与用量追踪 `[章节 12:15-15:00]`

**核心观点**
Remy 在 GitHub 仓库之上构建了一个名为"技能助手"的网页应用，将技能库可视化，并展示了技能之间的调用关系，甚至通过插件中的钩子（Hooks）追踪技能的实际使用频率。

**深度阐述**

Remy 建立的系统并未止步于插件分发。他还为团队构建了一个非常炫酷的可视化界面，以解决技能越来越多后难以管理和查看的问题。

在视频中，他展示了一个网页应用，这个应用以他的"团队技能" GitHub 仓库作为后端。这意味着，网页中显示的每个技能，都是实时从这个中央仓库拉取的。

**技能图谱**：这个界面最引人注目的功能是**可视化技能之间的关联**。Remy 以"YouTube 发布工作流"为例：这是一个"编排者技能"（Orchestrator Skill），它会按顺序调用"标题"、"缩略图"和"描述"技能。在这个 UI 中，这些技能之间的箭头连接关系一目了然，清晰地展示了技能链（Skill Chain）的运转逻辑。这对于理解复杂工作流和向新员工解释 AI 系统如何运作，提供了极大的便利。

**技能助手**：对于新加入团队、对 AI 不太熟悉的成员，这个 UI 内置了一个"询问"按钮。例如，Remy 演示了向它提问："用于决策的最佳技能有哪些？" 助手会立刻搜索公司内部的私有技能库，并给出建议："LLM 委员会"、"Matt PCO 的 'Grill Me' 技能"、"Corey Haynes 的 '营销技能'"等。对于像"我刚刚完成了通讯稿的每周研究，下一步应该运行什么技能？"这种问题，助手也能提供清晰的工作流程指导，有效地帮助 AI 新手快速上手。

**用量追踪**：在视频当天，Remy 刚刚添加了最后一项创新功能：**使用量追踪条**。他在插件中加入了一个"钩子（Hook）"，每当 Claude 使用一个技能时，这个钩子就会被触发，从而记录使用次数和具体团队成员的使用情况。这样一来，他可以轻松地分析哪些技能是高频使用的，哪些是长期闲置的。他笑称，想做一个年终"Spotify 年度报告"，看看自己"使用提案技能 56 次"。更重要的是，这种追踪可以帮助他清理那些长期未使用的技能，防止技能库变得臃肿。

> 重要原话: "I wanted to see the skills that I never use like after 6 months. Like show me all the skills that I haven't touched once and they can probably go" （我想看看我六个月都没用过的技能。比如，把我一次都没碰过的技能都列出来，然后就可以清除了。） `[章节 14:30-15:00]`

**个人感受**

这个部分展示的远不止是一个工具，而是一种"工程化"思维。Remy 并没有在构建完插件分发后就止步，他还在持续思考如何让技能库"可视化"、"可管理"、"可度量"。这已经超越了个人效率工具，进入了"企业级 AI 知识管理"的范畴。他在用构建一个产品的心态来管理他的 AI 运营体系。

**延伸思考**

"用量追踪"和"可视化关联"的功能，预示了未来 AI Agent 管理平台的发展方向。当一个公司的 AI 技能积累到一定程度，深入挖掘这些数据（即"技能分析"）将产生巨大的价值。这就像一个知识管理仪表盘，可以帮助你了解团队的 AI 能力布局，发现效率瓶颈，并优化 AI 投资回报率。

### 技能设计哲学：厚技能（Thick Skills）与薄代理（Thin Agents） `[章节 15:00-17:30]`

**核心观点**
Remy 奉行"厚技能、薄代理"的设计哲学：保持 AI 代理的指令文件精简，而将所有的专业知识、背景和步骤全部封装在技能中，让技能成为主要的"策略外挂"。

**深度阐述**

面对 Greg 关于"如何决定创建多少技能"的疑问，Remy 给出了他清晰的个人框架。

**"只要不涉及物理劳动，就能自动化"**。Remy 的核心理念是，只要不是"洗盘子"这类物理性任务，公司中的任何线上流程都可以通过一个出色的技能或者一系列技能链条实现自动化。在他看来，任何他每天重复执行的任务，都值得"技能化"，因为"我不想再碰它了"。

**关于技能链的设计原则**：当一个流程较为复杂时，他会将其拆分为多个技能并串联运行（如"标题-缩略图-描述"的 YouTube 发布流程）。但这个拆分的原则并不是盲目的，而是基于一个简单的判断："如果在以后，我会有单独运行其中某个子流程的需求（比如我只想要一个缩略图），那么我就会把它做成一个技能链。"

**"边缘案例"的反思**：Greg 询问了如何利用记忆功能来自动化创建技能的过程。Remy 分享了一个他最近加入所有技能文件的"自我改进循环"提示词。这个提示词要求 AI 在每次技能运行结束时，反思"是否有任何步骤失败或需要变通？用户是否纠正或拒绝了任何有意义的输出？你是否发现未来运行可能需要的任何东西？"然后只提出有意义的改动建议。在每次技能运行后，AI 通常会给出一到两条小的改进建议，Remy 只需简短的"批准"或"拒绝"，这个"自我改进循环"就让技能在一次次使用中变得越来越强大，这被他称为"超级好用"的功能。

**"厚技能，薄代理"**：Remy 引用了他朋友 Russ Mike 的理念，强调了他的核心哲学：**"薄代理，厚技能"（Thin Agents, Thick Skills）**。这意味着要尽量保持 AI 代理（即其核心指令文件）的简洁和瘦身，而将所有的专业知识、详细的步骤和上下文都填充到技能里面，使技能变得"厚实"。因为技能承担了绝大部分的策略和指导，代理只需要专注于执行。Remy 相信，在这种架构下，即使是新手，只要能执行技能，也可以完成任务，个人能力对任务质量的制约会大幅降低。

> 重要原话: "I'm big like same as Russ Mike says that I'm like thin agents, thick skills." （我非常认同 Russ Mike 所说的，薄代理，厚技能。） `[章节 16:30-17:00]`

**个人感受**

这段"厚技能、薄代理"的哲学是整期节目智力密度最高的地方。它点明了技能系统的本质：**将"人"的隐性经验（知道什么是好的）显性化，并以标准化的格式注入到 AI 的执行管线中**。它不是简单地把 AI 当作"自动填充工具"，而是把 AI 当作一个有能力执行你的"方法论"的"超级执行者"。

**延伸思考**

"决策下放到技能"这一概念，深刻地改变了 AI 应用的设计架构。在传统架构中，策略写在主提示词里，就像公司的规章制度都写在员工手册里，管理僵化且低效。"厚技能"则更像现代组织中的"工作流程"和"SOP 系统"，每个技能都是一个独立的、可维护和可优化的自动化模块。这也意味着，在未来的 AI 时代，团队里的竞争力，将不再仅仅依赖于个人"写提示词"的技巧，而更多地取决于个人和团队**构建高质量、可落地"技能"的能力**。

### 结语：技能，AI 时代的"军备竞赛"与行动指南 `[章节 17:30-19:00]`

**核心观点**
Remy 和 Greg 总结了系统的价值，并鼓励观众立即行动，开始构建自己的技能库。技能是这个时代最大的"不公平优势"，而整个系统实现起来远比想象中简单。

**深度阐述**

随着对话进入尾声，两位对谈者将视野拉回到对未来的判断上。

**企业级价值**：Remy 坚信技能具有长期的价值。他提到："我相信，技能或许现在不是，但未来一定会为许多公司带来真正的企业级价值（Enterprise Value）。" 就像公司用标准操作流程（SOP）来培训员工执行任务一样，好的技能也起着同样的作用——培训 AI 去执行对公司而言有真实经济价值的任务。

**公司资产保全**：通过将技能集中存放在公司所有的 GitHub 组织里，即使有员工带着他个人电脑上那些"才华横溢"的技能离开公司，公司也能保留对这些核心 AI 资产的"所有权和控制权"。这对于公司的知识管理和资产完整性，是一个极具前瞻性的策略保护。

**"多人游戏"的未来**：Greg 总结道："我们似乎正在进入一个 AI 的多人游戏时代（Multiplayer AI）。" 他用软件发展的历史规律来类比："Figma（协作设计工具）之所以能成功，是因为在此之前必须要有 Photoshop（单机设计工具）作为基础。而现在，这个基础已经成熟了。我们正在从单机 AI 走向多人 AI。" 而技能，将会是这场多人叙事中最重要的"共享引擎"和"协同语言"。

**行动号召**：
Remy 鼓励观众："现在，就去创造一些技能吧。把这些技能放进你的公司里，把它变成一个插件（Plugin）。创建一个仓库。你会对你获得的输出感到惊讶。" 他强调，很多人尝试 AI 工具后感到沮丧，是因为他们没有得到想要的精确输出。而这些提示词和框架，将帮助你解决这个问题。只要你有勇气迈出第一步，把第一个技能放进 GitHub 仓库，并给 Claude 一个命令让它帮你打好基础，整套系统就会为你开启。

> 重要原话: "I think that agent skills are probably like the single most important concept" （我认为代理技能可能是目前最重要的概念。） `[章节 0:30-1:30]`

**个人感受**

节目的结尾充满了一种"动员"的氛围。Remy 和 Greg 不仅仅是分享了一个技巧，更是在号召所有人将 AI 的使用方式提升到一个新的战略高度。这套方法论的自洽性在于，它并不需要你成为技术专家，它需要的只是你拥有将知识工具化、资产化的"意识"和"行动力"。

**延伸思考**

"技能"，正在从一个模糊的功能概念，演变为未来 AI 产业中非常重要的"知识和经验包"单位。它将像文件格式一样普及化，甚至标准化。谁能更早地掌握构建、管理和分发技能的能力，谁就能在即将到来的"AI 多人游戏"时代占据先机。这不仅是效率的"军备竞赛"，更是关于知识产权的"军备竞赛"。

## 精华收获

这期节目远不止是讲解了一个技术操作，它为我们揭示了在 AI 时代，个人与团队如何构建核心竞争力的系统性思维：

1.  **重新定义 AI 交互方式**：忘掉那些冗长的提示词吧。技能的核心理念是将你的方法论和标准"封装"起来，让 AI 一次到位，彻底告别"产出垃圾-反复调校-再次生成"的低效循环。
2.  **从"单机"到"多人"**：AI 的应用已经跨过了孤军奋战的阶段。利用 GitHub 作为中央知识库，以插件形式分发，并开启自动更新，是团队级 AI 协作的可行路径。这解决了 AI 知识和技能"资产化"和"规模化"的难题。
3.  **"厚技能，薄代理"的设计哲学**：保持 Agent 核心指令简洁，把知识全放到技能文件夹里。这让你能从任何 AI 客户端中获得一致性输出，让你的实践经验可以跨平台、跨团队无损复制。
4.  **建立个人与团队的双轨制**：将适合团队共享的"公司技能"和仅限个人使用的"个人技能"分开，利用版本控制进行管理，既能促进团队效率，又能保护个人工作流。更别提，这可以作为你丢失全部技能的"后悔药"。
5.  **用技能构建公司的隐性资产**：每一次关于"如何做好 XX"的知识封装，都是你个人或公司在 AI 时代的一笔"知识存款"。这些可执行、可复用的技能，将是未来的核心竞争力，它不依赖于某个特定的员工，而属于整个组织。

**行动清单**：
- **第一步**：整理你当前工作流中重复性最高的 3-5 个任务。
- **第二步**：为每个任务编写一个详细的 Markdown 文件（即技能），包含步骤、偏好、注意事项和示例。
- **第三步**：将你的技能文件上传到一个新的 GitHub 仓库中。
- **第四步**：使用节目提供的提示词（在视频描述中），让 Claude 帮你把这个仓库配置成一个插件（Plugin）。
- **第五步**：在你的 Claude Code 或 Codex 中，通过 `/plugin` 命令添加该 GitHub 仓库作为 Marketplace 并安装。
- **第六步**：将安装步骤分享给你的团队成员，并确保大家开启"自动更新"。

不要成为浪费时间在反复调教 AI 上的人。现在，就去创造属于你的技能吧。
